# 00 项目概述与业务蓝图

> 本文是全项目的起点。任何 AI 会话开始前必须先读本文建立业务认知。
> 术语含义不确定时读 [09-领域术语与编码规则.md](./09-领域术语与编码规则.md)。

---

## 1. 项目一句话定义

为**单厂多车间**的服装加工厂提供一套从 **裁剪 → 打菲 → 缝制计件 → 工资结算 → 入库 → 销售 → 收款 → 记账** 全链路的 ERP 系统，
由 AI 依据 `docs/` 内的规范全流程开发（设计 / 编码 / 测试 / 归档 / 发布）。

---

## 2. 业务背景与痛点

| 现状痛点 | 系统对应能力 |
| --- | --- |
| 裁剪数量与打菲数量对不上，损耗说不清 | 裁剪单 → 打菲单 → 缝制产出 逐层结转，损耗可追溯 |
| 车工做多少靠组长手工登记，月底算工资扯皮 | 扫码计件流水（唯一事实来源），实时可见，结算锁定不可反悔 |
| 员工不知道自己做了多少、多少钱 | 员工端 H5：扫码绑定工序 → 实时看数量 → 看当期工资 |
| 布料/辅料/成衣库存账实不符 | 批次（缸号）实际成本 + 选批出库 + 盘点 + 全量流水台账对账 |
| 客户应收应付靠 Excel，月底对不上 | 应收应付流水 + 核销 + 客户对账单 |
| 单据被随意改，改了没人知道 | 单据状态机 + 审核反审核 + 全量操作日志 |
| 老板看不清哪个款赚钱 | 款式成本毛利分析、计件成本归集 |

## 3. 范围（Scope）

### 3.1 本期要做（Must）

| # | 模块 | 核心交付 |
| --- | --- | --- |
| M1 | 基础资料 | 款号、物料（面料/辅料/成衣）、工序、单价、仓库、车间、组别、员工、客户、供应商、计量单位 |
| M2 | 裁剪 | 裁剪单（按款号+颜色+尺码+匹数+层数）、耗料出库、裁剪损耗统计 |
| M3 | 打菲 | 打菲单（一扎/一件式）、生成**唯一二维码/条码**、打印标签 |
| M4 | 扫码计件 | 员工扫码绑定款号+工序+色组；工位机扫码枪计件；计件流水实时入账 |
| M5 | 工资 | 按款号×工序×单价结算工资；反审核锁定；工资条；代发文件导出 |
| M6 | 库存 | 物料（面料/辅料）与成衣**双栈**；批次成本；出入库、调拨、盘点、库存台账 |
| M7 | 销售 | 销售订单、发货、销售单、成品出库、销售单价 |
| M8 | 应收应付 | 客户/供应商往来流水、收付款、核销、账龄分析、对账单 |
| M9 | 财务凭证 | 采购入库、销售出库、收款、付款、工资计提 → 自动生成记账凭证（借贷平衡） |
| M10 | 权限 | RBAC + 数据范围隔离；PC 管理端与员工端分开授权 |
| M11 | 员工端 H5 | 手机号登录 / 扫码绑定工序、看计件数量、看工资 |
| M12 | 报表 | 款式进度、计件汇总、库存台账、毛利分析、对账表 |

### 3.2 本期不做（Not Now，架构上预留扩展点）

- 多租户 SaaS（预留 `tenant_id` 字段位，当前不启用）
- 微信小程序 / 企业微信原生端（预留 auth provider 抽象，见 §5.3）
- PDA 专用 App（当前用 H5 + 工位机扫码枪覆盖）
- 完整会计科目体系自动建账（提供基础科目 + 凭证模板，允许手工调科目）
- 条码打印机专用驱动（先走标准标签打印 / CSV 导出给标签软件）
- 跨境多币种（金额一律本位币 RMB）

## 4. 角色与数据范围

| 角色 | 典型岗位 | 数据范围 | 关键权限 |
| --- | --- | --- | --- |
| 老板 / 总经理 | 管理层 | 全厂 | 全部只读 + 报表 + 审批终审 |
| 车间主管 | 裁剪组头、缝制组长 | 本车间 | 本车间单据审核、计件确认、进度查看 |
| 仓管 | 仓库管理员 | 全厂库存 | 出入库、调拨、盘点（不可改成本） |
| 跟单 | 跟单员 | 自己负责的款号 | 款号进度、客户订单查询 |
| 财务 | 会计 | 全厂 | 应收应付、收付款、凭证、反审核 |
| 采购 | 采购员 | 全厂物料 | 采购单、供应商资料 |
| 计件员 | 结算员 | 全厂 | 计件单价维护、工资结算 |
| 员工 | 车工、查勘 | **仅本人** | 扫码绑定工序、看自己计件数、看自己工资 |

**数据范围（Data Scope）四级**：`SELF`（本人）/ `GROUP`（本组）/ `WORKSHOP`（本车间）/ `FACTORY`（全厂）。
详见 [07-认证与权限规范.md](./07-认证与权限规范.md)。

## 5. 核心业务链路

### 5.1 生产主链路（数据流）

```
基础资料(款号/物料/工序/单价/仓库)
      │
      ▼
[裁剪单] ──耗料出库──▶ 物料库存(批次/色组/匹数)
      │                      │ 裁剪损耗
      ▼                      ▼
[打菲单] ──生成二维码──▶ [打印标签]      布料消耗核销
      │
      ▼
[缝制计件] ──扫码流水──▶ [计件明细] ──结算──▶ [工资单]
      │                                          │
      ▼                                          ▼
[完工入库] ──▶ 成衣库存(款号/色/码/扎)    [工资计提 → 凭证]
      │
      ▼
[销售单] ──▶ 发货/出库 ──▶ [应收] ──▶ [收款核销] ──▶ [凭证]
```

### 5.2 关键不变量（Invariants，AI 必须严格遵守）

| # | 不变量 | 说明 |
| --- | --- | --- |
| INV-1 | **一衣一码** | 每件（每扎）成衣有唯一 `bundle_no`，二维码内容为该号，终生不变 |
| INV-2 | **计件不可静默修改** | 已结算的计件流水只能通过"红冲 + 补录"两笔新流水修正，禁止 UPDATE 金额/数量 |
| INV-3 | **工序单价快照** | 计件流水落库时把当时单价快照进 `unit_price`，后续改基础资料不影响历史 |
| INV-4 | **批次成本不可篡改** | 已入库批次的成本只能通过盘点差异调整，不能直接 UPDATE |
| INV-5 | **凭证借贷平衡** | 每张凭证 `sum(debit) == sum(credit)`，由数据库约束 + 测试双重保证 |
| INV-6 | **成结转闭环 + 整件口径** | `裁剪数量 ≥ 打菲数量 + 损耗数量`；`打菲数量 ≥ 已完工入库数量 + 在制数量`；**所有数量向下取整到整件，不足一件的余量（`balance_qty`）计入裁剪损耗，不生成码、不计件、不入库**（[09 §4.2](./09-领域术语与编码规则.md)） |
| INV-7 | **软删** | 所有业务表带 `deleted_at`，列表查询默认过滤，统计时明确是否含已删 |
| INV-8 | **权限双校验** | 后端必须同时校验「操作权限」和「数据范围」，前端隐藏 ≠ 安全 |

### 5.3 可插拔点（架构预留，AI 不要擅自扩展范围）

| 扩展点 | 当前实现 | 未来替换 |
| --- | --- | --- |
| 员工登录方式 | 手机号 + 验证码 | 微信 H5 授权 / 企业微信 / 小程序（实现同一 `AuthProvider` 接口即可） |
| 二维码载体 | 二维码内容为 `bundle_no` | 小程序码 / 动态码（后端生成逻辑不变） |
| 计件终端 | 工位机 PC + 扫码枪 | PDA / 小程序（写入同一 `piecework_logs` 表） |
| 通知渠道 | 站内信 | 企业微信机器人 / 短信（实现 `Notifier` 接口） |
| 币种 | 单币 RMB | 多币（`amount` 字段加 `currency` 后缀） |

## 6. 非功能需求

| 维度 | 目标 | 说明 |
| --- | --- | --- |
| 性能 | 列表页 P95 < 800ms；扫码计件落库 P95 < 150ms | 计件写入必须同步返回，不做异步 |
| 并发 | 计件写入 50 QPS 无丢失；同 `bundle_no` 不重复计数 | 数据库唯一约束兜底，禁止"先查后插" |
| 可用 | 工作时间 99.5%（不含计划维护） | 单实例 + 每日备份足够，不上 K8s |
| 数据 | 每日 1 次全量备份 + WAL 归档，保留 30 天 | 见 11-部署运维与发布规范 |
| 可审计 | 单据变更全量留痕，日志不可删除 | `document_logs` 表 + 数据库权限禁止 DELETE |
| 移动端 | 员工端适配 iOS Safari / Android Chrome / 微信内置浏览器 | 首屏 < 2s，触控目标 ≥ 44px |

## 7. 里程碑路线图

| 阶段 | 内容 | 出口标准 |
| --- | --- | --- |
| **P0 地基** | 规范定稿、项目骨架、CI、部署流水线、认证权限、基础资料 | 能登录、能建款号、能发一个 API token |
| **P1 生产主线** | **库存基础表（`material_stocks` / `wip_stocks`）** + 裁剪单、打菲单、二维码打印 | 能从裁剪到打菲全流程走通并打印标签 |
| **P2 计件工资** | 扫码计件（工位机 + H5）、单价管理、工资结算 | 员工扫码能查到自己件数与工钱 |
| **P3 库存** | 物料/成衣双栈、批次成本、出入库、调拨、盘点 | 裁剪耗料能自动出库，完工能自动入库 |

> ⚠️ **REV-2026-10 修订：库存的「基础表」提前到 P1，库存的「业务」仍在 P3**
> （业务方 2026-10-04 定的方案 A）。
>
> 起因是一个**数据模型与路线图不匹配**：`cutting_order_lines.stock_id` 外键指向
> `material_stocks`，也就是说**裁剪单的核心动作「锁一个布批」需要库存表先存在** ——
> 而原路线图把库存整个放在 P3。实测结论（P1 开工前的就绪度检查）：
>
> ```
> ⛔ cutting_orders              被 material_stocks 阻塞
> ⛔ cutting_order_lines         被 cutting_orders 阻塞
> ```
>
> 把 `material_stocks` / `wip_stocks` 建出来不代表 P1 做库存业务 —— P1 只用它的
> **「按批次列出来 + 锁一行」** 这两个读能力（选批候选），耗用扣减、入库、调拨、盘点
> 仍然全在 P3。⚠️ **如果把这两张表按完整库存模块建**（含出入库单、成本结转），
> 那 P1 就会顺手把 P3 的核心做完，两个阶段的边界就没了 —— 建表卡的范围必须写死这一点。
| **P4 销售往来** | 销售单、发货、应收、收款、核销、对账单 | 客户对账能对平 |
| **P5 财务凭证** | 凭证模板、自动过账、科目表、反审核控制 | 一笔销售全流程能自动生成三张凭证且借贷平衡 |
| **P6 报表与打磨** | 款式进度、毛利分析、UI 统一、员工端体验 | 老板看板可上线 |

**并行约束**：每个阶段结束后必须通过 `docs/02-AI开发流水线规范.md` 第 6 节 5 道闸门才能进下一阶段。
