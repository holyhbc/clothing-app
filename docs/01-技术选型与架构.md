## 1. 选型总表

| 层 | 选型 | 版本 | 为什么选它 |
| --- | --- | --- | --- |
| 后端语言 | Python | 3.12 | 报表/数据处理生态强，AI 生成代码产出率高（框架约定少） |
| Web 框架 | FastAPI | 0.115+ | Pydantic v2 自动校验 + 生成 OpenAPI + 自带 async，比 Django 轻、比 Flask 规范 |
| ORM | SQLAlchemy | 2.0（`Mapped[]` / `mapped_column` 风格） | 2.0 有静态类型，配合 `asyncpg`；复杂查询可退到 Core 写 SQL |
| 数据迁移 | Alembic | 最新 | SQLAlchemy 官方，autogenerate + 手写可控 |
| 数据库 | PostgreSQL | 16 | **不做多行任务主数据首选**：并发计件写入可用 `SELECT ... FOR UPDATE`、窗口函数做工资汇总一行出结果、JSONB 存单据扩展字段、`numeric` 精确金额。MySQL 在这几项上都要绕路 |
| 缓存 / 队列 | Redis | 7 | 会话、幂等键、倒计时缓存、条码生成队列。**不使用 Redis 做唯一数据源** |
| PC 前端 | Vue | 3.5 + TypeScript 5.6 + Vite 6 | 单文件组件 + `<script setup>`，AI 产出可预测 |
| UI 库（PC） | Ant Design Vue | 4.2.x | 单据型 ERP 需要的 Table / Form / Tree / Transfer / Steps 全都有，不用自己写 |
| 员工端 | Vue 3 + Vant | Vant 4 | 移动端组件，微信内置浏览器兼容性已处理 |
| 状态管理 | Pinia | 3.x | 官方唯一推荐 |
| 路由 | Vue Router（PC）/ 同一份（员工端用独立 layout） | 4.x | — |
| 实时提示 | SSE（Server-Sent Events） | — | 计件数量刷新只读，SSE 比 WebSocket 简单，且能穿透 nginx |
| 测试 | pytest + pytest-asyncio + httpx / Vitest + Playwright | — | 见 [10-测试规范.md](./10-测试规范.md) |
| 代码质量 | ruff（lint+format）+ mypy（后端）/ vue-tsc（前端） | — | ruff 一把梭，替代 flake8+isort+black |
| 包管理 | pnpm（前端）+ uv（后端 Python） | — | uv 装依赖比 pip 快一个数量级 |
| 部署 | Docker Compose | — | 2C12G 不需要 K8s，见 §3 |

## 2. 为什么不用其他方案（已评估，勿重复讨论）

| 被否方案 | 否决理由 |
| --- | --- |
| MySQL | 并发计件写入需靠应用层串行化；工资汇总没有窗口函数，需自写递归 CTE；JSON 字段不能索引 |
| Django | 自带 admin/admin 后台对本项目是负担（我们要精细化权限，不是白送的 admin）；ORM 隐式行为多，AI 容易生成出不可预测代码 |
| Node/NestJS | 与 Python 报表/Excel 导出生态脱节；本项目报表重，Python 优势明显。代价是双栈，端类型需手工同步（用 OpenAPI 生成） |
| React + Ant Design | 与 Vue 等价，中后台组件齐全度 Ant Design Vue 略优；团队/AI 在 Vue 单文件组件上产出更稳定。若未来需要换，见 `adr/` |
| K8s | 2C12G 集群控制面本身就要吃掉 1-1.5G 内存，收益为负 |
| 小程序原生 | 需企业主体认证（300元/年），且要过微信审核；先用 H5，`AuthProvider` 抽象已预留切换 |
| 微服务 | 单厂多车间规模，微服务是纯粹的复杂度负担。单体 + 模块化边界清晰 |

## 3. 资源规划（VPS 2C / 12G）

### 3.1 生产环境预算

| 服务 | CPU | 内存上限 | 说明 |
| --- | --- | --- | --- |
| `nginx` | 0.3 | 256M | 反代 + gzip + 静态资源缓存 |
| `api`（uvicorn 2 worker） | 0.8 | 1.5G | Python 3.12 单 worker RSS 约 350-500M |
| `worker`（异步任务 1 实例） | 0.4 | 800M | 报表导出、条码批量生成 |
| `postgres` | 0.6 | 3G | `shared_buffers=1GB`，`work_mem=16MB`，`max_connections=60` |
| `redis` | 0.2 | 384M | `maxmemory=256mb`, `allkeys-lru` |
| **合计** | **≈2.3** | **≈6G** | 留约 5G 给系统与构建峰值 |

### 3.2 关键约束（必须写进 compose）

```yaml
# 关键参数，勿随意上调
postgres:
  command:
    - postgres
    - -c
    - shared_buffers=1GB
    - -c
    - work_mem=16MB
    - -c
    - max_connections=60
    - -c
    - shared_preload_libraries=pg_stat_statements
  deploy:
    resources:
      limits: { memory: 3G }
```

- 数据库 `max_connections=60`，应用侧 `pool_size=10, max_overflow=10` × 2 worker = 40，留 20 给 psql/备份。
- **禁止**在同一台 VPS 上跑开发环境 + 测试环境 + 生产环境三份数据库。开发用 `docker compose -f docker-compose.dev.yml` 限制内存 3G，需要时再起；或者开发只在本地跑，VPS 只跑生产。
- 前端构建（`pnpm build`）会瞬时吃掉 2-3G 内存，**必须在 CI 上构建镜像并推私有仓库**，不要在生产 VPS 上构建。见 [11-部署运维与发布规范.md](./11-部署运维与发布规范.md)。

## 4. 架构分层

```
┌─────────────────────────────────────────────────────┐
│  表现层  PC(Vue3+ADVue)   员工端(Vue3+Vant H5)      │
└───────────────┬─────────────────────────────────────┘
                │ HTTPS / JSON，Cookie + JWT 双通道
┌───────────────▼─────────────────────────────────────┐
│  接口层  FastAPI Router                              │
│          依赖注入：鉴权 → 数据范围 → 参数校验         │
└───────────────┬─────────────────────────────────────┘
┌───────────────▼─────────────────────────────────────┐
│  应用层  Service（事务边界唯一入口）                  │
│          状态机迁移、权限二次校验、领域事件派发        │
└──────┬───────────────┬──────────────────┬───────────┘
       │               │                  │
┌──────▼──────┐ ┌──────▼───────┐ ┌────────▼────────┐
│ 仓储层      │ │ 核算/单据引擎  │ │ 异步任务        │
│ Repository │ │ 凭证引擎      │ │ worker(Redis)   │
│ 只做查询   │ │ 成本引擎      │ │ 报表/条码       │
└──────┬──────┘ └──────┬───────┘ └─────────────────┘
       │               │
┌──────▼───────────────▼─────────────────────────────────┐
│  存储层  PostgreSQL 16   Redis 7   对象存储(本地/MinIO)│
└───────────────────────────────────────────────────────┘
```

### 4.1 分层硬规则

| 规则 | 说明 |
| --- | --- |
| Router 不写业务 | Router 只做：依赖声明 → Pydantic 校验 → 调 service → 包装响应 |
| Service 是唯一事务边界 | `async with session.begin():` 只出现在 service 方法第一层 |
| Repository 只查不写业务 | 只提供查询方法；写入由 service 直接操作模型 |
| 跨模块调用走 service 接口 | 模块间不互相 import Repository |
| 状态机只在 service | 状态字段禁出现在 Router/Repository 层 |
| 领域事件异步化 | `计件入库 → 工资计提`、`销售出库 → 凭证` 走 Redis Stream，**但计件落库必须同步** |

## 5. 关键技术约定

### 5.1 认证方案

- PC 端：`Authorization: Bearer <access_token>`（15 分钟）+ `refresh_token` HttpOnly Cookie（7 天）
- 员工端 H5：短期 token（2 小时）+ 设备绑定，防止员工互相用手机登录
- 密码：argon2id 哈希，禁止 MD5/SHA1
- 详见 [07-认证与权限规范.md](./07-认证与权限规范.md)

### 5.2 统一响应

```json
{ "code": 0, "message": "ok", "data": {...}, "request_id": "01JB..." }
```
- `code = 0` 成功；非 0 为业务错误码（见 [05-接口设计规范.md](./05-接口设计规范.md) §4）
- 列表统一：`{ "items": [...], "total": 123, "page": 1, "page_size": 20 }`

### 5.3 数据库访问

- 全部 `asyncpg` + SQLAlchemy async
- 只读报表可走 `text()` 写原生 SQL（复杂聚合、窗口函数），**必须写 SQL 单元测试**
- 所有多表写操作放在一个事务里，禁止跨事务补偿

### 5.4 实时

SSE 端点 `/api/v1/events/stream`（统一端点，按 `AuthContext` 决定推送范围：员工端看自己数量，主管看车间），事件：
`piecework_counted` / `payroll_settled` / `stock_low` / `doc_approved`
