# 02 AI 开发流水线规范

> 目标：**让 AI 独立完成"设计 → 编码 → 测试 → 归档 → 发布"全流程**，且每一步都可审计、可回滚。
> 本文是 `AGENTS.md` 第 1 节强制工作流的展开细则。

---

## 1. 全流程总览

```
        ┌──────────────── 阶段 0：需求澄清 ────────────────┐
   用户需求 ──▶ /clarify ──▶ 需求卡（docs/requirements/）
                              │
        ┌──────────────── 阶段 1：设计 ────────────────────┐
                    /design ──▶ 设计稿 + ADR + 库表草图
                              │  ⚠ 需用户确认后才可继续
        ┌──────────────── 阶段 2：拆任务 ────────────────────┐
                    /plan   ──▶ 任务卡（<1 天，可独立验收）
                              │
        ┌──────────────── 阶段 3：编码 ────────────────────┐
                    /implement（逐任务）──▶ 代码 + 迁移 + 测试
                              │
        ┌──────────────── 阶段 4：测试 ────────────────────┐
                    /test   ──▶ 覆盖率报告 + E2E + 闸门
                              │
        ┌──────────────── 阶段 5：归档 ────────────────────┐
                    /archive ──▶ 变更记录 + 文档同步 + 提交
                              │
        ┌──────────────── 阶段 6：发布 ────────────────────┐
                    /release ──▶ 镜像 + 迁移 + 健康检查 + 回滚预案
                              │
                    /verify ──▶ 上线后冒烟验证 + 归档完成
```

阶段之间**不允许跨步**。每个阶段有明确的"出口条件"，不满足就停下并告知用户。

---

## 2. 各阶段规则

### 2.1 阶段 0：需求澄清 `/clarify`

**输出**：需求卡（`docs/requirements/REQ-NNN-短标题.md`），必须包含：
- 背景与业务目标（为什么做，不是做什么）
- 用户角色与场景（谁在什么场景下用）
- 输入 / 输出 / 业务规则
- **明确的非目标**
- 待决问题（对应 [09](./09-领域术语与编码规则.md) §4 的 Q 编号，或新增）

**硬规则**：
- 业务规则必须来自用户或文档。**AI 不得自行发明业务规则**（例如"默认审批人是车间主管"这种必须问）。
- 出现"待决问题"时，如果它影响核心逻辑，**必须停下提问**，不要"先按常见做法做"。

### 2.2 阶段 1：设计 `/design`

**输出**：
1. 设计文档 `docs/modules/<模块>-<功能>.设计.md`，用 [templates/设计文档模板.md](./templates/设计文档模板.md)
2. 若涉及技术决策 → 新增 `docs/adr/NNNN-*.md`
3. **将要改动的文件清单**（给用户确认，禁止直接落地）

设计文档必填章节：
- 背景 / 目标
- 领域模型（实体、字段、关系、约束、不变量）
- 状态机（若有）
- 接口清单（方法、路径、请求、响应、权限点、错误码）
- 并发与幂等方案
- 风险与回滚方式
- 待决问题

**出口条件**：用户明确回复"设计通过/可以开工"。未确认不得写代码。

### 2.3 阶段 2：拆任务 `/plan`

**输出**：任务卡列表，写入 `docs/tasks/` 或需求卡内。任务粒度标准：
- **≤ 1 天**单人可完成
- 改动文件数 ≤ 8
- 有明确验收标准（可自动化验证优先）
- 有独立可运行/可测试的形态

任务卡模板见 [templates/任务卡模板.md](./templates/任务卡模板.md)。

任务卡之间标注依赖关系（`depends_on: [T-003]`），串行/并行都要写清。

### 2.4 阶段 3：编码 `/implement <任务卡号>`

**编码顺序（每个任务固定）**：
1. 迁移文件（库表）
2. 模型 → Schema → Repository → Service → Router（自底向上）
3. 前端 `shared` 类型与 API → `admin`/`mobile` 页面
4. 测试
5. 顺带更新受影响的 docs（这一步经常被 AI 跳过，**属于验收项**）

**每个任务结束的必检项**：
- [ ] 库表含审计字段 + `version` + `deleted_at`
- [ ] 状态变更走 service 迁移方法并写 `document_logs`
- [ ] 所有新接口有权限声明 + 错误码 + OpenAPI `tags`
- [ ] 无硬编码业务常量
- [ ] 测试先红后绿（提交记录里能看出）
- [ ] `docs/12` 变更记录已加行

### 2.5 阶段 4：测试 `/test`

见 [10-测试规范.md](./10-测试规范.md)。AI 必须在回复中给出：测试清单、覆盖率、通过/失败明细。

### 2.6 阶段 5：归档 `/archive`

见 [12-文档与变更归档规范.md](./12-文档与变更归档规范.md)。产出：
- 变更记录新增行
- 任务卡状态置 `done` 并填实际改动文件列表
- 遗留问题登记
- 提交（Conventional Commits）

### 2.7 阶段 6：发布 `/release`

见 [11-部署运维与发布规范.md](./11-部署运维与发布规范.md)。铁律：
- **发布前必须有备份成功的证据**
- **迁移必须先在预演环境跑通 up + down**
- **必须有回滚方案，且回滚步骤要写进发布单**
- **发布单里 AI 不得自动执行 `docker compose down -v` 或任何删数据命令**

## 3. 五道闸门（Definition of Done）

任何任务/合并请求必须依次通过，**任一失败即停止**：

| 闸门 | 命令 | 通过标准 |
| --- | --- | --- |
| **闸门 1 lint** | `cd backend && uv run ruff check . && uv run ruff format --check .`<br>`cd frontend && pnpm lint` | 0 error |
| **闸门 2 typecheck** | `cd backend && uv run mypy app`<br>`cd frontend && pnpm typecheck` | 0 error |
| **闸门 3 单测** | `cd backend && uv run pytest -q --cov=app --cov-fail-under=80`<br>`cd frontend && pnpm test:unit` | 全部通过，覆盖率达标 |
| **闸门 4 迁移** | `uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head` | 正向成功、可回滚、再正向成功 |
| **闸门 5 构建** | `scripts/gate.sh`（等价于 `docker compose -f docker-compose.ci.yml build api-image web-image` + `docker compose -f docker-compose.ci.yml run --rm api-image` 与 `... run --rm web-image`） | 两个生产镜像都能构建，且**起得来**（`run --rm` 是真的跑一遍 entrypoint，只 build 不 run 会漏掉镜像里漏拷文件、配置语法错这类只在启动时暴露的问题 —— `nginx -t` 顺带验证 runtime 阶段的 COPY） |

> ⚠️ **REV-2026-10 修订（闭环 Q-P0-09）**：这一行原先写 `docker compose build`，
> 而生产 compose（`docker-compose.prod.yml`）里**按 docs/11 §3 没有 `build:` 段** ——
> 照原文敲会构建出**零个镜像**然后报「no such service」，看起来像环境坏了。
> 真相是：闸门要构建的是 **CI 用的** 镜像（`docker-compose.ci.yml` 里的
> `api-image` / `web-image` / `lint`），它们带 `build:`；生产 compose 只引用已构建的镜像。
> 「AI 不得在生产 compose 里加 `build:`」这条禁令（11 §3）说的是**生产编排**，
> 不是**构建闸门**，两者不冲突 —— 但原文用同一个 `docker compose build`
> 指代两件事，就必然有人踩。
>
> ⚠️ 因此**闸门一律走 `scripts/gate.sh`**：它把「构建一次 + 按顺序跑 5 道 + 失败即停」
> 固定下来。手工敲 6 条命令时最容易漏掉开头的 build，于是闸门跑的是**上一次的镜像**，
> 失败信息长得像代码 bug（真实踩过：刚加的迁移 0003 被报成 "Can't locate revision"）。

**闸门补充规则**：
- 后端新增/修改代码行覆盖率 ≥ 80%，核心 service（计件、工资、库存、凭证）≥ 90%。
- 前端新增组件必须有至少 1 个单测；PC 端关键页面（单据列表/单据详情/审批）必须有 E2E。
- 闸门不允许被跳过或配置放宽。要放宽先改本文并写 ADR。

## 4. AI 分工：主 agent 与子 agent

| 角色 | opencode agent | 职责 | 权限 |
| --- | --- | --- | --- |
| 编排 | `build`（默认） | 与用户对话、拆任务、串流程、把关闸门 | 全权限 |
| 架构 | `architect` | 产出设计稿与 ADR，不写业务代码 | `edit: 仅允许写 docs/` |
| 后端 | `backend-dev` | 实现后端任务卡 | `edit: 允许 backend/` |
| 前端 | `frontend-dev` | 实现前端任务卡 | `edit: 允许 frontend/` |
| 测试 | `qa` | 补测试、跑闸门、出测试报告 | `edit: 允许 tests/` |
| 审查 | `reviewer` | 只读审查，指出违反规范处 | `edit: deny` |
| 发布 | `releaser` | 执行发布单，出发布报告 | `edit: deny`，bash 需确认 |

**规则**：
- 一次任务只派 1 个子 agent 干，改完由主 agent 复核，**不要并行派多个改同一片代码**。
- 跨模块任务拆成多次派发（见 AGENTS.md §6）。
- 子 agent 的产出必须由主 agent 对照规范逐条复核后才可提交。

## 5. 提示词使用约定

所有提示词模板集中在 [13-AI提示词与任务模板库.md](./13-AI提示词与任务模板库.md)。
命令（`/design` `/implement` 等）实现在 `.opencode/command/`，skill 实现在 `.opencode/skills/`。

**通用要求**：每个提示词开头都要带"先读哪些 docs"的清单，避免 AI 用通用知识猜业务规则。

## 6. 风险控制

| 风险 | 控制手段 |
| --- | --- |
| AI 幻觉出不存在的字段/接口 | 设计阶段强制出接口清单与库表草图；编码阶段对照已有实现 |
| 一次性改动过大无法 review | 单次提交 ≤ 1200 行手写、≤ 3 模块；**单文件 ≤ 400 行**（ADR-0030）；超了必须先出设计 |
| 数据被 AI 误删 | 硬删命令在权限层 deny；删除走软删；备份每日执行 |
| 迁移不可逆 | 闸门 4 强制验证 down；生产迁移必须先在生产数据副本上演练 |
| 并发写入重复计数 | 数据库唯一约束 + 幂等键；并发测试必写 |
| 凭证不平 | 数据库约束 + 单测 + 发布前自动对账脚本 |
