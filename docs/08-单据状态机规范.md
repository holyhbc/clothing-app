# 08 单据状态机规范

> 本项目所有业务单据**必须**经状态机流转。状态只能由 service 层迁移方法变更，
> Router / Repository / 脚本**禁止**直接写 `status` 字段。

---

## 1. 通用状态定义

```python
# app/common/enums.py
class DocumentStatus(StrEnum):
    DRAFT = "DRAFT"          # 草稿：可编辑、可删除
    SUBMITTED = "SUBMITTED"  # 已提交待审核：只读
    APPROVED = "APPROVED"    # 已审核：生效，参与库存/计件/成本
    REJECTED = "REJECTED"    # 已驳回：回到可编辑，需重新提交
    CANCELLED = "CANCELLED"  # 已作废：终态，只读
    PAID = "PAID"            # 已发放/已结清：仅工资单使用，REV-2026-10 新增
```

> **REV-2026-10**：`PAID` 加入通用枚举，仅 `PayrollSheet` 使用。
> 新增值必须走 `ALTER TYPE ... ADD VALUE` 迁移，**禁止改动已有值**（见 [04-数据库规范.md](./04-数据库规范.md) §3）。
> 记账凭证**不使用** `DocumentStatus`，它有独立枚举：

```python
class VoucherStatus(StrEnum):
    DRAFT = "DRAFT"          # 已录入未过账，可改
    POSTED = "POSTED"        # 已过账，不可改（INV-5）
    REVERSED = "REVERSED"    # 已红冲
    CLOSED = "CLOSED"        # 所属会计期间已关账，彻底只读
```

凭证动作：`create` / `update`（仅 DRAFT）/ `post` / `reverse`（红冲）/ `void`（仅 DRAFT 作废）。
会计期间动作：`open` / `close` / `reopen`（`reopen` 仅 `super_admin`，必填原因，写日志）。

### 1.1 合法迁移图

```
        ┌──────────────── 提交 submit ────────────────┐
        │                                          ▼
    [DRAFT] ──── 提交 ────▶ [SUBMITTED] ──── 审核 ────▶ [APPROVED]  ◀─┐
        │                     │                        │             │
        │                     │ 驳回                    │ 反审核      │ 撤回
        │                     ▼                        ▼（必填原因）│
        │◀──── 可继续编辑 ─── [REJECTED] ◀─────────────┘             │
        │                     │                                      │
        └── 作废(仅草稿) ──▶ [CANCELLED] ◀── 作废（已审核需先反审核）─┘
                                    ▲
                            反审核也可直接作废
```

| 动作 | 起始 | 目标 | 权限点 | 附加要求 |
| --- | --- | --- | --- | --- |
| `create` | — | DRAFT | `<mod>:create` | 权限点校验 |
| `update` | DRAFT / REJECTED | DRAFT / REJECTED | `<mod>:update` | 仅字段级可改白名单 |
| `submit` | DRAFT / REJECTED | SUBMITTED | `<mod>:submit` | 业务校验全部通过 |
| `approve` | SUBMITTED | APPROVED | `<mod>:approve` | 制单人 ≠ 审核人；写日志 |
| `reject` | SUBMITTED | REJECTED | `<mod>:reject` | **必填原因**；写日志 |
| `withdraw` | SUBMITTED | DRAFT | `<mod>:update` | 撤回人 = 制单人 |
| `reverse` | APPROVED | SUBMITTED | `<mod>:reverse` | **必填原因**；下游校验；写日志；生成反向流水 |
| `cancel` | DRAFT / REJECTED | CANCELLED | `<mod>:cancel` | 必填原因；作废后终态 |

### 1.2 铁律

| # | 规则 |
| --- | --- |
| R1 | 状态迁移统一入口：`service.<entity>.<action>()`，方法内先校验 `self._assert_transition(from, to)` |
| R2 | 每次迁移必须写 `document_logs`（含 `from_status` / `to_status` / `reason` / `operator_id`） |
| R3 | 每次迁移用乐观锁：`WHERE id = ? AND version = ? AND status = ?`，`rowcount == 0` 报 `10003` |
| R4 | **审核 = 生效**：状态改为 APPROVED 的同一个事务里，必须完成所有下游副作用（库存增减、计件生效、凭证生成） |
| R5 | **反审核 = 全链路反向**：同事务内冲销所有下游副作用，生成反向台账/红冲流水，**不删原始记录** |
| R6 | 终态 `CANCELLED` 不可再迁移；如需重建，复制为新单据（新 `doc_no`） |
| R7 | 状态字段不出现在 Repository 方法签名里；禁止 `update(Doc).values(status=...)` 出现在 service 迁移方法之外 |

## 2. 单据类型迁移表

### 2.1 裁剪单 `CuttingOrder`

| 动作 | 迁移 | 业务校验（审核时执行） |
| --- | --- | --- |
| 提交 | DRAFT→SUBMITTED | 款号存在且启用且**已选商品分类**（ADR-0020）；明细非空；**每个尺码手数为正整数**（否则 `30006`）；耗料量 > 0；**所选布批可用库存足**（超出 → `40006`） |
| 审核 | SUBMITTED→APPROVED | **八步**（ADR-0017 三层结构；⚠️ REV-2026-10 下表是「八步」不是「七步」，见 [modules/02 §4.1](./modules/02-裁剪.md)）：① **按行（布批缸号+匹号）选批扣料** + 写 `stock_ledger_lines` ② 行 `waste_qty` 拆分：布头（可再裁）入库为布料批次，布损计入损耗 ③ **逐尺码明细 `output_qty = hands × qty_per_hand`**（`hands` 由用户直接输入的整数，**不取 floor**，ADR-0020 取消比例反算）**求和得 `Σ(颜色尺码出数)`** ④ **行耗料校验**：`fabric_qty ≥ Σ(颜色 Σ(尺码 output_qty × BOM.用量)) + waste_qty`，不足 → `30002` ⑤ **有效门幅校验**（所选批次 `width_cm` 是否满足铺布） ⑥ **行 `balance_qty = 行 output_qty − Σ(颜色出数)`，负数报错**（⚠️ **REV-2026-10 澄清**：行 `output_qty` 是**用户按铺布实耗正向录入**的估算值，不是第 ③ 步求和得来的 —— 见 [modules/02 §12 C34](./modules/02-裁剪.md)；早期版本这里写「求和得行 `output_qty`」，那会让 `balance_qty` 恒为 0、余量概念消失） ⑦ 写 `cutting_outputs` 结转（按行） ⑧ **裁片入在制品 WIP**：写 `wip_stocks` + `wip_ledger_lines(direction='IN')`（ADR-0018），尾数不入 WIP |
| 修改 | APPROVED 仍可改但**需重新审核**（回到 SUBMITTED），否则 `30005` | 按 §2.1.1 改单联动规则 |
| 反审核 | APPROVED→SUBMITTED | ① **任一码已计件（`counted_at IS NOT NULL`）→ 拒绝 `30004`**，必须先红冲反计件；② 已打菲未计件：未打印的码软删重建、已打印码置 `VOIDED`（`31007`）；③ 生成反向台账；④ 冲销 `cutting_outputs` 与 WIP `IN` 段 |

### 2.1.1 裁剪改单 → 打菲码联动（REV-2026-10，见 [ADR-0021](./adr/0021-裁剪改单与打菲联动.md)）

| 裁剪单状态 | 改耗料/布批/备注 | 改尺码手数 | 已有码 |
| --- | --- | --- | --- |
| DRAFT / SUBMITTED | 允许 | 允许 | 无影响 |
| APPROVED，未打菲 | 允许（需重新审核 `30005`） | 允许（需重新审核） | 无 |
| APPROVED，已打菲未扫码 | 允许（需重新审核） | 允许（需重新审核） | 未打印 → 软删重建；已打印 → `VOIDED` + `31007` 提示作废重打 |
| **任一码已计件** | **拒绝 `30004`** | **拒绝 `30004`** | 冻结 |

**唯一合法修正路径（红冲链）**：

```
piecework:reverse 红冲反计件（生成 REVERSAL 流水）
  → cutting:reverse 反审核裁剪单
  → 修改 hands / qty_per_hand
  → cutting:submit + cutting:approve 重新审核
  → 重新打菲（新单据号；旧打菲单 CANCELLED，码 VOIDED）
  → 员工重新扫码
```

每一步写 `document_logs`；`piecework_logs` 保持 append-only（[ADR-0005](./adr/0005-计件流水不可变与红冲机制.md) 不变）。

### 2.2 打菲单 `BundlingOrder`

| 动作 | 迁移 | 业务校验 |
| --- | --- | --- |
| 提交 | DRAFT→SUBMITTED | 款号+工序存在；`bundle_qty` > 0；所属裁剪单已审核 |
| 审核 | SUBMITTED→APPROVED | ① **按手生成 `bundle_no`（一码一手，手序号内嵌，ADR-0016）**；② 每手件数 = 裁剪明细该尺码的 **`qty_per_hand`（直接取，不由比例反算）**；码数 = 该尺码 `hands`（一码一手，ADR-0016）；③ **打菲手数不得超打裁剪手数**，否则 `31004`（少打允许；单尺码 >99 手 → `10001`，B21）；④ 手序号重复 → `31005`；⑤ `UNIQUE(doc_id, color_code, size_code, hands)` 兜底；⑥ 更新裁剪结转 |
| 反审核 | APPROVED→SUBMITTED | ① 已有计件流水存在 → **拒绝**（`32003` 口径），必须先冲销计件；② 已作废的码不可恢复 |
| 作废码 | 任意 | 单码作废写 `voided_at` + `void_reason`，必填原因 |

### 2.5 采购单（`PurchaseOrder`）+ 到货登记（`PurchaseArrival`）

> **REV-2026-10 / ADR-0015**：采购**审核只确认订单，不入库**；**入库的唯一入口是「到货登记」**（支持分批到货）。
> **不再有独立的「采购入库单」**（`RC` 单号已取消，见 [ADR-0012](./adr/0012-采购原材料批次字段.md) 与 [09 §2.1](./09-领域术语与编码规则.md)）。
> 单据归属**采购模块**（权限 `purchase:*`），库存模块只提供批次与台账能力。

| 动作 | 迁移 | 业务校验（审核时执行） |
| --- | --- | --- |
| 提交 | DRAFT→SUBMITTED | 供应商启用；行 `material_id/color_code/dye_lot_no/bolt_count/weight_kg/width_cm` 齐全；`purpose=REWORK_RECEIPT` 时 `rework_note` 必填（`10006`）；重量与米数差异 > 5% 只**警告**不阻断 |
| 审核 | SUBMITTED→APPROVED | **只确认订单，不入库**（ADR-0015）：① 汇总 `total_amount` ② 生成应付承诺（`ap_ledgers` 状态 `PENDING_ARRIVAL`）③ 勾了「一次到货」且到货日已到 → 自动生成第 1 次到货并走下面的入库流程 |
| **到货登记**（新，独立于状态机） | APPROVED | **入库唯一入口**（ADR-0015）：① 累计到货 ≤ 订单量（超 → `50011`）② 按**到货行**生成 `material_stocks` 批次（**到货行缸号可覆盖采购行** + 匹号 + 颜色 + 门幅 + 重量 + `purpose`），单位成本 = `(行金额 + 行分摊运费) ÷ 计重量`（ADR-0011）③ 写 `stock_ledgers.direction='IN'` + `stock_ledger_lines` ④ 按到货金额冲减应付 ⑤ 生成入库凭证（`NORMAL`→`1405`、`REWORK_RECEIPT`→`5403`、`RETURN`→冲减 `1406`、`SAMPLE`→`6602`）⑥ 累加 `arrival_count` / `arrived_amount` |
| 反审核（到货级） | APPROVED | ① 该批次已被下游裁剪消耗 → `40005` ② 按同一批 `stock_ledger_lines` 逐条反向冲回 ③ 红冲该次入库凭证 ④ 冲减该次应付 |
| 反审核（单据级） | APPROVED→SUBMITTED | **必须先冲完全部到货**；未冲完 → `50012` |

### 2.4 在制品 WIP 与成衣入库（REV-2026-10，见 [ADR-0018](./adr/0018-出入库链路与在制品WIP.md)）

WIP 与成衣入库**不走单据状态机**（无审核态），由触发动作驱动，但每次写入必须记 `document_logs`：

| 触发 | 动作 | 效果 |
| --- | --- | --- |
| 裁剪单审核通过 | `WIP_IN` | `wip_ledger_lines(direction='IN')`，裁片进入 WIP |
| **最后一道工序（= 整烫 / 烫衣服）**扫码计件完成（`style_operations.is_final_operation = true`） | `WIP_OUT + FG_IN` | 同一事务：WIP 出 + 成衣入库 + **一次性结转成本**（面料实际成本 + 全部已计工价）；数量不符 → `40007` |
| 手动完单入库（漏扫/返修补入库） | `WIP_OUT + FG_IN`（手动） | 需 `stock:in:manual` 权限 + **必填原因**（`10006`）+ 日志 |
| 返修报损 | `WIP_OUT` | 出 WIP 并计损耗，不入成衣 |

**最后一道工序 = 整烫（烫衣服）**（业务确认 2026-10-02）：默认按工序名含「整烫 / 烫衣」自动识别为最后工序；「工序与单价」页对它打醒目徽标；款号保存时校验**必须能识别到一道**，识别不到则标红提示人工指定（不允许留空）。工位机在整烫扫码时提示「本工序完成即成衣入库」。

**禁止**：裁剪完成直接把裁片当作成衣入库（会超卖且损耗无处体现）。

## 3. 状态机实现规范

### 3.1 迁移表声明式定义

```python
# app/modules/cutting/state.py
from app.common.enums import DocumentStatus
from app.core.errors import BusinessError, ErrorCode
from app.core.state_machine import Transition, StateMachine


CUTTING_TRANSITIONS: dict[DocumentStatus, list[Transition]] = {
    DocumentStatus.DRAFT: [
        Transition("submit", DocumentStatus.SUBMITTED),
        Transition("cancel", DocumentStatus.CANCELLED),
    ],
    DocumentStatus.REJECTED: [
        Transition("submit", DocumentStatus.SUBMITTED),
        Transition("cancel", DocumentStatus.CANCELLED),
    ],
    DocumentStatus.SUBMITTED: [
        Transition("approve", DocumentStatus.APPROVED),
        Transition("reject", DocumentStatus.REJECTED),
        Transition("withdraw", DocumentStatus.DRAFT),
    ],
    DocumentStatus.APPROVED: [
        Transition("reverse", DocumentStatus.SUBMITTED),
    ],
    DocumentStatus.CANCELLED: [],
}

CUTTING_SM = StateMachine(
    transitions=CUTTING_TRANSITIONS,
    actions_requiring_reason={"reject", "reverse", "cancel"},
    error_code=ErrorCode.INVALID_TRANSITION,  # 10007
)


def assert_transition(from_status: DocumentStatus, action: str) -> DocumentStatus:
    return CUTTING_SM.resolve(from_status, action)
```

### 3.2 Service 迁移方法模板

```python
# app/modules/cutting/service.py
class CuttingOrderService:

    async def approve(
        self,
        order_id: UUID,
        operator: AuthContext,
        *,
        expected_version: int,
        remark: str | None = None,
    ) -> CuttingOrder:
        """审核裁剪单。审核即生效：扣料 + 台账 + 结转 同事务完成。"""
        async with self.session.begin():
            order = await self._lock_for_update(order_id, expected_version)

            if operator.user_id == order.created_by:
                raise BusinessError(ErrorCode.SELF_APPROVE_FORBIDDEN, "不能审核自己创建的单据")  # 10005

            CUTTING_SM.assert_transition(order.status, "approve")   # 状态机校验

            # ── 下游副作用（必须与状态变更同一事务）──────────────────
            await StockService(self.session).issue_for_cutoff(order)
            await self._create_output_records(order)

            await self._apply_status(
                order,
                action="approve",
                to_status=DocumentStatus.APPROVED,
                operator=operator,
                expected_version=expected_version,
                remark=remark,
            )
        return order

    async def _apply_status(
        self,
        order: CuttingOrder,
        *,
        action: str,
        to_status: DocumentStatus,
        operator: AuthContext,
        expected_version: int,
        reason: str | None = None,
    ) -> None:
        """唯一允许写 status 的方法。乐观锁 + 审计日志 + 状态机三重保障。"""
        if action in CUTTING_SM.actions_requiring_reason and not (reason or "").strip():
            raise BusinessError(ErrorCode.REASON_REQUIRED, f"{action} 操作必须填写原因")

        stmt = (
            update(CuttingOrder)
            .where(
                CuttingOrder.id == order.id,
                CuttingOrder.version == expected_version,
                CuttingOrder.status == order.status,
            )
            .values(
                status=to_status,
                version=CuttingOrder.version + 1,
                updated_at=func.now(),
                updated_by=operator.user_id,
                approved_by=operator.user_id if to_status is DocumentStatus.APPROVED else order.approved_by,
                approved_at=func.now() if to_status is DocumentStatus.APPROVED else order.approved_at,
            )
        )
        result = await self.session.execute(stmt)
        if result.rowcount == 0:
            raise BusinessError(ErrorCode.OPTIMISTIC_LOCK_CONFLICT, "单据已被他人修改或状态已变化，请刷新")

        await AuditService(self.session).log_transition(
            doc_type="CuttingOrder",
            doc_id=order.id,
            doc_no=order.doc_no,
            action=action,
            from_status=order.status,
            to_status=to_status,
            operator=operator,
            reason=reason,
        )
        order.status = to_status
        order.version += 1
```

### 3.3 副作用清单（审核动作必须成对实现）

**审核与反审核的副作用必须严格对称**，漏一个反审核就会数据错。

| 单据 | 审核时做 | 反审核时反向做 |
| --- | --- | --- |
| 裁剪单 | 扣面料库存 + 耗料台账 + 结转记录 | 加回库存 + 反向台账 + 冲销结转 |
| 打菲单 | 生成 bundle_no + 更新裁剪结转 | 作废码 + 冲销结转 |
| 完工入库 | 加成衣库存 + 物料成本结转 | 减成衣库存 + 反向台账 |
| **到货登记** | 加库存（批次实际成本含运费）+ 门幅/重量/`purpose` + 批次明细 + 冲减应付 + 入库凭证 | 先按到货反审核：按同一批 `stock_ledger_lines` 逐条反向冲回；已下游消耗 → `40005`；未冲完不许反审核单据 → `50012` |
| 销售出库 | 减库存 + 生成应收 + 出库凭证 | 全量反向 |
| 计件结算 | 标记流水已结算 + 写 payroll_id | 清除 payroll_id |
| 工资审核 | 计提凭证 | 红冲计提凭证 |
| 工资发放 | 付款凭证 + 代发文件 | 已发放禁止，只走红冲 |
| 凭证过账 | 写总账 | 红字反向凭证 |

## 4. 审核权限与分工

| 原则 | 说明 |
| --- | --- |
| 不自审 | `created_by == operator.user_id` → 拒绝（错误码 `10005`，见 [05-接口设计规范.md](./05-接口设计规范.md) §4）。例外：`super_admin` 需显式传 `force=true` 且写日志 |
| 分级审核 | 金额超过阈值需 `factory_manager` 终审（阶段二，先只留数据字段 `need_final_approval`） |
| 审核留痕 | 日志必须含操作人、IP、时间、原因 |
| 批量审核 | 逐单独立校验，不允许"全部通过"式放行（防误操作）；失败项单独列出 |

## 5. 测试要求（状态机必测项）

每个单据模块的状态机必须有：

| # | 用例 |
| --- | --- |
| 1 | 每条合法迁移成功，状态与日志正确 |
| 2 | 每条**非法**迁移被拒（`10003` 或对应错误码），状态不变 |
| 3 | 版本号不符时迁移失败（乐观锁生效） |
| 4 | `reject/reverse/cancel` 未填原因被拒 |
| 5 | 制单人自审被拒 |
| 6 | **审核后反审核，库存/流水/凭证完全还原**（用测试夹具对比快照） |
| 7 | 反审核两次被拒（幂等保护） |
| 8 | 作废后不可再迁移 |

**第 6 条是本项目的核心测试**，不允许只测状态不测副作用。
