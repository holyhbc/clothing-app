# 11 部署运维与发布规范

> 目标：**在 2C/12G 的 VPS 上稳定跑**，且任何一次发布都能在 5 分钟内回滚。
> AI 执行发布时必须逐条对照本文，**禁止执行任何删数据的命令**。

---

## 1. 环境

| 环境 | 用途 | 位置 | 数据库 |
| --- | --- | --- | --- |
| `local` | 开发 | 开发者机器（也可能是同一台 VPS） | `garment_erp_dev` |
| `test` | CI + 集成测试 | GitHub Actions 容器 / VPS 容器 | `garment_erp_test`（每次重建） |
| `prod` | 生产 | VPS 2C/12G | `garment_erp` |

**铁律**：
1. 三套环境**数据库物理隔离**，生产凭据不进任何测试环境。
2. **禁止**在生产 VPS 上同时跑 dev 与 test 数据库（内存不够，见 [01](./01-技术选型与架构.md) §3）。
3. 生产数据库账号权限最小化：应用账号**只有** `SELECT/INSERT/UPDATE`，**没有 DELETE 与 TRUNCATE**；`document_logs` 连 `UPDATE` 都没有。

## 2. 环境变量与密钥

```bash
# .env（不入 git，权限 600）
POSTGRES_USER=erp_app
POSTGRES_PASSWORD=<强密码>
POSTGRES_DB=garment_erp
DATABASE_URL=postgresql+asyncpg://erp_app:<密码>@postgres:5432/garment_erp
REDIS_URL=redis://redis:6379/0
JWT_SECRET=<openssl rand -hex 32>
JWT_EXPIRE_MINUTES=15
APP_ENV=production
SENTRY_DSN=            # 可空
SMS_ACCESS_KEY_ID=      # 短信登录，可空（阶段一用测试通道）
SMS_ACCESS_KEY_SECRET=
```

| 规则 | 说明 |
| --- | --- |
| 只进环境变量 | 禁止写进代码、镜像、`opencode.json` |
| `.env.example` 入 git | 所有键留空，值为占位 |
| 镜像里不烘焙密钥 | 用 `env_file` / `environment` 注入 |
| 泄露处理 | 立刻轮换 + 记 `docs/12` 变更记录 + 写 ADR 说明影响 |

## 3. 目录与 compose

```
/opt/garment-erp/
├── docker-compose.yml          # 生产编排（提交进 git）
├── docker-compose.override.yml # 本机端口映射（不进 git）
├── .env                        # 密钥（不进 git）
├── docker/
│   ├── backend/Dockerfile
│   ├── frontend/Dockerfile
│   ├── nginx/nginx.conf
│   └── scripts/
│       ├── entrypoint.sh        # 等待 DB → alembic upgrade → 启动
│       ├── backup.sh            # pg_dump + 校验
│       ├── restore.sh
│       └── healthcheck.sh
├── deploy/
│   ├── backup-cron.sh
│   └── release.sh               # 发布脚本（幂等、可回滚）
└── backups/                     # 备份落盘（挂载独立磁盘更佳）
```

### 3.1 关键 compose 片段

```yaml
services:
  api:
    image: ${REGISTRY}/garment-erp-api:${APP_VERSION}
    restart: always
    env_file: [.env]
    environment:
      DATABASE_URL: ${DATABASE_URL}
    depends_on:
      postgres: { condition: service_healthy }
    command: ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]
    deploy:
      resources: { limits: { memory: 1536M } }
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8000/readyz"]
      interval: 30s
      timeout: 5s
      retries: 3

  postgres:
    image: postgres:16-alpine
    restart: always
    volumes: ["pgdata:/var/lib/postgresql/data", "./backups:/backups"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources: { limits: { memory: 3G } }
    command:
      - postgres
      - -c
      - shared_buffers=1GB
      - -c
      - work_mem=16MB
      - -c
      - max_connections=60
      - -c
      - timezone=Asia/Shanghai

volumes:
  pgdata:
```

**禁令**：
- ❌ 生产 compose 中不得出现 `build:`（生产只拉镜像，构建在 CI）
- ❌ 不得出现 `docker-compose down -v`（`-v` 会删卷 = 删数据）
- ❌ 不得把 `postgres` 端口 `5432` 暴露到 `0.0.0.0`

## 4. 镜像构建（必须在 CI）

**为什么不能在生产 VPS 上构建**：`pnpm build` + vite 打包会瞬时吃 2-3G 内存，2C VPS 会 OOM 且拖慢线上。

```yaml
# .github/workflows/release.yml（骨架）
on:
  push: { tags: ["v*"] }

jobs:
  test-build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 闸门 1-3 测试
        run: docker compose -f docker-compose.ci.yml run --rm test
      - name: 闸门 4 迁移往返验证
        run: docker compose -f docker-compose.ci.yml run --rm migrate-check
      - name: 闸门 5 构建镜像
        run: |
          docker buildx build --platform linux/amd64 -f docker/backend/Dockerfile \
            -t registry.example.com/garment-erp-api:${{ github.ref_name }} --push .
          docker buildx build --platform linux/amd64 -f docker/frontend/Dockerfile \
            -t registry.example.com/garment-erp-web:${{ github.ref_name }} --push .
      - name: 部署到 VPS
        run: ssh deploy@$VPS "cd /opt/garment-erp && APP_VERSION=${{ github.ref_name }} ./deploy/release.sh"
```

**镜像要求**：
| 项 | 要求 |
| --- | --- |
| 基础镜像 | `python:3.12-slim` / `node:22-alpine`（前端只用于 build，最终用 `nginx:alpine`） |
| 多阶段 | build 阶段依赖不进最终镜像 |
| 非 root | `USER app` |
| 多架构 | 必须 `linux/amd64`（VPS 是 x86） |
| 层缓存 | 依赖层先于源码层 |
| 镜像 tag | 用 git tag（`v1.2.0`），**禁止 `latest`**（无法回滚） |
| 摘要留存 | 记录 image digest 到发布单 |

## 5. 发布流程（AI 执行 `/release` 时逐条走）

```
[1] 确认发布单          发布单已生成且用户明确批准
[2] 记录当前版本         APP_VERSION=<当前 tag>，写进发布单（回滚要用）
[3] 备份 + 校验         ./docker/scripts/backup.sh → 必须看到 "OK <文件名> <size>"
[4] 演练迁移             在生产数据副本上跑 upgrade → 验证 → downgrade → 再 upgrade
[5] 拉取新镜像           docker compose pull
[6] 执行迁移             docker compose run --rm api alembic upgrade head
[7] 滚动重启             docker compose up -d --no-deps api   （先 api，后 web）
[8] 健康检查             curl /readyz 连续 3 次成功；再看 /api/v1/healthz
[9] 冒烟验证             见 §6 清单（必须人工确认关键 3 项）
[10] 归档               发布单完成 + docs/12 变更记录 + 保留新旧镜像 digest
```

**禁止**：
- ❌ 未备份就发布
- ❌ 迁移失败后强行启动服务（必须停在这里回滚）
- ❌ 在发布过程中改数据库里的业务数据（数据修正走单据或脚本 + ADR）

### 5.1 回滚

| 场景 | 回滚步骤 |
| --- | --- |
| 代码问题（迁移可逆） | `APP_VERSION=<旧 tag> docker compose up -d` + `alembic downgrade <目标版本>` |
| 迁移不可逆 | 从备份恢复：`停服 → 解压备份 → pg_restore → 启动旧镜像`；**数据丢失窗口 = 备份时点之后**，必须评估并告知用户 |
| 迁移报错 | **不要**继续 forward fix（会污染生产）；优先回滚到备份重放 |

回滚判据（满足任一即回滚）：
- `/readyz` 失败
- 计件接口 P95 > 500ms
- 库存对账视图非空
- 凭证借贷不平
- 冒烟验证任一项失败

## 6. 冒烟验证清单（每次发布后必做）

```bash
# 1. 服务存活
curl -fsS https://erp.example.com/api/v1/readyz

# 2. 登录可用（不记录密码到日志）
curl -fsS -X POST https://erp.example.com/api/v1/auth/login -d '{"employee_no":"TEST01","password":"***"}'

# 3. 数据库一致性（必须输出 0 行）
docker compose exec -T postgres psql -U erp_app -d garment_erp -c "
  SELECT * FROM v_stock_reconciliation;"
docker compose exec -T postgres psql -U erp_app -d garment_erp -c "
  SELECT * FROM v_voucher_balance;"

# 4. 迁移版本 = 期望版本
docker compose exec -T api alembic current

# 5. 迁移历史健康：本次 up → down → 再 up 是否成功
docker compose exec -T api alembic downgrade -1
docker compose exec -T api alembic upgrade head
docker compose exec -T api alembic current
```

**人工确认 3 项**（AI 提示用户操作，不代劳）：
1. 登录 PC 端 → 单据列表能打开 → 打开一条已审核单据详情（校验 token 与权限链路）
2. 员工端 H5 用手机打开 → 能看到今日计件数
3. 打开库存台账页 → 与手工核对一个批次数量一致

## 7. 备份与恢复

| 项 | 策略 |
| --- | --- |
| 全量 | 每日 03:00 `pg_dump -Fc`，保留 30 天 |
| 校验 | 备份脚本必须 `pg_restore -l` 校验，失败则报警 |
| WAL 归档 | 开启 `archive_mode=on`（阶段二），RPO 目标 1 小时 |
| 异地 | 每天同步一份到另一台机器/对象存储（阶段二） |
| 演练 | **每月一次**在干净容器里恢复成功才算合格 |

```bash
#!/usr/bin/env bash
# docker/scripts/backup.sh —— 幂等 + 校验
set -euo pipefail
TS=$(date +%Y%m%d_%H%M%S)
FILE="/backups/garment_erp_${TS}.dump"
docker compose exec -T postgres pg_dump -U "${POSTGRES_USER}" -d "${POSTGRES_DB}" -Fc > "$FILE"
test -s "$FILE" || { echo "BACKUP EMPTY"; exit 1; }
docker compose exec -T postgres pg_restore -l < "$FILE" > /dev/null || { echo "BACKUP CORRUPT"; exit 1; }
echo "OK ${FILE} $(du -h "$FILE" | cut -f1)"
find /backups -name 'garment_erp_*.dump' -mtime +30 -delete
```

恢复：
```bash
docker compose stop api web
docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c \
  "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='$POSTGRES_DB';"
gunzip -c backups/xxx.dump | docker compose exec -T postgres pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists
docker compose start api web
```

**备份失败的处置**：备份失败必须在当天处理，不得"明天再说"。连续 2 天失败视为线上事故。

## 8. 日常运维

| 频率 | 事项 |
| --- | --- |
| 每日 | 看磁盘用量（>80% 报警）、备份成功、`pg_stat_statements` TOP 慢查询、错误日志 |
| 每周 | 慢 SQL 分析（连续两周 TOP3 才优化）、`ANALYZE` 大表、`v_*` 对账视图 |
| 每月 | 恢复演练、账号与权限审计（离职员工停用）、`document_logs` 完整性检查 |
| 每季 | 依赖升级评估（AI 产出升级 PR，人工审） |

### 8.1 日志

| 项 | 规范 |
| --- | --- |
| 后端 | 结构化 JSON → stdout → docker logs → `json-file` driver，`max-size=50m,max-file=5` |
| 访问日志 | Nginx：`access.log` 轮转，保留 14 天 |
| 慢查询 | `log_min_duration_statement = 500`，单独文件 |
| 敏感信息 | 日志禁止打印密码、token、完整身份证/银行卡号（脱敏） |

### 8.2 告警（阶段二接 webhook/企业微信机器人）

| 阈值 | 动作 |
| --- | --- |
| 磁盘 > 80% | 告警 |
| 备份缺失 | 告警 |
| `/readyz` 连续失败 3 次 | 告警 + 记录 |
| `v_stock_reconciliation` 非空 | **严重告警**（数据不一致） |
| `v_voucher_balance` 非空 | **严重告警**（账不平） |
| 内存 > 90% | 告警 |

## 9. 环境搭建（首次）

```bash
# 1. 基础
apt update && apt install -y curl ca-certificates
curl -fsSL https://get.docker.com | sh
usermod -aG docker $USER && newgrp docker

# 2. 目录与克隆
mkdir -p /opt/garment-erp && cd /opt/garment-erp
git clone <repo> .

# 3. 环境变量
cp .env.example .env && vi .env     # 填密码与 JWT_SECRET，chmod 600

# 4. 首个版本
docker compose pull && docker compose up -d postgres redis
docker compose run --rm api alembic upgrade head
docker compose up -d

# 5. 初始化数据（角色/权限/科目/内置角色）
docker compose exec api python -m app.cli.seed_baseline

# 6. 验收
curl -fsS https://erp.example.com/api/v1/readyz
```

**端口**：只暴露 `80` / `443`（Nginx）。SSH 改非 22 端口 + 禁密码登录 + 只允许密钥。

## 10. AI 执行发布的红线

| # | 红线 |
| --- | --- |
| 1 | 禁止 `docker compose down -v` / `docker volume rm` / `dropdb` / `TRUNCATE` / `DELETE FROM`（无 WHERE） |
| 2 | 禁止在未确认发布单的情况下执行部署命令 |
| 3 | 禁止跳过备份直接发布 |
| 4 | 禁止把 `.env` 内容打印到会话输出 |
| 5 | 禁止自动 force-push 或改写已发布 tag |
| 6 | 迁移失败必须停下并报告，**禁止尝试手工改表"救活"** |
| 7 | 破坏性 DDL（`drop_table` / `drop_column`）必须先在 ADR 说明回滚方案，并二次确认 |
| 8 | 一切发布命令执行前，先向用户复述将要执行的命令并等确认 |
