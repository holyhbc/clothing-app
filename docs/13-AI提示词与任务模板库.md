# 13 AI 提示词与任务模板库

> 这里存放**可复用的提示词**。命令实现见 `.opencode/command/`，角色实现见 `.opencode/agent/`。
> **铁律：任何提示词开头都要写"先读哪些 docs"**，避免 AI 用通用知识猜业务规则。

---

## 1. 提示词通用骨架

```
【目标】        一句话，不超过 40 字
【先读规范】    精确到文件 + 章节（必填）
【范围】        要做什么 / 明确不做什么
【约束】        硬性要求（最多 8 条）
【产出】        文件清单 / 接口清单 / 测试清单
【验收】        可验证的标准
```

**反面示例**（会导致 AI 编造业务规则）：
> 帮我写个裁剪单的功能。

**正面示例**：
> 【目标】实现裁剪单的提交与审核（含扣料出库）
> 【先读规范】AGENTS.md §1、docs/04-数据库规范.md §7、docs/08-单据状态机规范.md §2.1、docs/modules/02-裁剪.md
> 【范围】只做 cutting_orders 的 submit/approve/reject + 审核时的库存扣减与 cutting_outputs 结转；不做打菲、不做报表
> 【约束】1) 事务边界只在 service 2) 状态机走 CUTTING_SM 3) 审核副作用与反审核成对 4) 库存不足返回 40001 5) 写 document_logs
> 【产出】迁移 + service + router + 测试 + 更新 modules/02 §5
> 【验收】闸门 1-5 全绿；审核→反审核库存完全还原；权限矩阵 5 条通过

## 2. 阶段提示词

### 2.1 `/clarify` 需求澄清

```
你在 /root/opencode。先读 AGENTS.md、docs/00-项目概述与业务蓝图.md、docs/09-领域术语与编码规则.md。

用户需求：{{用户原话}}

请：
1. 把需求翻译成领域术语（对照 09 §1），指出用户用了哪些不规范的说法
2. 列出：用户角色 / 场景 / 输入 / 输出 / 业务规则 / 明确的非目标
3. 逐条列出**缺失的信息**与**你不能自行决定的业务规则**，以问题形式给出
4. 判断哪些问题阻塞设计（标 🔴）、哪些可以先假设（标 🟡，并写明假设）

输出需求卡草稿（docs/templates/需求卡模板.md 格式）到 docs/requirements/。
不要写代码。业务规则不允许你发明。
```

### 2.2 `/design` 设计

```
你在 /root/opencode。先读 AGENTS.md §1-§2、docs/02-AI开发流水线规范.md §2.2、
docs/templates/设计文档模板.md、以及本任务涉及的 docs/modules/*.md。

需求卡：{{路径}}

请：
1. 按设计文档模板产出设计稿，逐节填写；不适用的写"不适用（理由）"
2. 列出**将要改动的文件清单**（新建/修改，各一句话说明）
3. 领域模型必须给出字段名与约束；单据必须给出状态迁移表 + 审核/反审核的成对副作用
4. 识别是否需要新 ADR（触发条件见 docs/12 §3.1）
5. 待决问题进 §10，标出哪些阻塞编码

停下来等用户确认"设计通过"再继续。禁止直接写代码。
```

### 2.3 `/plan` 拆任务

```
你在 /root/opencode。先读 AGENTS.md §6、docs/02-AI开发流水线规范.md §2.3、docs/templates/任务卡模板.md。

设计稿：{{路径}}

请把设计拆成任务卡：
1. 每个任务 ≤ 1 天、≤ 8 个文件、有可自动化验证的验收标准
2. 顺序：迁移 → 模型/Schema → Repository → Service → Router → 前端 shared → 前端页面 → 测试
3. 标出依赖关系（depends_on）与可并行的任务
4. 每个任务列出"将改动的文件"
5. 明确哪些任务受待决问题阻塞（blocked）

输出到 docs/tasks/，并给出总工期估算与里程碑建议。
```

### 2.4 `/implement` 编码

```
你在 /root/opencode。先读 AGENTS.md §1-§2、docs/03-代码规范.md、docs/04-数据库规范.md、
docs/05-接口设计规范.md、docs/08-单据状态机规范.md、docs/10-测试规范.md、
以及任务卡指定的 docs/modules/*.md。

任务卡：{{路径}}

按任务卡执行，顺序固定：迁移 → 模型 → Schema → Repository → Service → Router → 前端 → 测试。
硬性要求：
- 先复述"将要改动的文件清单"，与任务卡不一致时先说明原因
- 每个状态迁移必须走状态机 + 乐观锁 + document_logs
- 新接口必须有权限声明、错误码（取自 05 §4）、OpenAPI tags/summary
- 新表必须含 id/审计字段/deleted_at/version/remark
- 写测试，先让它失败再让它通过（给出失败输出）
- 不改测试断言来迁就实现

完成后输出：改动文件清单、测试报告格式（见 docs/10 §9）、闸门执行结果。
```

### 2.5 `/test` 测试

```
你在 /root/opencode。先读 docs/10-测试规范.md、docs/modules/<模块>.md §11、AGENTS.md §9。

范围：{{任务卡或模块}}

请：
1. 跑闸门 1-3，输出逐条结果
2. 核对模块文档 §11 测试清单，标出哪些用例缺失并补齐
3. 强制覆盖：权限矩阵 5 条 + 状态机 8 条 + 并发 4 类（计件/库存/结算/凭证）
4. 核对"审核→反审核 数据完全还原"用例存在且通过
5. 输出测试报告（docs/10 §9 格式），含覆盖率与遗留问题
```

### 2.6 `/archive` 归档

```
你在 /root/opencode。先读 AGENTS.md §7-§9、docs/12-文档与变更归档规范.md。

本次改动：{{git diff --stat}}

请：
1. 在 docs/12 §2 变更记录表追加一行（类型/范围/摘要/影响/ADR）
2. 把任务卡置 done，回填实际改动文件与提交信息
3. 检查受影响的 docs/modules/*.md 是否与代码一致（字段/接口/状态机）
4. 新发现的无关问题登记到 docs/12 §5 遗留问题清单
5. 给出 Conventional Commits 提交信息（含 Refs: docs/modules/xxx.md §n）
6. 对照 AGENTS.md §9 自检清单逐条确认后输出结果
```

### 2.7 `/release` 发布

```
你在 /root/opencode。先读 AGENTS.md §2.1、docs/02 §2.7、docs/11-部署运维与发布规范.md。

版本：{{tag}}   变更集：{{commit range}}

按 docs/11 §5 逐条执行，但**在执行任何 docker/数据库命令前，先把命令完整列出给用户确认**。

硬性顺序：记录当前版本 → 备份并确认输出含 "OK" → 生产副本演练迁移 → 拉镜像 →
alembic upgrade → 滚动重启 → 健康检查 → docs/11 §6 冒烟（对账视图必须 0 行）→ 归档发布单。

红线（docs/11 §10）：禁止 down -v / dropdb / TRUNCATE / 无 WHERE 的 DELETE / 打印 .env / 跳过备份。
任何一步失败立即停止并报告，给出回滚方案，不要自行继续。
```

## 3. 专项提示词

### 3.1 新增单据类型

```
你在 /root/opencode。先读 AGENTS.md、docs/08-单据状态机规范.md、docs/04-数据库规范.md §7.3、
docs/05-接口设计规范.md、docs/modules/ 中最相似的一个单据模块。

需求：新增单据 {{名称}}，业务场景 {{场景}}

请按 docs/08 §1 的通用迁移表设计该单据的状态机，并：
1. 明确"审核即生效"的全部下游副作用
2. 明确每个副作用在"反审核"时的**成对反向操作**（漏一个就数据错）
3. 给出在 07 §2.2 需要新增的权限点清单（不能发明表外权限点）
4. 给出在 05 §4 需要新增的错误码清单（不能发明表外错误码）
5. 给出在 09 §2.1 需要登记的单据号前缀（必须不重复）
先输出设计，不写代码。
```

### 3.2 新增接口

```
你在 /root/opencode。先读 AGENTS.md、docs/05-接口设计规范.md、docs/07-认证与权限规范.md §3、docs/03-代码规范.md §1。

接口：{{方法 + 路径}}，用途 {{用途}}

请给出：
1. 请求/响应 Schema（Pydantic，`extra=forbid`，每个字段带 description 与 examples）
2. 权限点（取自 07 §2.2）与数据范围声明方式
3. 错误码（取自 05 §4）；需要新码时写进"建议新增错误码"清单而不是直接用
4. 幂等要求（写接口是否需要 Idempotency-Key，幂等键怎么推导）
5. service 层方法签名 + 数据范围过滤代码骨架（apply_data_scope 必须在第一行）
6. 5 条权限矩阵测试用例
输出设计，不写代码。
```

### 3.3 排查线上问题

```
你在 /root/opencode。现象：{{现象}}，发生时间 {{时间}}，影响 {{范围}}

排查步骤：
1. 先判断是"数据问题"还是"代码问题"（查 document_logs 与 docker logs 时间线）
2. 若是数据不一致，先跑对账视图：
   SELECT * FROM v_stock_reconciliation;      -- 必须 0 行
   SELECT * FROM v_voucher_balance;           -- 必须 0 行
3. 定位到具体单据：列出 doc_no、status、version、updated_by、updated_at
4. 判断能否用业务动作修复（反审核/红冲/盘点），**优先用业务动作，不要直接改表**
5. 输出：根因、影响范围、修复方案（业务动作优先）、是否需要补 ADR 或补测试
禁止直接执行 UPDATE/DELETE 修数据。
```

### 3.4 规范冲突发现

```
你在 /root/opencode。你发现规范之间存在冲突：{{冲突描述}}，涉及 {{文件章节}}

请：
1. 逐条列出冲突点（引用的两处原文）
2. 判断哪个是权威（按 docs/12 §1.1 优先级）
3. 给出**最小修改方案**（改哪篇哪一节，改成什么）
4. 列出受影响的文件（代码、模块文档、迁移脚本、前端常量）
5. 判断是否需要 ADR
输出修改方案，等确认后再改文档。禁止默默改代码。
```

### 3.5 权限变更

```
你在 /root/opencode。先读 AGENTS.md §2.2、docs/07-认证与权限规范.md §2.2/§6。

需求：{{给某角色加/减某权限}}

按 docs/07 §6 的 6 步流程执行，并额外确认：
- 该权限点已在 07 §2.2 表格中登记（没有就先补登记，不要发明）
- 权限变更会写 document_logs（doc_type='Role'）
- 涉及成本可见性（stock:cost:view）或工资（payroll:*）时要提示保密影响
- 给出至少 3 条回归测试：授权后可访问 / 撤权后 403 / 越权按 ID 直查 403
```

## 4. 反面清单（AI 不要这样）

| 反面 | 后果 | 正确 |
| --- | --- | --- |
| "参考主流做法实现审批" | 编造业务规则 | 问用户，或引用已有单据的状态机 |
| "把默认单价设为 0.5" | 硬编码业务常量 | 走基础资料表，代码里查 |
| "直接 UPDATE 库存修正" | 破坏台账对账 | 盘点单 / 红冲单据 |
| "为了测试通过改断言" | 掩盖缺陷 | 改实现 |
| "跳过 coverage 阈值" | 质量下滑 | 补测试 |
| "顺手重构一下 service" | 超出任务范围，超 800 行 | 登记遗留问题 |
| "生成一个测试用 `await asyncio.sleep`" | 并发测试测不出真问题 | `asyncio.gather` 独立 session |
| "DELETE FROM piecework_logs WHERE id = ..." | 工资数据不可恢复 | 软删或红冲 |
| "新增一个状态 `PARTIAL_APPROVED`" | 未登记枚举，破坏契约 | 先改 08 §1.1 + 迁移 |
| "接口忘了加权限依赖" | 越权 | 每个接口必须 `require_permission` |

## 5. 提示词维护

| 规则 | 说明 |
| --- | --- |
| 模板必须带「先读规范」 | 无规范约束的提示词不许入库 |
| 与 `AGENTS.md` 同步 | 规范变更时同步更新模板 |
| 有效提示词库 | 实践中被反复使用且有效的才进本文；一次性提示词不入库 |
| 记录来源 | 新增模板注明来自哪个真实任务（便于评估效果） |
