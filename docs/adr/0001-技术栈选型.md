## 背景

系统要覆盖裁剪 → 打菲 → 缝制计件 → 工资结算 → 库存 → 销售 → 应收应付 → 凭证全链路，报表密集、并发写入集中在一个环节（扫码计件），且交付环境只有 **1 台 VPS 2C/12G**。

- 现状：项目零代码，`docs/` 已定规范 13 篇 + 9 个模块设计。技术栈只在 `01` §1 列了一版选型表，未落 ADR。
- 痛点/风险：
  1. 选型一旦落地再换，等于全部重写，代价接近重做项目。
  2. 报表与 Excel 导出（裁剪损耗表、计件汇总、毛利分析）工作量占比预估 > 30%，需要生态支撑。
  3. **AI 产出率**：本项目由 AI 写绝大部分代码，框架的"隐式行为"越少越好，类型推断越强越好。
  4. 双栈（后端 Python + 前端 TS）本身就有类型漂移风险，跨栈类型必须自动同步。
  5. 2C/12G 上前端构建瞬时吃 2-3G 内存，不能在生产机构建。
- 硬约束：单机 2C/12G；无专职运维；PostgreSQL 已在 ADR-0002 论证；员工端必须是 H5（无资质，见 ADR-0003）。

---

## 决策

**我们决定：后端用 Python 3.12 + FastAPI + SQLAlchemy 2.0 async + Alembic，前端用 Vue 3 + TypeScript strict + Vite + Pinia（PC 端 Ant Design Vue 5、员工端 Vant 4），存储用 PostgreSQL 16 + Redis 7，API 以 uvicorn 2 worker 运行。**

```text
backend:  Python 3.12 / FastAPI 0.115+ / SQLAlchemy 2.0 (Mapped[] / mapped_column)
          / Alembic / asyncpg / pydantic v2 / uvicorn --workers 2
          / ruff (lint+format) + mypy strict
frontend: Vue 3.5 + TS 5.6 + Vite 6 + Pinia 3 + Vue Router 4
          packages/admin = Ant Design Vue 5
          packages/mobile = Vant 4
infra:    PostgreSQL 16 + Redis 7 (shared_buffers=1GB, maxmemory=256mb, allkeys-lru)
          pnpm（前端） / uv（后端依赖）
```

生产内存分配（1 台 2C/12G，见 ADR-0006）：

| 服务 | 内存上限 | 说明 |
| --- | --- | --- |
| `nginx` | 256M | 反代 + gzip + 静态缓存 |
| `api`（uvicorn 2 worker） | 1.5G | 单 worker RSS 约 350-500M |
| `worker`（1 实例） | 800M | 报表导出、条码批量生成 |
| `postgres` | 3G | `max_connections=60` |
| `redis` | 384M | `allkeys-lru` |
| **合计** | **≈6G** | 留 ≈5G 给系统与构建峰值（构建在 CI，不在生产） |

跨栈类型同步（唯一允许的人工步骤收口点）：

```bash
# 后端导出 openapi.json → 前端生成类型，闸门 1 校验 diff 为空
uv run python -m app.tools.export_openapi > openapi.json
pnpm --filter @erp/shared generate:api    # openapi-typescript + 手写 api/ 封装
```

## 理由

| # | 理由 |
| --- | --- |
| 1 | Python 处理 pandas / openpyxl 生态直接对上 30%+ 工作量的报表需求，Node 在 Excel/统计上要绕道。 |
| 2 | FastAPI 的 Pydantic v2 既做参数校验又产出 OpenAPI，等于接口契约自动生成，AI 不用手写类型。 |
| 3 | SQLAlchemy 2.0 `Mapped[]` + mypy strict 提供编译期类型检查，复杂统计可退 Core 写原生 SQL（工资汇总窗口函数）。 |
| 4 | Vue `<script setup>` + TS strict 单文件结构，AI 生成可预测；Ant Design Vue 的 Table/Form/Tree/Transfer/Steps 覆盖单据型 ERP，零自研。 |
| 5 | Vite 构建产物小、启动快，`pnpm build` 放在 CI，规避生产 OOM。 |
| 6 | 2 worker 匹配 2 核；连接池 `pool_size=10, max_overflow=10` × 2 = 40，`max_connections=60` 留 20 给备份。 |
| 7 | 双栈是明确的代价，靠 openapi 生成 + `packages/shared` 收口，而不是靠人工约定。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| Java + Spring Boot | ✅ | 报表/Excel 生态不如 Python；JVM 常驻内存 512M-1G 起，2C12G 上与 PostgreSQL 3G 上限叠加后余量太薄；样板代码与注解多，AI 产出噪声大（Getter/Setter/构造器）。 |
| Node + NestJS | ✅ | 与 Python 报表优势失掉；金额用 JS number 需 decimal.js 兜；本项目报表重，收益为负。 |
| React + Ant Design | ✅ | 与 Vue 等价，但 Ant Design Vue 在 Transfer/Tree-select 等单据场景的 API 更贴合；团队与 AI 在 SFC 上产出更稳。 |
| Django + DRF | ✅ | admin 后台是负担（本项目要精细化权限，不是白送后台）；ORM 隐式行为多，AI 易产出不可预期代码；同步 ORM 阻塞 asyncpg 路线。 |
| Flask | ✅ | 无 Pydantic/OpenAPI 自动契约，需另搭，AI 容易写出无校验的裸接口。 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 报表开发效率最高；契约自动生成；类型安全覆盖前后端；与 ADR-0002/0006 的结论自洽。 |
| 负面/代价 | 双栈，跨栈类型需生成；Python GIL 下 2 worker 对 CPU 密集报表是上限（重报表走 `worker`）。 |
| 风险 | 依赖版本漂移（FastAPI/pydantic 大版本）；pnpm 与 uv 混用导致新人上手成本；`any` 逃逸导致 mypy 形同虚设。 |
| 迁移路径 | 无存量代码，无需迁移。若未来换栈，必须新写 ADR 并按 §4.3 双端同时替换。 |
| 回滚方式 | 规范层面回滚：改 ADR 状态为 `Superseded`，重写 `01` §1/§2。代码层回滚靠 git revert，未上线前无数据影响。 |
| 对规范的影响 | `01` §1/§2/§3/§4、`03`（ruff/mypy 命令）、`10`（pytest/Vitest/Playwright）、`11`（镜像构建在 CI）。不新增权限点或错误码。 |
| 对测试的影响 | 后端 `pytest` + `pytest-asyncio` + `httpx`；前端 `Vitest` + `Playwright`；原生 SQL 报表必须写 SQL 单元测试（`01` §5.3）。 |

| 指标 | 目标值 | 观测方式 |
