## 背景

员工端要给车工、查勘用，核心场景只有三件事：扫码绑定工序、看自己今天做了多少、看当期工资。当前工厂**没有企业主体资质**。

- 现状：`users.phone` 已有 UNIQUE 约束（`07` §2.1），`employee_external_identities` 表结构已建但无数据。
- 痛点/风险：
  1. 员工普遍不记密码、不装 App、不愿输账号密码 → 必须免密码。
  2. 员工端不能暴露管理端接口，否则车工能看全厂工资与成本（07 §5 工资保密是硬要求）。
  3. 手机被互相借用 → 员工看到的是别人的工资，需要设备绑定。
  4. 未来若切微信/企业微信，如果登录逻辑写在 service 里，切换成本会波及全部员工端接口。
- 硬约束（资质与费用，关键事实）：
  - 企业微信自建应用 / 公众号网页授权 / 微信小程序：**必须企业主体认证**。企业主体 300 元/年；个体工商户优惠期 30 元/年；**个人主体不支持认证**（也就无法开通微信支付等能力）。
  - 小程序除认证外还需**备案**（主体+人脸核验），周期以周计。
  - 结论：阶段一走 H5 短信登录，**零资质、零合规成本**，拿到认证后再换 Provider。

---

## 决策

**我们决定：阶段一员工端用手机号 + 短信验证码（H5），认证能力抽象为 `AuthProvider` Protocol，当前唯一实现是 `SmsAuthProvider`；员工端 token 只能访问 `/api/v1/self/**`。**

```python
# app/modules/auth/providers/base.py（已定，07 §1.3）
class AuthProvider(Protocol):
    name: str
    async def verify_code(self, code: str) -> ExternalIdentity: ...
    async def get_user_by_external(self, identity: ExternalIdentity) -> "Employee | None": ...

PROVIDERS: dict[str, AuthProvider] = {
    "sms": SmsAuthProvider(),          # 阶段一，唯一实现
    # "wecom": WeComAuthProvider(),      # 认证通过后新增，service 零改动
    # "wechat_mini": WeChatMiniAuthProvider(),
}
```

```text
阶段一差异（07 §1.1 vs §1.2）：
  PC 端    : account + argon2id 密码 → access token 15 分钟 + refresh 7 天 HttpOnly Cookie
  员工端   : phone + 短信验证码     → access token 2 小时  + refresh 30 天
  权限集   : PC 端查 role_permissions；员工端恒为固定 self:* 四点
  数据范围 : 恒为 SELF，不可由前端传参放大（00 §3 误区表）
```

自助权限点（代码内建 `AuthContext`，**不进 `permissions` 表、不进角色表**）：

```text
self:profile:read   self:piecework:read   self:piecework:bind   self:payroll:read
# 明确不存在 self:piecework:count（REV-2026-10）：员工端不开放计件写入
```

设备绑定：首次登录生成 `device_id` 存 localStorage，服务端记录；同账号新设备登录可配置为拒绝或通知（`07` §1.2）。

## 理由

| # | 理由 |
| --- | --- |
| 1 | 零资质零成本：企业认证 300 元/年、个人主体不可认证、小程序还要备案，H5 无任何前置条件，可当天上线。 |
| 2 | 免密码符合车工实际使用习惯（不设密码 → 不存在员工间相互盗号看工资的问题）。 |
| 3 | `AuthProvider` 抽象把"如何证明你是你"与"登录后能干什么"彻底分离，未来切微信只新增一个类 + 一条映射表记录，service 与接口零改动。 |
| 4 | 接口前缀 `/api/v1/self/**` 是比"权限点判断"更硬的边界：即使权限配置被误改，员工端也访问不到管理端路由。 |
| 5 | token 有效期 2 小时是权衡结果：PC 15 分钟对车工频繁扫码太短，2 小时足够覆盖一个班次且离职/换岗后失效可控。 |
| 6 | 员工端不开放 `self:piecework:count`，计件写入只走工位机扫码枪（带 `piecework:count` 权限），避免员工手机批量刷数。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 微信小程序原生 | ✅ | 需企业主体认证（300 元/年，个体工商户 30 元/年，个人主体不可认证）+ 小程序备案 + 微信审核；工位机扫码枪场景小程序完全用不上；多一套构建与审核链路。 |
| 企业微信自建应用 | ✅ | 同为企业主体认证依赖；车工手机未必装企业微信；审批/组织架构同步对本项目不是刚需（车间/组别已在基础资料里维护）。 |
| 员工自设密码 | ✅ | 车工记不住密码，密码遗忘要走主管重置，是现场投诉源；也失去"设备即身份"的对账价值。 |
| 纯前端页面密码 | ✅ | 可绕过、无法审计"谁在什么时候看了自己工资"，违反 07 §5。 |
| 不做员工端 | ✅ | 直接导致"员工不知道自己做了多少、多少钱"这一首条痛点无解，月底算工资扯皮依旧。 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 当天可上线；无资质门槛；未来换 Provider 成本≈1 个类 + 1 张映射表记录。 |
| 负面/代价 | 依赖第三方短信通道（`Notifier` 接口已预留），有按条费用与到达率风险；2 小时 token 意味着手机丢失后风险窗口更长。 |
| 风险 | 员工手机被他人使用看到工资 → 靠 `device_id` 绑定 + 主管数据范围复核；短信接口被刷（费用攻击）→ 需限流（按 `phone` 60 秒 1 次、IP 日限）。 |
| 迁移路径 | 拿到企业认证后：① 注册小程序/企微应用；② 实现 `WeComAuthProvider` 或 `WeChatMiniAuthProvider`；③ 写映射数据把现有 `users.phone` 关联到 `external_id`；④ 前端加一个入口。**业务代码与表结构零改动。** |
| 回滚方式 | 移除 Provider 注册项，回退到 `sms`；已绑定的 `employee_external_identities` 行软删，不影响 `users`。 |
| 对规范的影响 | 确认 `07` §1.2/§1.3；`00` §5.3 可插拔点表。**不新增权限点**（`self:*` 内建，不进 07 §2.2 表）。 |
| 对测试的影响 | 必测：员工 token 访问 `/api/v1/piecework-logs` 必须 403；`self:*` 四点外的接口一律 403；设备换绑策略两种配置各测一遍；限流触发返回正确错误码。 |

## 未来替换方式（不做什么）

- **不做**原生小程序 App / 原生 iOS / Android App：工位机用扫码枪（HID，见 ADR-0004），员工用 H5 已覆盖，无离线复杂计算需求。
- **不做**多 Provider 并存登录（不做"选择登录方式"页）：避免员工混淆，Provider 由部署配置 `AUTH_PROVIDER` 单选。
- **不做**把 `self:*` 提进 `permissions` 表：它们是常量集合，进表会被误授予角色，反而扩大攻击面。

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 员工端首屏 | < 2s | 真机 4G 实测 10 次 |
| 短信验证码到达率 | > 98% | `auth_login_logs` 成功率统计 |
| 越权尝试（员工 token 打管理端接口） | 100% 403 | 安全测试用例全绿 |
| 单账号并发设备数 | ≤ 1（按配置） | `auth_login_logs` 统计 |
| 换 Provider 改动行数 | ≤ 1 个新文件 + 1 条配置 | 阶段二实施时按此验收 |
