## 背景

打菲完成的每一件（或每一扎）成衣要贴一个码，之后缝制计件、查勘、返工、完工入库、销售发货全链路都靠扫码识别。识别场景有三类：工位机扫码枪、员工手机扫一扫、管理员手机扫一扫查进度。

- 现状：`bundle_no` 格式已定 `{打菲单号}-{7 位序号}`，例 `BD-20260815-000045-0000123`；`bundling:code:void` 权限点已登记。
- 痛点/风险：
  1. 码内容若带业务字段（款号、色、码、重量），改色返工要重打标签，且容易出现"标签与实物不符"。
  2. 扫错码要能被识破：内容必须能唯一对应数据库一行，且不能被猜。
  3. 员工手机在弱光/油污车间环境下扫普通二维码，识别率不够就要有第二载体。
  4. 工位机是**扫码枪不是摄像头**——很多人默认"扫码 = 手机摄像头"，这是个高频误解。
  5. 2000 件一批打印，逐条 INSERT 会打满 2C 机器的连接与事务开销。
- 硬约束：单机 2C/12G；标签机为普通热敏/不干胶打印机，无专用驱动；旧码必须可作废追溯（INV-1 + `voided_at`）。

---

## 决策

**我们决定：二维码内容 = `bundle_no` 纯文本（纠错等级 M，尺寸 ≥ 20mm），同一内容另编码为 Code 128 供扫码枪；一衣一码，返工/换色必须新建码，旧码写 `voided_at` 作废。**

```text
标签规格：40mm × 40mm 不干胶，字段布局
┌──────────────────────────┐
│ ST-2026-0001  黑色  XL   │   ← 款号 / 色 / 码，供人工核对
│ 工序：车面                │
│  ┌────────┐              │
│  │ QR 20mm+│  ← 纠错 M   │
│  └────────┘              │
│ |||||||||||||||||||||||   │   ← Code 128，与 QR 同内容
│ BD-20260815-000045-0000123│   ← 纯文本可读
└──────────────────────────┘
```

扫码枪输入约定（工位机，**这是本决策最关键的技术事实**）：

```text
扫码枪 = USB 键盘 HID 设备
  → 扫到码后以 keydown 事件逐字符吐出 ASCII
  → 末尾自动发送 Enter
  → 前端必须全局捕获（keydown 累积字符 + Enter 触发提交）
  → 不依赖焦点在哪个输入框；工位机页面不申请摄像头权限
```

```python
# 工位机计件提交：幂等键 = bundle_no + station + operation + 时间片
idempotency_key = f"{bundle_no}:{source_station}:{operation_no}:{slot_30s}"
# 重复提交返回上次结果，不报错（09 §2.4 / 07 §7）
```

批量生成必须批量写：

```sql
INSERT INTO bundle_codes (bundle_no, style_no, color_name, size_name,
                           qr_payload, barcode_payload, voided_at)
SELECT ... FROM unnest(:rows) AS t(...) ON CONFLICT (bundle_no) DO NOTHING;
-- 2000 件一次事务，禁止循环单条 INSERT
```

作废：`voided_at = now()` + `void_reason` + 写 `document_logs`（谁、何时、为什么）→ 复用权限点 `bundling:code:void`。

## 理由

| # | 理由 |
| --- | --- |
| 1 | 内容只有 `bundle_no` 一个字段，标签与实物的一致性由数据库唯一索引保证，不依赖打印正确性。 |
| 2 | 纯文本可被任意扫码 App 读取（含微信扫一扫），不锁死在自家体系。 |
| 3 | Code 128 承载同一内容，扫码枪一次读出即可入参，避免"扫二维码得再复制粘贴"的两步操作。 |
| 4 | 二维码尺寸 ≥20mm + 纠错 M 是油污/折皱缝边的余量；20mm 以下在车间环境下识别率明显下降。 |
| 5 | 一衣一码 + 返工新建码，让"这张标签属于哪件成衣"始终唯一，返工历史不断链。 |
| 6 | 扫码枪是 HID 键盘，**全局 keydown 捕获**是唯一正确实现方式；依赖输入框焦点会在页面切换、弹窗、快捷键时静默丢扫。 |
| 7 | 工位机不装摄像头 → 零摄像头授权、零相机 SDK、零驱动兼容问题。 |
| 8 | 批量 INSERT + `ON CONFLICT DO NOTHING` 让 2000 件打印任务在 1 个事务内完成，可重跑不重复。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| GS1-128（原 GS1-128 / EAN-13） | ✅ | 服装厂零售端不通用，服装行业没有 EAN 编码体系；需申请 GS1 前缀与厂商代码，成本与收益不匹配。 |
| 动态码（每次扫码内容随时间变化，含签名 token） | ✅ | 增加一层签名服务与失效策略，返工/补打要维护 token 生命周期；工厂内网场景无防伪需求，复杂度纯负担。 |
| 微信小程序码 / 小程序扫码 | ✅ | 需企业主体认证 + 备案（300 元/年，见 ADR-0003）；工位机是扫码枪不是摄像头，小程序码只解决手机侧，反而与扫码枪双载体重复。 |
| GS1 DataMatrix / 纯 DataMatrix | ✅ | 手机相机识别率比 QR 差，车间弱光场景不划算；常见扫码枪对 DataMatrix 支持参差。 |
| 内容塞业务字段（款号+色+码+工序） | ✅ | 换色返工必须重打，且标签与实物不符的概率高；件重等易变字段还会造成"标签即脏数据"。 |
| 只印 Code 128 不印二维码 | ✅ | 手机扫一扫扫不了 1D 条码，员工自助查进度、主管扫码核查就断了。 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 一个内容两种载体覆盖三类终端；一衣一码可追溯；标签规格固定、耗材成本低；工位机零摄像头依赖。 |
| 负面/代价 | 标签 40×40mm 比 20×20mm 耗材高；返工需重打标签（有成本，属正常业务代价）。 |
| 风险 | 扫码枪兼容性（个别廉价枪不补 Enter 键 → 需在全局捕获里加超时兜底）；批量打印中途断电导致部分标签已出、部分未出（靠 `bundle_codes` 已入库 + 重跑幂等解决）。 |
| 迁移路径 | 无存量。新增表 `bundle_codes`（`bundle_no` UNIQUE）+ 打印任务 `print_jobs`。已存在的线下标签不追溯补码，上线后新打菲单必须走系统。 |
| 回滚方式 | 打印路径回退到"导出 CSV 给第三方标签软件"（`00` §3.2 已列为本期不做项的兜底）。 |
| 对规范的影响 | `09` §2.4、`modules/03-打菲.md`；`01` §5.3（批量任务走 `worker`）。新增权限点：无（`bundling:code:void` 已登记）。 |
| 对测试的影响 | 必测：内容纯文本断言（不带任何其他字符）；批量生成 2000 条幂等重跑不产生重复；`voided_at` 写入 + 旧码扫码返回明确"已作废"提示；扫码枪模拟（Playwright 派发 keydown 序列）端到端计件成功。 |

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 扫码识别率（车间真实环境） | ≥ 99.5% | 现场 500 次扫码抽样 |
| 扫码计件落库 P95 | < 150ms | 压测 |
| 2000 件标签生成耗时 | < 60s | 批量任务日志 |
| 重复扫码幂等返回率 | 100%（不报错、不重复计数） | 并发测试 |
| 作废码被扫时提示正确率 | 100% | 用例断言 |
