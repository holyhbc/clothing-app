## 背景

`piecework_logs` 是工资的**唯一事实来源**。车间主管发现某笔计件记错了（扫错件、重复扫、工序录错），在工资已经结算、员工已经拿到钱之后，是会被发现并被要求的。系统必须能回答"这笔钱为什么是这个数"。

- 现状：表结构已定（`04` §7.1）：`log_type ∈ SCAN/MANUAL/REVERSAL/SUPPLEMENT`、`reversal_of_id`、`payroll_id`、`ck_piecework_logs_sign`。
- 痛点/风险：
  1. 一条 `UPDATE piecework_logs SET qty = 3 WHERE id = ...` 在数据库里完全合法，查不出痕迹。
  2. 软删再重录会让流水表出现"空洞"：原始记录 `deleted_at` 有值、新记录 `id` 全新，事后对账无法判断是"修错"还是"重复计件"，责任无法归属。
  3. 结算标记如果用 `is_settled boolean`，会出现"已回写 `payroll_id` 但布尔位忘了改"的双源不一致。
  4. 红冲与补录是**两笔**而不是一笔：红冲必须指向原流水（`reversal_of_id`），否则审计链断掉。
  5. 高并发下红冲 + 补录要一起落事务，否则中途失败会留下"已冲未补"的空账。
- 硬约束：INV-2 明文禁止 UPDATE 金额/数量；只有 `remark/updated_*` 允许改；结算反审核要能自动生成红冲链路。

---

## 决策

**我们决定：`piecework_logs` 只允许 INSERT。修正已记计件用两笔新流水（`REVERSAL` 负数 + `SUPPLEMENT` 正确值）；符号规则由 `ck_piecework_logs_sign` 约束；结算标记只用 `payroll_id`，不设 `is_settled` 布尔列。**

```sql
-- 表结构关键约束（04 §7.1，唯一真源）
CONSTRAINT uq_piecework_logs_idem UNIQUE
  (bundle_no, operation_no, employee_id, work_date, log_type),
CONSTRAINT ck_piecework_logs_sign CHECK (
  (log_type = 'REVERSAL' AND qty < 0 AND amount < 0)
  OR (log_type <> 'REVERSAL' AND qty > 0 AND amount > 0)
);

-- 兜底一：数据库层禁 UPDATE/DELETE（REVOKE + 触发器双保险）
REVOKE UPDATE, DELETE ON piecework_logs FROM app_rw;
CREATE TRIGGER trg_piecework_logs_immutable
BEFORE UPDATE OR DELETE ON piecework_logs
FOR EACH ROW EXECUTE FUNCTION deny_mutate();
-- 触发器仅放行 remark / updated_at / updated_by / payroll_id 四个字段
-- 其余任一字段变更 → raise exception
```

```python
# service 层：红冲 + 补录同事务，且校验前置状态
async def reverse_and_supplement(self, log_id, *, reason: str, ctx: AuthContext):
    async with self.session.begin():
        origin = await self.repo.lock(log_id)            # SELECT ... FOR UPDATE
        if origin.payroll_id is not None:
            raise BusinessError(ErrorCode.PIECEWORK_SETTLED, "已结算流水只能由工资反审核链路红冲"  # 32003)
        reversal = await self.repo.insert_reversal(origin, reason=reason)
        supplement = await self.repo.insert_supplement(origin)   # 正确值
        await self.repo.write_document_logs(origin, reversal, supplement, ctx)
```

```text
结算标记唯一真源：payroll_id IS NULL = 未结算；不为空 = 已归属该工资单。
查询「未结算流水」一律用 payroll_id IS NULL，禁止出现 is_settled 字样。
```

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | 工资是钱。事后可静默修改 = 可篡改 = 无法审计，事后没人能说清钱少了还是被改了。 |
| 2 | append-only 让「这个月的工资明细」永远可重放：所有流水按 `work_date` 汇总即可复现任何历史月份的计算结果。 |
| 3 | 唯一约束同时是幂等键：工位机断网重试（07 §7 指数退避 8 次）携带同 `bundle_no`，`ON CONFLICT DO NOTHING` 保证不重复计数。 |
| 4 | `ck_piecework_logs_sign` 把"负数只可能来自红冲"这条业务规则落到数据库，应用层 bug 也无法写出负数量的正常计件。 |
| 5 | `reversal_of_id` 保留审计链：从任意一笔金额都能追到它的原始流水和修正原因。 |
| 6 | `payroll_id` 单源避免布尔位与外键不一致；`NULL` 判断在索引上比查询布尔列更紧凑。 |
| 7 | 数据库层 `REVOKE` + 触发器是最后一道闸：即使有人绕过 service 层直接写 SQL，也改不动。 |

---

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 直接 `UPDATE qty/amount` | ✅ | 无痕修改，破坏审计，违反 INV-2。工资纠纷时无法举证，且无法回答"这个月为什么少了 200 元"。 |
| 软删（`deleted_at`）后重新录入 | ✅ | 产生数据空洞：原始行被标记删除、新行是全新 id，两行并存在表里，事后无法区分"修正"与"重复计件"，责任不可归属；且部分唯一索引下软删行会挤占幂等键。 |
| 只加 `document_logs` 审计日志，表结构不变 | ✅ | 审计日志是"事后补记"，防不住绕过 service 的直接 SQL；应用层仍有 UPDATE 代码路径，未来会被误用。 |
| 数据库触发器禁一切 UPDATE | ✅ | **采纳为兜底之一**（配合四字段白名单）。单纯"禁一切"会挡住 `payroll_id` 回写和 `remark` 补注，不可取。 |
| 事件溯源 + 单独快照表 | ✅ | 复杂度远超收益；本项目流水量级（年百万行）不需要，快照反而制造双源。 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 审计链完整；工资可重放复算；并发幂等由数据库兜底；应用层 bug 无法破坏数据。 |
| 负面/代价 | 反审核链路更复杂（工资单反审核要级联红冲计件流水，不是简单回滚）；表体积随修正次数增长（年增约 5-10%）；统计查询必须过滤 `log_type` 或直接求和（含负数）。 |
| 风险 | 有人在统计时漏掉负数流水导致件数虚高 → 报表统一走 `SUM(qty)` 不做 `COUNT(*)`，并写 SQL 单元测试；`SUM(qty)` 为 0 的员工在工资单里应显示而非被过滤。 |
| 迁移路径 | 无存量。若已有历史数据需转 append-only：先补 `log_type` 枚举，再按笔生成历史 `REVERSAL`/`SUPPLEMENT` 对，**不改原行**。 |
| 回滚方式 | 不可回滚（append-only 语义一旦上线即永久）。若确需放开，**必须新写 ADR** 并同时下线 `ck_piecework_logs_sign`、触发器、`revoke` 三项，不得只改一处。 |
| 对规范的影响 | `04` §7.1、`00` §5.2 INV-2/INV-3、`modules/04-计件.md`、`modules/05-工资.md` 反审核章节。已用权限点：`piecework:reverse`、`piecework:manual`、`piecework:rate:manage`（均已登记，无需新增）。 |
| 对测试的影响 | 必测（`10` §5 并发场景）：① 50 QPS 同 `bundle_no` 重复提交 → 只落 1 行；② 触发器拒绝 `UPDATE qty`；③ 红冲 + 补录后 `SUM(amount)` 等于修正值；④ 已结算流水被直接红冲 → 拒绝并返回正确错误码；⑤ 工资单反审核级联红冲后账单金额回到修正前。 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| `piecework_logs` UPDATE/DELETE 尝试 | 全部被拒（0 例成功） | 触发器用例 + 权限探针 |
| 重复扫码落库 | 0 重复（唯一约束冲突被捕获） | 并发压测 |
| 每月工资复算差异 | 与结算时结果 0 差异 | 每月重放脚本 |
| 负数流水占比 | < 10%（异常率观测） | `SELECT log_type, count(*) ... GROUP BY 1` |
| 审计链完整率 | 100%（每笔红冲可追到原流水） | 抽样 SQL 检查 `reversal_of_id` 无悬空 |
