# ADR-0008：权限点命名与总表：两级动作词 + 自助权限点内建

## 背景

权限要覆盖 9 个业务模块 × 约 90 个动作点，还要处理"员工自助"和"成本可见性"两个特殊面。命名一旦不统一（比如同时存在 `read`/`list`/`query`），就没法做"权限点完整性检查"，也没法回答"某个用户到底被授了什么"。

- 现状：`07` §2.2 已有权限点总表与命名规则，迁移脚本要按表插入，但两处一致性无强制机制。
- 痛点/风险：
  1. 扁平命名会导致同义异名（`piecework:read` vs `piecework:list`），审计日志里看不出管理员到底授了哪个。
  2. 领域专用动作若合并成单词（`bundling:void_code`），与通用动作混在同一命名空间里，无法用"前缀是否在通用动作表"来判断合法性。
  3. 员工自助权限若进 `permissions` 表，可被误授予角色 → 员工可能拿到管理端能力。
  4. 仓管若默认带成本可见性，服装厂里"仓管知道每件成本"是商业风险。
  5. 工资数据是全项目最敏感数据（`07` §5 工资保密），导出与查看必须分离，且要有二次授权。
  6. **多车间隔离**是本项目的组织前提：单厂多车间是数据范围隔离，不是多租户，所以权限必须同时管"能做什么"和"能看哪些车间"。
- 硬约束：INV-8 权限双校验（操作权限 + 数据范围），前端隐藏 ≠ 安全；新增权限点三处同步，不一致视为闸门 1 失败。

---

## 决策

**我们决定：权限点命名统一为 `<模块>:<动作>`，动作分「通用单据动作」与「领域专用动作」两组，领域动作必须写两级（如 `bundling:code:void`）；员工自助权限点 `self:*` 代码内建、不进角色表；`warehouse_keeper` 不含 `stock:cost:view`；工资相关需二次授权。**

```text
通用单据动作（对齐 08 §1.1，允许一级）：
  read create update submit approve reject withdraw reverse cancel export

领域专用动作（必须两级，禁止合并成单词）：
  print count manual rate:manage settle pay ship order:create
  in out transfer stocktake post receipt payment statement
  cost:view code:void
  例：bundling:code:void（✅）    bundling:void_code（❌ 已废弃 REV-2026-10）
```

```python
# 员工自助权限点：代码内建于 AuthContext，不查 permissions 表
SELF_PERMISSIONS: frozenset[str] = frozenset({
    "self:profile:read", "self:piecework:read",
    "self:piecework:bind", "self:payroll:read",
})
# 明确不存在 self:piecework:count（REV-2026-10）：员工端不开放计件写入

# 成本可见性：接口层按权限裁字段，不是按角色
if not ctx.has("stock:cost:view"):
    row.pop("unit_cost", None); row.pop("amount", None)
```

三处同步（新增权限点时缺一即闸门 1 失败）：

```text
1. docs/07-认证与权限规范.md §2.2 权限点总表
2. Alembic 迁移：INSERT INTO permissions (...) ON CONFLICT DO NOTHING
3. frontend/packages/shared/enums/permissions.ts 权限点常量
```

工资二次授权（`07` §5）：

| 动作 | 权限点 | 附加要求 |
| --- | --- | --- |
| 看本车间工资 | `payroll:read` | 数据范围 ≥ `WORKSHOP` |
| 导出工资表 | `payroll:export` | 写 `document_logs`，记录导出人与行数 |
| 工资结算 | `payroll:settle` | 制单人 ≠ 审核人 |
| 工资发放 | `payroll:pay` | 期间未关账 |

数据范围四级（`apply_data_scope` 在 service 第一行强制注入，**禁止放 Router**）：
`SELF` / `GROUP` / `WORKSHOP` / `FACTORY`；无车间且范围为 `WORKSHOP` → `where(False)`，查不到任何数据。

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | 单一扁平命名会让 `read`/`list`/`query` 混用，审计时无法反查"谁被授权了什么"，也无法做完整性检查。 |
| 2 | 领域动作写两级后，可用"动作段是否属于已知集合"作为 CI 校验规则，非法权限点在迁移阶段就被拦下。 |
| 3 | `self:*` 内建使其成为不可被角色授予的常量集合，缩小攻击面；员工端接口又由 `/api/v1/self/**` 前缀双重锁死。 |
| 4 | `stock:cost:view` 独立权限让"仓管能管库存但看不到成本"成为可配置事实，而不是靠角色硬编码。 |
| 5 | 工资二次授权（`read` / `export` / `settle` / `pay` 四层）匹配"工资是钱"的敏感度要求，导出额外留痕。 |
| 6 | 数据范围与操作权限分离是单厂多车间隔离的最低要求：车间主管有 `cutting:approve` 也不该能审别的车间。 |
| 7 | 固定总表 + 三处同步，使"权限点全集"可被静态检查，AI 生成迁移时越权或漏授权会被立刻发现。 |

---

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 纯 RBAC，不做数据范围 | ✅ | 单厂多车间隔离必须做：车间主管会看到并可能误操作其他车间的单据，计件和工资直接错账。数据范围是组织前提，不是可选项。 |
| 页面级权限（按菜单/路由授权） | ✅ | 页面粒度与业务动作不对齐（同一页面的"审核"和"反审核"风险完全不同），且页面改版就失效，无法审计。 |
| 前端控制为主，后端只判登录 | ✅ | 直接违反 INV-8。任何人改前端 JS 或直接 curl 就能越权，工资与成本数据不可接受。 |
| 字段级 RBAC（统一 `field_mask` 配置） | ✅ | 配置复杂度高于收益；本项目只有成本单价一个必须裁剪的敏感字段，用 `stock:cost:view` 一个权限点足够。 |
| ABAC（属性规则引擎） | ✅ | 需要规则引擎与规则库，2C12G 单机加一个组件不划算；当前数据范围四级用 `apply_data_scope` 的 `match` 已完全覆盖。 |
| 每用户直授权限（跳过角色） | ✅ | 权限授予路径 proliferate 后无法回答"某个角色本该有什么"，且 200 名员工的授权清单不可维护。 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 权限点全集可静态校验；审计可反查；成本与工资的敏感面可独立收口；越权在 service 层被拦。 |
| 负面/代价 | 新增动作要改三处（规范 + 迁移 + TS 常量），前期慢；两级命名比一级长，前端书写略啰嗦。 |
| 风险 | 三处不同步（最常见：改了迁移忘了改 TS 常量，前端按钮永久隐藏，表现为"权限没生效"）→ 闸门 1 有专门校验脚本；`warehouse_keeper` 被误加 `stock:cost:view` → 角色初始化迁移用显式列表 + 审查。 |
| 迁移路径 | 初始化迁移幂等插入全部权限点与 10 个系统角色；存量无数据。后续新增权限点走"改表 → 加迁移 → 改 TS"三步。 |
| 回滚方式 | 权限点行可软删（`permissions` 属硬删禁令表，只能软删）；角色权限解绑写 `document_logs`。命名规则若要改，属决策变更，须新写 ADR 并把本篇标记 `Superseded`。 |
| 对规范的影响 | `07` §2.2（总表，唯一真源）/§2.3（内置角色）/§3/§4/§5/§6、`08` §1.1（通用动作对齐）、`03`（禁止 `if role == 'admin'` 硬编码）。**本文不新增权限点**，只固化命名与总表机制。 |
| 对测试的影响 | 必测：① 每个权限点至少一条 403 用例（约 90 条，参数化跑）；② 数据范围四级各一条越权用例（`SELF` 查他人、`WORKSHOP` 查他车间）；③ 无车间 + `WORKSHOP` → 空列表；④ `warehouse_keeper` 调成本接口响应体无 `unit_cost`；⑤ 员工 token 调 `/api/v1/self/**` 之外全 403；⑥ 权限点三处一致性脚本测试。 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 权限点三处一致性 | 100%（闸门 1 每次发版校验） | CI 脚本比对规范表 / 迁移 / TS 常量 |
| 无孤儿权限点 | 0（未被任何角色引用的权限点，要么是规划中要么删掉） | 巡检 SQL |
| 未引用角色/权限 | 0 | 巡检 SQL |
| 越权测试覆盖 | 每个权限点 ≥ 1 条 403 用例，覆盖率 100% | 覆盖率报告 |
| 成本字段泄漏 | 0 例（无 `stock:cost:view` 的响应体不含 `unit_cost`） | 安全用例 |
| 员工端越权尝试 | 100% 403 | 安全用例 |
