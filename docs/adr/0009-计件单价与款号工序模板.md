# ADR-0009：计件单价按工序定价，支持时间维度调价与款号工序模板复制

## 背景

### 现状

业务方确认的计件定价规则：

1. **单价按工序定** —— 不同工序单价不同（如打边 0.35 元/件、装袖 1.20 元/件）。**不按技能等级分级**。
2. **工序由用户自定义增删改** —— 各厂工序名不同（有的叫"拼前"、有的叫"合并前身"），不能内置枚举。
3. **同一款号、同一工序，单价可能随时间变化** —— 旺季加急、物价上涨、用工成本变化都会调价。
4. **款号工序与单价要能当模板快速复制** —— 同一客户连续几款衣服工序和工价基本相同，每次手工重录成本高且易错。

### 痛点

| # | 痛点 | 后果 |
| --- | --- | --- |
| 1 | 如果单价存在一行可 UPDATE | 改了价格后历史计件流水的金额含义漂移，无法复盘"当时为什么按这个价" |
| 2 | 调价若"从今天起生效"但已计件的数据已按旧价落库 | 月底结算时工资与车间对账不上 |
| 3 | 工序内置枚举 | 换厂/加工序要改代码发版 |
| 4 | 款式工序手工重录 | 复制 15 个工序 × 6 款 = 90 行手工输入，出错率极高 |

### 硬约束

- 已有规范 `INV-3`：计件流水必须快照单价，历史不受基础资料变更影响（不可推翻，是审计底线）
- 已结算的工资不能因基础资料改动而变化
- 计件流水 `append-only`（`INV-2`，见 [ADR-0005](./0005-计件流水不可变与红冲机制.md)）

---

## 决策

**我们决定：计件单价以「款号 × 工序 × 生效区间」建模，价格历史只追加不修改；工序为用户自定义主数据；款号工序配置与单价可整套复制到另一个款号。**

### 1. 单价时间维度（`operation_rates`）

```sql
style_no + operation_no + effective_from + effective_to + unit_price
UNIQUE (style_no, operation_no, effective_from)
```

- 取价按**计件日期 `work_date`** 命中生效区间：`effective_from <= work_date < effective_to`（`effective_to` NULL 表示当前有效）
- **调价 = 关闭旧区间 + 插入新区间**，绝不 `UPDATE unit_price`
- 生效日可以是未来日期（提前公告）
- 生效区间不允许重叠

### 2. 工序为用户自定义主数据（`operations`）

- `operation_no` + `name` + `is_piecework` + `default_bundle_qty` + `is_active`
- **不内置枚举**
- 被引用后禁止删除，只能停用
- 一扎几件（`bundle_qty`）由**款号工序配置**决定，工序表只给默认值

### 3. 款号工序配置（`style_operations`）+ 模板复制

```sql
UNIQUE (style_no, operation_no)   -- 字段：sequence 工序顺序、bundle_qty、is_piecework
```

**模板复制**：以源款号的 `style_operations` + `operation_rates` 为模板，一键复制到目标款号。
复制选项（用户选择）：① 沿用源价 ② 沿用源价并按比例调整 ③ 只复制工序结构，价格到目标款号单独设。

### 4. 与既有不变量的关系

| 不变量 | 如何满足 |
| --- | --- |
| `INV-3` 单价快照 | 计件流水仍写死 `unit_price`；取价只发生在流水落库那一刻 |
| `INV-2` 流水 append-only | 调价不动流水，只改 `operation_rates` |
| 已结算工资不变 | 结算单里 `unit_price/amount` 也是快照 |

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **价格历史必须可解释**。月底工人问"为什么我这件是 0.35"，系统要能答"因为你 8 月 1 日到 8 月 15 日做的是 0.35，8 月 16 日起调为 0.38"。只存当前价的表答不出来。 |
| 2 | **调价不能改历史**。这是发工资的凭据，一旦允许 UPDATE 就无法审计，也无法应对劳动争议。 |
| 3 | **按计件日期取价而不是按结算日期取价**。否则月中调价会导致月中已做的东西被追溯扣钱，工人不会接受。 |
| 4 | **工序不内置**。服装厂工序名高度本地化（打边/敲边/合并前身/打缆/点烫…），内置枚举必然要发版。 |
| 5 | **`bundle_qty` 挂在款号工序上而不是工序上**。因为"打边一扎 1 件"和"查勘一打 12 件"同时存在于同一款衣服。 |
| 6 | **模板复制解决最高频的重复劳动**。款式开发中"同客户同系列"占比很高，复制比录入快 10 倍且不会漏工序。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 单价表加 `updated_at`，只保留当前价 + 一个 `price_history` JSONB | ✅ | JSONB 里的历史无法建约束、无法按日期索引查询；取价 SQL 变成 JSON 展开，性能与可维护性都差 |
| 单价表用 `(style_no, operation_no)` 唯一，允许同键多行但靠业务判断最新 | ✅ | 没有生效区间字段就无法回答"8 月 10 日那天该多少价" |
| 单价挂在"工序"上（款号无关） | ✅ | 同款不同工序同价时冗余；不同款同工序价差极大（简单款打边 0.30，复杂款 0.80），必须按款号定价 |
| 单价按"工序 + 技能等级"二级维度 | ✅ | **业务方明确否掉**。等级判定主观、争议大，工人不接受"凭啥他拿一级我拿三级" |
| 工序内置枚举 + 配置扩展 | ✅ | 枚举仍会被绕过；直接做主数据表更干净 |
| 模板复制用"整单复制"（连带 BOM、颜色） | ✅ | 范围过大，BOM 与颜色因款而异；只复制工序与单价才是高频可复用部分 |
| 用 PostgreSQL 范围类型 `daterange` + `EXCLUDE` 防重叠 | ✅（未采纳） | 更严谨，但需要 btree_gist 扩展且中国工厂日期口径简单；用 `effective_from` 唯一索引 + 服务端校验区间不重叠已足够 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 调价可追溯；模板复制省 90% 重复录入；工序扩展零发版；历史工资永远可解释 |
| 负面/代价 | 取价 SQL 变复杂（区间命中）；调价必须走"关闭+新增"两步而不是一次 UPDATE，前端要设计调价表单 |
| 风险 | 生效区间重叠导致取价不确定 → 服务端校验 + 数据库唯一索引双保险；未来调价误操作 → `document_logs` 记录新旧价 + 调价必填原因 |
| 迁移路径 | 新建 `operations` / `style_operations` / `operation_rates` 三表；存量（阶段一为空）无需数据迁移；`piecework_logs.unit_price` 保持不变 |
| 回滚方式 | 三表为新增，删除即可；`piecework_logs` 未改动，回滚无数据损失 |
| 对规范的影响 | 04 §7.5 新增三表 DDL 与取价口径；07 §2.2 新增 `base:operation:manage` / `base:rate_template:manage`；05 §4 新增 `20004 未设单价`；09 §4 关闭 Q-01 |
| 对测试的影响 | **必测**：① 按 `work_date` 取到历史价（调价前后各一条）② 调价后旧流水金额不变 ③ 生效区间重叠被拒 ④ 未来生效价不影响当日计件 ⑤ 未设单价报 `20004` ⑥ 模板复制后目标款号工序完整且价格可覆盖 ⑦ 工序被引用后删除被拒 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 调价可追溯率 | 100% | 任取历史计件流水，能查到当日生效单价并复算出金额 |
| 新建款号工序录入耗时 | ≤ 30 秒（用模板复制） | 手工计时 |
| 模板复制错误率 | 0 | 复制后工序数与单价数与源款号逐项核对 |
| 月底工资对账争议 | 0 起无法解释的金额差异 | 车间对账记录 |
