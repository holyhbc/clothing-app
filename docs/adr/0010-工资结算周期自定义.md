# ADR-0010：工资结算周期为用户自定义起止日期区间

| 项 | 内容 |
| --- | --- |
| 状态 | Accepted |
| 日期 | 2026-10-01 |
| 决策人 | 业务方 + AI |
| 影响范围 | 数据库 / 工资模块 / 计件取数 |
| 关联 | [04-数据库规范 §7.4](./../docs/04-数据库规范.md)、[modules/05-工资](./../docs/modules/05-工资.md) |

---

## 背景

### 现状

业务方确认的结算周期规则：

1. **周期由用户自定义截止时间**，不写死自然月。
2. **常见两种**：整月一次；两月一次（例：7 月 + 8 月一起结）。
3. 有时**按裁剪打菲的完成时间截取**作为周期边界（货做完了就结算）。

### 痛点

| # | 痛点 | 后果 |
| --- | --- | --- |
| 1 | 若用 `period varchar` 存 `'2026-08'` 这类标签 | 无法用 SQL 按区间取数；两月一次写成 `'2026-07~08'` 后所有统计都要字符串解析 |
| 2 | 若枚举固定周期（月/半月） | 两月一次要改代码；不规则周期（按裁剪完成日）完全没法支持 |
| 3 | 周期边界不明确 | 月中调价时，8 月 16 日做的活算 7 月还是 8 月，会和车间扯皮 |

### 硬约束

- 计件流水按 `work_date` 落库（每日一条，不按周期落）
- 已结算的工资不能因周期调整而变化（结算单是快照）
- 结算单必须能防重复结算同一区间

---

## 决策

**我们决定：结算周期是一张用户自建的「起止日期区间」表，取数按 `work_date BETWEEN start_date AND end_date`；标签与区间分离，标签随便写，区间是唯一约束依据。**

### 1. 周期主数据（`payroll_periods`）

```sql
period_code  varchar(32)   -- 用户自定义标签，随便写：'2026-08' / '7-8月' / '夏季款'
start_date   date NOT NULL -- 起始日（含）
end_date     date NOT NULL -- 截止日（含）
status       OPEN | CLOSED
source       MANUAL | CUTTING_BOUNDARY  -- 是否从裁剪/打菲完成日自动推导
UNIQUE (period_code)
UNIQUE (start_date, end_date)           -- 区间不重复，从库层面防重复建周期
```

### 2. 标签与区间分离

`period_code` 是给人看的，**唯一性由 `(start_date, end_date)` 保证**。
这让"7-8 月"这种非标准标签也能用，同时 SQL 取数永远走日期比较。

### 3. 三种建周期的方式（都落在同一张表）

| 方式 | 操作 | `source` |
| --- | --- | --- |
| 自定义 | 手工填标签 + 起止日 | `MANUAL` |
| 整月 | 点"生成整月"自动填 `YYYY-MM-01` ~ `月末`，标签 `YYYY-MM` | `MANUAL` |
| 两月一次 | 点"生成两月"选起始月，自动算 2 个自然月 | `MANUAL` |
| 按裁剪打菲截取 | 选定款号，系统取该款裁剪单最早完成日 ~ 最晚打菲完成日，生成区间，标签自动填 `裁剪{起}-{止}` | `CUTTING_BOUNDARY` |

### 4. 关闭与重开

- 周期 `CLOSED` 后不可再往里加结算单（`33003`）
- 重开需 `payroll:period:manage` + 必填原因 + 写 `document_logs`
- 周期区间重叠申请被拒（`33004`）

### 5. 取数口径

```sql
SELECT employee_id, operation_no, SUM(qty), SUM(amount)
FROM piecework_logs
WHERE work_date BETWEEN :start_date AND :end_date
  AND workshop_id = :workshop_id
  AND payroll_id IS NULL          -- 只算未结算的（INV：不重复结算）
  AND deleted_at IS NULL
GROUP BY employee_id, operation_no;
```

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **区间是唯一可计算的形式**。标签随便写，统计靠日期。两月一次不需要任何特殊处理。 |
| 2 | **用户自定义是硬需求**。代工厂的结算节奏跟着货走，跟着客户走，跟着老板心情走。写死枚举必然要发版。 |
| 3 | **`UNIQUE (start_date, end_date)` 从库层面防重复建周期**，比服务端校验可靠。 |
| 4 | **`payroll_id IS NULL` 保证不重复结算**，与 `INV-2` 的 append-only 一致。 |
| 5 | **`source = CUTTING_BOUNDARY` 覆盖"按裁剪打菲时间截取"**，把业务方的实际做法落进系统，而不是让用户在日历上自己数天数。 |
| 6 | **标签与区间分离**避免了"标签必须唯一导致不能有两个同名的 8 月结算"这种尴尬。 |

---

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| `period varchar` 存 `'2026-08'` | ✅ | 无法按区间取数；两月一次与按裁剪截取都要字符串解析，越用越乱 |
| 枚举固定周期（月/周/半月） | ✅ | 两月一次与不规则周期不支持；加一种周期就要发版 |
| 用 `date_part('month', work_date)` 分组自动出周期 | ✅ | 不支持两月一次；也无法表达"到 8 月 25 日为止" |
| 每个车间一个结算周期（表里存 `workshop_id`） | ✅ | 周期是全厂口径，车间只是结算维度。放在周期表会导致同区间多行、`UNIQUE` 失效 |
| 用 PostgreSQL `daterange` + 范围排除约束防重叠 | ✅（未采纳） | 严谨但对"整月/两月"这类规则化区间收益低；用日期区间 + 应用层校验即可 |
| 周期关闭后自动重开 | ✅ | 会让已结算数据被动变化，违反结算单快照原则 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 支持任意区间；整月/两月/按裁剪截取统一模型；标签自由不影响计算 |
| 负面/代价 | 计件流水查询必须带区间条件（有利有弊：走 `idx_piecework_logs_work_date_workshop_id_style_no`）；建周期需要 UI 提供"生成整月/两月/按裁剪"三个快捷入口 |
| 风险 | 周期区间设错（比如漏了 8 月最后 3 天）→ 已结算的单不受影响，但未结算流水会漏；缓解：建周期时**显示区间内的计件流水条数与金额合计**，让用户核对 |
| 迁移路径 | 新建 `payroll_periods`；`payroll_settlements.period varchar` 改为 `period_id uuid` 外键（阶段一表为空，无数据迁移） |
| 回滚方式 | 表为新增，删除即可 |
| 对规范的影响 | 04 §7.4 新增周期表 DDL；05 §4 新增 `33003` / `33004`；07 §2.2 新增 `payroll:period:manage`；09 §4 关闭 Q-02 |
| 对测试的影响 | **必测**：① 整月周期取数边界（含首尾日，不含次日）② 两月一次跨月取数 ③ 同区间重复建周期被拒 ④ `CLOSED` 周期加结算单被拒 ⑤ `payroll_id IS NULL` 保证不重复结算 ⑥ 重开周期必填原因 ⑦ 区间有重叠申请被拒 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 结算漏算 | 0 | 结算完成后对账：`周期内未结算流水条数 = 0` |
| 重复结算 | 0 | 每条流水 `payroll_id` 唯一 |
| 建周期耗时 | ≤ 1 分钟 | 手工计时（点"生成两月"后确认） |
| 边界争议 | 0 起 | 车间对账记录 |
