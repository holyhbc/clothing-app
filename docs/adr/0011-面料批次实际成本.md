# ADR-0011：面料成本采用逐批（缸号）实际成本，撤销移动加权平均

## 背景

### 现状

业务方明确要求：**面料成本逐批计算**（不要移动加权平均）。

### 为什么业务方要逐批

| # | 业务原因 |
| --- | --- |
| 1 | **色差是服装代工的常规争议点**。同款面料不同缸号有色差，客户拒收时按缸号追溯成本。如果用移动加权，成本被抹平，追溯不出来源缸号 |
| 2 | **对账习惯**。代工厂与客户/面料商常按缸号核销损耗，"这个缸用了多少米"要能直接查 |
| 3 | **损耗责任到缸**。面料损耗争议往往精确到某个缸，用加权成本算出来的金额客户不认 |
| 4 | **旺季加价与缸价差异**。同一面料不同时间采购价不同（涨跌、涨价函），加权会把低价料和高价料混在一起 |

### 原规范为什么写的是移动加权

AI 在初版规范中按制造业通用做法选了移动加权平均（`unit_cost = (金额+入库金额)/(数量+入库数量)`），理由是"实现简单、报表平滑"。**这是 AI 自行选型，没有问业务方** —— 属于典型的"AI 自行发明业务规则"，本次由业务决策纠正。

---

## 决策

**我们决定：撤销移动加权平均。面料/辅料库存按批次（缸号 `dye_lot_no` + 匹号 `bolt_no`）独立计价，批次内 `unit_cost` 恒定不变；出库必须记录用了哪些批次，成本按实际批次结转。**

### 1. 库存粒度到批次

```sql
material_stocks:  仓库 + 物料 + dye_lot_no + bolt_no + 色 + stock_qty + unit_cost
```

`unit_cost` 在入库审核那一刻确定，**此后永不改变**。

### 2. 入库时确定批次成本

| 场景 | `unit_cost` |
| --- | --- |
| 采购入库 | `(采购金额 + 分摊费用) ÷ 入库数量`，精确 6 位 |
| 生产退料 | 沿用原批次 `unit_cost` |
| 盘盈 | 同物料同缸号最近批次；无则同物料最近批次 + 写日志 |
| 成本调整 | **禁止 UPDATE**。必须红冲原入库单 + 重新入库 |

### 3. 出库选批规则（强制优先级）

| 优先级 | 规则 | 场景 |
| --- | --- | --- |
| 1 | **人工指定批次** | 裁剪按客户指定缸号配料（最常见） |
| 2 | **FEFO**（先到期先出） | 有保质期辅料 |
| 3 | **FIFO**（先进先出） | 无保质期物料默认 |

**禁止**跨批次混合后按平均价出库。

### 4. 出库必须留批次耗用明细

新增 `stock_ledger_lines`（出库批次耗明细）：一条出库台账 → N 条批次耗用（`dye_lot_no` / `bolt_no` / `qty` / `unit_cost` / `amount`）。

这让「这件成衣用了哪几缸布、各多少米、各多少钱」可完整反查。

### 5. 成衣成本

```
成衣单位成本 = Σ(stock_ledger_lines.amount 该扎消耗) + Σ(piecework_logs.amount 该扎计提工价)
```

完工入库时快照，之后不可改。

### 6. 报表口径

毛利、成本分析一律按**实际批次成本**出账，不得使用任何平均价。

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **可追溯性 > 报表平滑**。ERP 首先要能对账和追溯，"好看"的平滑成本在对账时是负资产。 |
| 2 | **批次成本天然可加**。同一缸的多批次合并求和即可，无需重新分配。 |
| 3 | **选批规则前置**。人工指定批次把"用哪缸布"的决定权交给车间/跟单，这符合代工厂实际做法。 |
| 4 | **审计友好**。批次成本不变意味着任何历史时点的成本都能重算出来，移动加权做不到（要依赖完整的入出库顺序）。 |
| 5 | **与服装行业事实一致**。缸号是服装面料成本的最小管理单元，这不是 ERP 的抽象而是行业现实。 |

---

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 移动加权平均（原规范） | ✅ | **业务方否决**。色差追溯与缸号对账做不了，损耗责任无法定位到缸 |
| 批次实际成本（**采纳**） | ✅ | 实现略复杂（需 `stock_ledger_lines`），但换来完整可追溯性 |
| 先进先出 + 固定单价（无批次） | ✅ | 同缸不同价无法区分，仍是变相加权 |
| 双轨（可选移动加权） | ✅ | 双轨会让财务口径不唯一，报表对不上；本项目只保留批次实际成本 |
| PostgreSQL `range` 分区表按时间切批 | ✅（未采纳） | 缸号不是时间维度的连续区间，分区表解决不了一缸多批次 |
| 批次成本允许管理员手工改 | ✅ | 违反 `INV-4`（批次成本不可篡改），只能红冲重入 |
| 用 `stock_ledgers` 单表加 `dye_lot_no` 存批次 | ✅（未采纳） | 一条出库跨多批次时无法表达，会被迫取"主批次"丢失信息。必须拆子表 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 成本可追溯到缸号；与客户/面料商按缸对账；毛利分析真实；历史任意时点成本可重算 |
| 负面/代价 | 出库必须选批（用户多一步操作）；库存表行数增加（同缸多匹 → 多行）；`stock_ledger_lines` 增加存储与查询复杂度 |
| 风险 | ① 用户漏选批次导致成本不准 → 强制选批规则（不允许"按平均"）② 库存行数膨胀影响列表性能 → 列表默认按批次折叠到物料级 ③ 选批逻辑并发不安全 → 条件 UPDATE `WHERE stock_qty >= n` + 唯一约束兜底 |
| 迁移路径 | ① `material_stocks` 增列 `dye_lot_no` / `bolt_no` / `unit_cost`（改为 NOT NULL 的 CHECK）② 新建 `stock_ledger_lines` 表 ③ `stock_ledgers` 移除 `unit_cost`/`amount`（改由子表汇总）④ **数据迁移分两步**：先加可空列 → 存量数据按移动加权反算填充批次 → 加约束（避免一次 ALTER 长时间锁表） |
| 回滚方式 | 步骤 ①② 可逆（删列、删表）；步骤 ③ 的数据回填需从备份恢复或写反向脚本，因此**上线前必须备份并演练** |
| 对规范的影响 | 04 §7.2 整节重写（加 `stock_ledger_lines`、选批规则、入库成本确定规则）；04 §7.1 → §7.6 章节号调整；09 §4 关闭 Q-03 |
| 对测试的影响 | **必测**：① 同缸两批次不同价，出库按选中批次结转 ② FIFO 选批顺序正确 ③ FEFO 按到期日 ④ 库存不足不部分出库 ⑤ 出库台账必有批次明细 ⑥ `v_stock_reconciliation` 恒 0 行 ⑦ 批次成本禁止 UPDATE（DB 层触发器或权限拒绝） ⑧ 成衣成本 = 批次耗用合计 + 计提工价 ⑨ 反审核按同一 `stock_ledger_lines` 逐条反向冲回 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 成本可追溯率 | 100% | 任抽 10 扎成衣，能列出消耗的缸号、匹号、米数、金额 |
| 缸级对账通过率 | 100% | 按缸号汇总耗用与账面一致 |
| 库存与台账对账 | `v_stock_reconciliation` 恒 0 行 | 每日巡检 + 发布前强制 |
| 出库行数膨胀 | 列表 P95 < 800ms | `EXPLAIN ANALYZE` + 慢查询日志 |
