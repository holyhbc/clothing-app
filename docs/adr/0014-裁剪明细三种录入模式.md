# ADR-0014：裁剪明细三种录入模式（比例只是建议值）

| 项 | 内容 |
| --- | --- |
| 状态 | Accepted（**修订 ADR-0013 的「用户只填 1 个每手件数」条款**；ADR-0013 其余内容仍有效） |
| 日期 | 2026-10-01 |
| 决策人 | 业务方 + AI |
| 影响范围 | 数据库 / 裁剪模块 / 基础资料 |
| 关联 | [04-数据库规范 §7.7](./../docs/04-数据库规范.md)、[modules/02-裁剪](./../docs/modules/02-裁剪.md) |

## 背景

### ADR-0013 原本的决策（以及为什么不够用）

ADR-0013 定的是：**比例按款号 × 颜色预置（手数），`每手件数` 在裁剪单上逐行输入，明细 = `floor(ratio × qty_per_hand)`。**
即"用户只填 1 个每手件数，比例自动带出所有尺码"。

### 业务方补充的真实场景（2026-10-01）

> 比例和每手件数支持输入。
> 有的时候**所有的尺码件数一样**；
> 有的时候**裁床个别尺码数量不一致，需要自定义**。
> 比如 L XL XXL 3XL 比例是 1 2 2 1，每手 60 件，
> **后来又多个 XL 1 手 30 件**，支持我增加、修改、删除录入。

### 逐条拆解出 3 个新需求

| # | 需求 | ADR-0013 能否满足 |
| --- | --- | --- |
| 1 | 所有尺码件数一样 | ❌ 比例不为 1:1:1:1 时算不出等量 |
| 2 | 个别尺码数量不一致（自定义） | ❌ 比例是主数据，改主数据会污染其他单据 |
| 3 | **同一尺码多行且每手件数不同**（XL 既有 2手×60件，又加 1手×30件） | ❌ ADR-0013 的行模型是「一尺码一行」，无法表达 |

### 痛点

如果强行沿用 ADR-0013，业务方为了"XL 多裁 1 手 30 件"会去改**比例主数据**，把 XL 从 2 手改成 3 手 —— 结果**下次裁剪也会变成 3 手**，污染所有历史与未来单据。这是严重的数据污染。

---

## 决策

**我们决定：比例降级为「建议值」，裁剪单明细行升级为「权威数据」，提供三种录入模式（A 按比例带出 / B 统一件数 / C 自定义明细），三种模式可按颜色混用。**

### 1. 行模型修订（核心）

| 字段 | 粒度 | 语义 | 修订前（0013） | 修订后（0014） |
| --- | --- | --- | --- | --- |
| `hands` | **行级** | 本次该尺码裁几手 | 取自比例，不可改 | **行级可改，同尺码多行可不同** |
| `qty_per_hand` | **行级** | 本次该尺码每手几件 | 单据级（1 个值） | **行级，同尺码多行可不同** |
| `qty` | 行级 | 出数 | `floor(ratio × qty_per_hand)` | `floor(hands × qty_per_hand)`，可人工覆盖 |
| `entry_mode` | 颜色级 | 录入模式 | 无 | `MASTER` / `UNIFORM` / `MANUAL` |
| `ratio_snapshot` | 单据级 | 比例快照 | 无 | jsonb，便于事后解释 |
| 唯一约束 | — | — | `(doc_id, size_code)` 隐含 | **`(doc_id, color_code, size_code, line_no)`，允许同尺码多行** |

### 2. 三种模式

| 模式 | 界面动作 | 行为 | 适用场景 |
| --- | --- | --- | --- |
| **A `MASTER` 按比例带出** | 点「按比例带出」 | 自动生成每个尺码一行，`hands` = 比例；用户只填 `qty_per_hand` | 常规，比例固定的款 |
| **B `UNIFORM` 统一件数** | 点「统一件数」→ 填 1 个件数 | 所有尺码行 `qty` 相同；`hands` 反算 | **所有尺码件数一样** |
| **C `MANUAL` 自定义明细** | 可增/删/改任意行 | `hands` / `qty_per_hand` / `qty` 任填其一 | **裁床个别尺码不一致** |

**模式是颜色级属性**，同一张裁剪单里红色走 A、黑色走 C 完全允许。

### 3. 业务方原话场景的落地

```
红色 · L:XL:XXL:3XL = 1:2:2:1，每手 60 件     〔模式 A〕
┌──────┬───────────┬───────┬────────────────┐
│ 尺码 │ hands(手) │ 每手  │ qty(件)        │
├──────┼───────────┼───────┼────────────────┤
│ L    │ 1.0000    │ 60    │ 60             │
│ XL   │ 2.0000    │ 60    │ 120            │
│ XXL  │ 2.0000    │ 60    │ 120            │
│ 3XL  │ 1.0000    │ 60    │ 60             │
├──────┼───────────┼───────┼────────────────┤
│ 合计 │ 6.0000    │       │ 360            │
└──────┴───────────┴───────┴────────────────┘

后来又多个 XL 1手 30 件                        〔切到模式 C，追加一行〕
│ XL   │ 2.0000    │ 60    │ 120            │  ← 原比例行
│ XL   │ 1.0000    │ 30    │ 30             │  ← 新增行（每手件数不同）
│ 合计 │ 7.0000    │       │ 390            │
```

**关键**：新加的那行**不写回比例主数据**，只存在于这张裁剪单里。

### 4. 切换模式的保护

从 `MASTER` 切到 `UNIFORM` / `MANUAL` 会清掉当前行的 `hands`，必须**二次确认**并提示"已有 N 行手数将被清空"。

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **比例是"排版模板"，不是"本次裁多少"**。这两件事天然不同，硬合并成一个必然出问题。 |
| 2 | **同尺码多行是真实需求**。业务方明确"XL 1手60件 + XL 1手30件"，这是"同一尺码不同每手件数"，一对一模型表达不了。 |
| 3 | **降级比例为建议值 = 零污染**。业务方临时改量不再需要动主数据，历史单据的 `ratio_snapshot` 仍能解释"当时为什么这么裁"。 |
| 4 | **三种模式覆盖全部实际情况**：常规（比例）、等量（统一）、特殊（自定义）。不留死角。 |
| 5 | **模式是颜色级**而不是单据级，因为业务方的差异是"这个颜色特殊"，不是"整单特殊"。 |
| 6 | **保留 `MASTER` 作为默认**，让 90% 的常规裁剪仍然只需填 1 个数，不增加操作负担。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 沿用 ADR-0013（一尺码一行） | ✅ | 表达不了"XL 1手60 + XL 1手30" |
| 改比例主数据来表达 | ✅ | **数据污染** —— 改主数据影响所有未来单据，是严重错误 |
| 用一条明细 + 备注写"XL 再加 30 件" | ✅ | 备注不可计算、不可校验，打菲与计件无法引用 |
| 比例做到"尺码+每手件数"二维 | ✅ | 组合爆炸（4 尺码 × 5 每手件数 = 20 行主数据），不可维护 |
| 只做「按比例」和「全手填」两种模式（不做统一件数） | ✅ | 统一件数是高频场景（补单、小单），不该让用户手填 N 行 |
| 每次裁剪都手工全新录明细（不要比例） | ✅ | 常规场景录入负担大，比例复用价值被浪费 |
| 明细行加 `notes` 存差异说明 | ✅ | 说明不可计算；系统必须能算出件数才能往下游传 |
| 模式做成单据级（整单统一一种模式） | ✅ | 业务方差异是颜色级；整单级别会把 A 的便利强加给 C 的场景 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 覆盖全部实际裁剪场景；临时改量零污染；录入负担从"填 N 行"降到"点一下 + 填 1 个数"（模式 A/B） |
| 负面/代价 | 界面需要三个模式切换按钮 + 二次确认；行数可能变多（模式 C）；`ratio_snapshot` 占少量存储 |
| 风险 | ① 用户误以为改比例会改单据 → 模式 A 的 `hands` 显示为"建议值（可改）"，并注明"改动不影响其他单据" ② 切模式丢数据 → 二次确认 + 已保存的行在切前提示 ③ 同尺码多行导致打菲/计件引用歧义 → 打菲单引用 `cutting_order_line_id`（**行级**，不是尺码级），见下方"下游影响" |
| 迁移路径 | `cutting_order_lines` 增 `hands`、`entry_mode`、`ratio_snapshot`；唯一约束从 `(doc_id, size_code)` 改为 `(doc_id, color_code, size_code, line_no)`；阶段一表为空，无数据迁移 |
| 回滚方式 | 列与约束可逆 |
| 对规范的影响 | 04 §7.7 整节重写（新增 §7.7.2 行模型 + §7.7.3 三种模式）；05 §4 新增 `50011`/`50012`；07 §2.2 采购行补 `purchase:arrival`；08 §2.1 裁剪审核③ 表述微调 |
| 对测试的影响 | **必测**：① 模式 A 1:2:2:1×60 → 60/120/120/60 = 360 ② 模式 B 统一 100 件 → 全尺码 100 ③ 模式 C 追加 XL 1手30件 → 合计 390 且**比例主数据未被修改** ④ 同尺码多行可保存可查询 ⑤ 模式切换二次确认 ⑥ 人工改 `qty` 自动转 MANUAL ⑦ 余量并入 `balance_qty` ⑧ 三模式同单混用（红 A 黑 C） |
| **下游影响（重要）** | 打菲单与计件必须引用 **`cutting_order_line_id`（行级）**而不是 `size_code`。因为同尺码可能有多行，打菲/计件要能区分是哪一行。`piecework_logs` 增加 `cutting_line_id`（可空，兼容历史）。 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 录入耗时 | 模式 A/B ≤ 1 分钟；模式 C 按行数 | 手工计时 |
| 比例主数据污染 | 0 次 | 模式 C 用完后检查 `style_color_size_ratios` 未变 |
| 明细行正确性 | 100% | 裁剪单出数与车间实际件数核对 |
| 下游引用无歧义 | 100% | 打菲/计件均带 `cutting_line_id` |
