# ADR-0016：打菲按「手」—— 一码一手、手序号编号、扫码得件数

| 项 | 内容 |
| --- | --- |
| 状态 | Accepted（**修订 ADR-0004 的「一码一件」默认口径**；ADR-0004 的「二维码=纯 bundle_no」条款仍有效） |
| 日期 | 2026-10-01 |
| 决策人 | 业务方 + AI |
| 影响范围 | 数据库 / 打菲模块 / 计件模块 / 标签打印 / 裁剪模块 |
| 关联 | [04-数据库规范 §7.1 / §7.7](./../docs/04-数据库规范.md)、[modules/03-打菲](./../docs/modules/03-打菲.md)、[modules/04-计件](./../docs/modules/04-计件.md) |

---

## 背景

### 业务方 2026-10-01 原话

> 打菲按照手数大，比如尺码比例 1 2 2 1 那就 6 手，**如果再加一个那就 7 手**，**扫码就可以知道这手数量**。
>
> **对，按照手打，而且每手要有编号**。例如 XL 2 手打两张就重复 —— 如果多个员工生产就不知道谁做工。
>
> 扫一下默认是这手件数，但有时候这手可能就生产一部分数量，**可以支持手写数量**，但是**数量必须小于等于裁剪单该手的件数**。
>
> 数量**不带**在码里，**查库得到**（沿用 ADR-0004）。

### 逐条拆解

| # | 需求 | 影响 |
| --- | --- | --- |
| 1 | 打菲单位是「**手**」不是「件」 | 打菲行粒度 = 尺码 + 手序号 |
| 2 | **每手要有编号** | `bundle_no` 必须能区分同一尺码的多个手；标签要印「第 N 手 / 共 M 手」 |
| 3 | **多员工生产要能区分谁做的** | 一码 = 一手 = 一个责任单元，只允许一个员工计一次 |
| 4 | **扫码就知道这手数量** | `bundles.bundle_qty` 落库，扫码查库得到（**码里不带数量**） |
| 5 | 支持**部分生产**（这手只做了一半） | 计件 `qty` 可手写，但 `0 < qty ≤ bundle_qty`（不允许超产） |
| 6 | 数量不写进码 | 沿用 ADR-0004：二维码 = 纯 `bundle_no`；好处是改件数不用作废旧码 |

### 硬约束（不变）

- 二维码内容 = 纯 `bundle_no` 文本，Code128 同内容（[ADR-0004](./0004-打菲二维码编码方案.md)）
- 一衣一码，返工/换色必须新建码，旧码作废
- 计件流水 append-only，红冲补录（[ADR-0005](./0005-计件流水不可变与红冲机制.md)）
- 整件口径（[09 §4.2](./../docs/09-领域术语与编码规则.md)）

---

## 决策

**我们决定：打菲的粒度是「尺码 + 手序号」，每一手一个码；`bundle_no` 内嵌尺码码与手序号；`bundles.bundle_qty` 存该手件数；扫码默认按整手计件，允许手写不超过该手件数。**

### 1. `bundle_no` 格式（**内嵌手序号**）

```
{打菲单号}-{尺码码}{手序号 2 位}-{件序号 4 位}

示例：
BD-20261018-000031-XL02-0001     ← XL 的第 2 手，件序号 0001（默认一码一手）
BD-20261018-000031-XL02-0002     ← 同一尺码第 2 手的第 2 件（将来要拆"一手多码"时用）
BD-20261018-000031-L01-0001      ← L 的第 1 手
```

| 段 | 宽度 | 说明 |
| --- | --- | --- |
| 打菲单号 | `BD-YYYYMMDD-NNNNNN` | 同 09 §2.1 |
| 尺码码 + 手序号 | 2 位码 + 2 位序号 | `XL02` = XL 尺码第 2 手；手序号在**同一单 + 同一尺码内**从 1 递增 |
| 件序号 | 4 位 | 同一手内的件序号；**一码一手时恒为 `0001`**；预留"一手拆多码"扩展 |

**唯一约束**：`UNIQUE (doc_id, color_code, size_code, hands)` —— 同一单同一尺码同一手号只能有一手。这从库层面保证"XL 2 手"不会重复成两个第 2 手。

### 2. `bundles` 表关键列（修订）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `bundle_no` | varchar(64) UNIQUE | 见上格式 |
| **`hands`** | integer NOT NULL | **手序号**（同尺码内从 1 开始） |
| `size_code` | varchar(32) NOT NULL | 尺码 |
| `color_code` | varchar(32) NOT NULL | 颜色（一码一色） |
| **`bundle_qty`** | numeric(14,3) NOT NULL | **该手件数**，来自裁剪尺码明细的 `output_qty / hands`，扫码即知 |
| **`cutting_size_line_id`** | uuid NOT NULL | 引用裁剪的尺码明细行（权威件数来源） |
| **`counted_qty`** | numeric(14,3) NOT NULL DEFAULT 0 | 已计件数量（`0 ≤ counted_qty ≤ bundle_qty`） |
| **`counted_by`** | uuid | 计件员工（一人一扫，**一码一员工**） |
| **`counted_at`** | timestamptz | 计件时间 |
| `status` | bundle_status | `ACTIVE` / `VOIDED` |
| `qr_content` | varchar(64) | = `bundle_no`（ADR-0004 不变） |

### 3. 裁剪 → 打菲 的衔接

```
裁剪（按 ADR-0014 展开到尺码明细）
  XL: hands=2, qty_per_hand=60  →  output_qty = 120 件
       ↓ 打菲按手拆分（hands=2 → 2 个码）
  bundle 1: XL01  bundle_qty = 60   ← 员工 王海涛
  bundle 2: XL02  bundle_qty = 60   ← 员工 陈美玲
```

| 规则 | 说明 |
| --- | --- |
| `bundle_qty = floor(裁剪该尺码 output_qty / 裁剪该尺码 hands)` | 每手件数 |
| 余数处理 | 若 `output_qty` 除不尽（`120 / 3 = 40` 整除没问题；`100 / 3 = 33.33`），**余下不足一件进 `balance_qty`**（09 §4.2） |
| 打菲码数必须等于裁剪手数 | 少打 → 提交时校验报 `30002`；多打 → 报 `31004` |
| 一码 = 一个责任单元 | `counted_by` 只允许一个员工；第二个员工扫同一码 → `32001`（该手已由 XXX 完成） |

### 4. 计件规则（扫码得件数 + 支持部分生产）

```
扫码 → 事务内 SELECT ... FOR UPDATE 锁 bundle 行
  ├─ bundle 不存在                    → 31001
  ├─ status = VOIDED                  → 31002
  ├─ counted_at 非空                  → 32001（提示已由 XXX 于 HH:MM 计过）
  └─ 正常：
     default_qty = bundle.bundle_qty              ← 扫码即知这手数量
     qty = 用户手写值（可选），默认取 default_qty
     校验 0 < qty ≤ bundle.bundle_qty            ← 超产拒绝 → 32006
     qty 必须是整数（CHECK ck_piecework_logs_whole）
     写 piecework_logs（qty = qty，bundle_id 引用）
     回写 bundle.counted_qty / counted_by / counted_at
```

| 场景 | 结果 |
| --- | --- |
| 员工 A 一个人做完整手 | 扫一次 → `qty = 60`，`counted_by = A` |
| 员工 A 只做了一半 | 扫一次手写 `qty = 28` → 允许（`28 ≤ 60`） |
| 手写 `qty = 88` | 拒绝 `32006`（超出该手件数）——**超产必须先追加手**（新裁剪 + 新打菲），不能靠改数量 |
| 员工 B 扫已被 A 计过的码 | 拒绝 `32001`，提示 A 的姓名与时间 |
| 整手只做了一半，剩下的怎么办 | 剩余部分不改码；如需补做，走**红冲 + 补录**（ADR-0005），或追加新手 |

### 5. 标签改动

| 标签上要印 | 说明 |
| --- | --- |
| 款号 / 颜色 / 尺码 | 同前 |
| **第 N 手 / 共 M 手** | ← **新增**，多员工分工时肉眼可辨 |
| **件数（该手）** | ← **新增**，与扫码结果一致，避免扫码核对 |
| `bundle_no` | 等宽字体完整显示 + Code128 |
| 二维码 | 内容 = `bundle_no` 纯文本 |

### 6. 工位机页面改动

| 改动 | 说明 |
| --- | --- |
| 计数单位 | 从「件」改为「**手**」为主计数，旁边并列「件」 |
| 扫码反馈 | `✓ 打边 第 1 手 · 60 件 · +¥25.20` |
| 部分生产 | 弹出「这手只做完了 N 件？」→ 可输入实际件数（≤ 该手件数） |
| 重复码 | 提示「XL 第 1 手，陈美玲 09:44 已计 60 件」 |

## 理由

| # | 理由 |
| --- | --- |
| 1 | **手是车间的自然工作单元**。裁床排版按手分配，车工拿到的是"一只手"，不是"60 件散件"。 |
| 2 | **手序号必须在码里**。业务方明确"XL 2 手打两张就重复" —— 不带序号，工位机上无法区分第 1 手和第 2 手，追溯全乱。 |
| 3 | **一码一员工解决"谁做的"**。业务方原话："多个员工生产就不知道谁做工"。责任单元就是手。 |
| 4 | **数量存库不入码**。手数可能被更正（追加手、改每手件数），码里写死数量会导致旧码失效、必须重打。查库得到则改数不影响码。 |
| 5 | **部分生产是常态**（返修、缺料、赶工）。硬要求整手会逼工人刷量或浪费码；允许手写 `≤ bundle_qty` 兼顾真实与管控。 |
| 6 | **禁止超产**（`qty > bundle_qty` 拒绝）。否则会出现"一只手做了 88 件"的账实不符，裁剪结转闭环（INV-6）被打穿。要超产必须追加手。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 维持 ADR-0004「一码一件」 | ✅ | 一码一件意味着 XL 2 手 120 件要打 120 个码，标签成本高；且责任单元太细，工人扫码 120 次 |
| `bundle_no` 不带手序号（保持全局 7 位） | ✅ | 业务方明确要求"每手要有编号"。虽然全局序号技术上唯一，但人看不出是第几手，工位机和标签都不可读 |
| 数量写进二维码（`bundle_no,60`） | ✅ | 业务方明确"不带，查库得到"；且改每手件数会导致旧码失效 |
| 一手多码（一件一码），只在码上标手号 | ✅ | 回到 ADR-0004 的老问题：扫码次数多；且部分生产时无法"整手确认" |
| 一码可被多员工各扫一次（累加计件） | ✅ | 破坏"谁做的"可追溯性；业务方明确要能区分 |
| 允许 `qty > bundle_qty`（超产） | ✅ | 打穿 INV-6 结转闭环；且无法解释"这手为什么多了 28 件" |
| 部分生产用新码表示（做 28 件就发 28 件的码） | ✅ | 码数膨胀（120 件 → 拆成 5 个码），且剩余 32 件怎么处理变复杂 |
| 码里带 `size+hands` 但不带件数 | ✅ | **采纳**：手号给人看，件数查库 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 码数与手数一致（6 手 = 6 码），标签成本降 90%；责任单元清晰；扫码即知件数；部分生产可真实记录 |
| 负面/代价 | `bundles` 增 5 列（`hands`/`bundle_qty`/`cutting_size_line_id`/`counted_qty`/`counted_by`）；`bundle_no` 格式变更（**ADR-0004 格式作废**）；标签重新设计；工位机页面改造 |
| 风险 | ① 手序号重复 → `UNIQUE(doc_id, color_code, size_code, hands)` 兜底 ② 超产绕过 → `32006` + DB CHECK `counted_qty ≤ bundle_qty` ③ 部分生产后剩余量无人管 → 报表"未计件手数"清单 ④ 改每手件数后旧 `bundle_qty` 不一致 → 改数必须同步 `bundles.bundle_qty`，且已计件的码不可改 |
| 迁移路径 | `bundles` 增列；`bundle_no` 生成器重写；阶段一表为空，无数据迁移 |
| 回滚方式 | 列可逆；码格式回滚会导致旧码不可识别，需配合停用 |
| 对规范的影响 | 04 新增 §7.0 `bundles` 表与扫码规则；05 §4 新增 `31004`（码数≠手数）/`31005`（手号重复）/`31006`（已计件不可改）/`32006`（超产）；08 §2.2 打菲审核副作用 + §2.3 计件前置校验；09 §1.4「一扎=1件」作废、§2.4 码格式更新；09 §4 关闭 Q-C09 |
| 对测试的影响 | **必测**：① 1:2:2:1 → 6 手 = 6 码，手号 L01/XL01/XL02/XXL01/XXL02/3XL01 ② 同尺码多手不重复 ③ 扫码得该手件数 ④ 手写 `qty < bundle_qty` 允许 ⑤ 手写 `qty > bundle_qty` 报 `31004` ⑥ 同码第二人扫报 `32001` ⑦ 码数 ≠ 裁剪手数报 `30002`/`31004` ⑧ 部分生产后剩余量可见 ⑨ 改每手件数同步 `bundle_qty` 且已计件码不可改 |
| **下游影响** | `piecework_logs.bundle_id`（uuid）替代仅靠 `bundle_no`；幂等键从"同码可重复扫"变为"一码一次"（`counted_at IS NULL` 判定）；工位机计数单位改「手」 |

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 码数 = 手数 | 100% | 打菲单审核时校验 |
| 一码一员工 | 100% | `counted_by` 非空率与唯一性 |
| 超产次数 | 0 | `31004` 拦截 + 报表核对 |
| 扫码反馈时延 | P95 < 150ms | 同 04-计件要求 |
| 未计件手数可见 | 是 | "未计件手清单"报表 |
