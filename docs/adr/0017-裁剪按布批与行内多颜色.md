# ADR-0017：裁剪按「布批」组织单据，行内支持多颜色

## 背景

### 业务方 2026-10-01 原话

> **裁剪有时候一床多个颜色。**

### 问题

现有结构（ADR-0013 / 0014）：
```
cutting_orders → cutting_order_lines（款号 + 色组）→ cutting_order_colors（颜色）→ 尺码明细
```
即：**裁剪行 = 款号 + 一个色组**，颜色挂在行下。

但真实裁剪现场是：
1. **耗料是布的属性** —— 一匹布（一个缸号 `DY-2609-01`）裁什么，与布本身有关，与裁几个颜色无关
2. **一床布可裁多个颜色** —— 铺布时红布和黑布可以拼在一个裁床上按各自比例裁，**省布**（拼接对花）
3. 上一轮 ADR-0012 已确立「批次唯一键 = `仓库 + 物料 + 缸号 + 匹号`」，缸号是**批次身份**，天然属于布

### 痛点

| # | 痛点 | 后果 |
| --- | --- | --- |
| 1 | 行绑色组 → 一行只能一个颜色组 | **一床多颜色做不了**，必须拆成 3 张单、重复录同一缸布的耗料 |
| 2 | 耗料记在行上但行绑颜色 | 同一缸布被两个颜色用时，耗料归属说不清 |
| 3 | 出库选批按行 | 一行一个缸号，拆单后同一缸被多个单据占用，对账困难 |

---

## 决策

**我们决定：裁剪单的行 = 「款号 + 布批（缸号 + 匹号）」；耗料记在行（布批）级；颜色下沉为行的第二层明细，各颜色的尺码比例与手数独立计算。**

### 1. 三层结构

```
cutting_orders                       裁剪单（按日期 / 车间 / 款号）
└── cutting_order_lines               ★ 行 = 款号 + 布批（dye_lot_no + bolt_no + 门幅 + 重量 + 耗料）
    └── cutting_order_line_colors     ★ 颜色（一床可多个）+ entry_mode + ratio_snapshot
        └── cutting_order_size_lines  尺码 + hands + qty_per_hand + output_qty + hands_seq
```

| 层 | 表达什么 | 关键字段 |
| --- | --- | --- |
| `cutting_order_lines`（行） | **一匹布裁这个款** | `style_no`、`dye_lot_no`、`bolt_no`、`width_cm`、`weight_kg`、`fabric_qty`（耗料）、`output_qty` 汇总、`balance_qty` |
| `cutting_order_line_colors` | **这匹布裁哪些颜色** | `color_code`、`entry_mode`（MASTER/UNIFORM/MANUAL）、`qty_per_hand`、`uniform_qty`、`ratio_snapshot` |
| `cutting_order_size_lines` | **这个颜色各尺码几手几件** | `size_code`、`hands`、`qty_per_hand`、`output_qty`、`hands_seq` |

### 2. 耗料归行，出数归颜色

```
fabric_qty（耗料，米）记在【行】          ← 布的属性，与颜色无关
output_qty（出数，件）记在【尺码明细】     ← 颜色的属性
```

| 校验 | 规则 |
| --- | --- |
| 行耗料下限 | `行 fabric_qty ≥ Σ(该行各颜色的 Σ(尺码 output_qty × BOM.单件用量)) + 该行损耗量` |
| 余量归行 | `行 balance_qty = 行 output_qty − Σ(颜色尺码 output_qty)`；负数 → 报错（耗料不足） |
| 取整 | 行级 `output_qty = floor(可裁件数)`（09 §4.2 整件口径） |

> 这样避免循环计算：耗料不再从出数反推（ADR-0013 已把「按 BOM 反算件数」废掉），耗料由**铺布时按实际排版**录入，出数由比例算出。两者独立，用校验约束一致性。

### 3. 一床多颜色的实际写法

```
裁剪单 CT-20261018-000150
款号 HB-2026-0018 · 裁床组 · 2026-10-18
┌───────────────────────────────────────────────────────────────┐
│ 行1 · 缸号 DY-2609-01 · 匹 B-2610-001 · 门幅 152 · 重 61.0kg    │
│      耗料 96.0 米（按 6 手铺布 152 幅宽 × 0.63 幅利用率 算出）      │
│   ├─ 颜色 WHT 本白　[MASTER] 每手 60 件                        │
│   │    L 1手→60　XL 2手→120　XXL 2手→120　3XL 1手→60 = 360 件    │
│   └─ 颜色 BLK 黑　[MASTER] 每手 50 件                          │
│        L 1手→50　XL 2手→100　XXL 2手→100 = 250 件                │
│ 行1 小计：610 件，耗料 96.0 米                                  │
├───────────────────────────────────────────────────────────────┤
│ 行2 · 缸号 DY-2609-02 · 匹 B-2610-002 · 门幅 150.5 · 重 29.4kg  │
│      耗料 31.5 米                                                │
│   └─ 颜色 WHT 本白　[MANUAL] 自定义明细                          │
│        XL 2手×60=120　XL 1手×30=30　XXL 2手×60=120 = 270 件        │
└───────────────────────────────────────────────────────────────┘
本单合计：880 件，耗料 127.5 米
```

### 4. 下游衔接（配合 ADR-0016）

打菲单的行 = `款号 + 颜色 + 尺码 + 手序号`，每手一个码，且必须引用 **`cutting_order_size_line_id`**（不是缸号行）：

```
cutting_order_size_line (BLK, XL, hands=2, qty_per_hand=50, output_qty=100)
  ↓ 打菲按手拆
bundle 1: BD-…-XL01-0001  bundle_qty=50  ← 员工 王海涛
bundle 2: BD-…-XL02-0001  bundle_qty=50  ← 员工 陈美玲
```

| 规则 | 说明 |
| --- | --- |
| 可打菲件数 | `Σ(该尺码所有布批行的 output_qty)`；**一码一手** |
| 归属布批 | 一个手来自**一个布批行**（同尺码多布批时，逐布批分配手数；多出的合并到最后一批） |
| 耗料 | 由**布批行**出库领料（`stock_ledger_lines` 记缸号 + 匹号），与颜色无关 |

### 5. 校验清单

| # | 校验 | 失败 |
| --- | --- | --- |
| 1 | 一行的所有颜色，其尺码比例合计各自独立（不同颜色可不同） | `20006`（某色完全无比例） |
| 2 | 行耗料 ≥ Σ(颜色尺码 output_qty × BOM.usage) + 损耗 | `30002` |
| 3 | 缸号 + 匹号必须在本厂可用库存中，且门幅满足铺布要求 | `40001` / 门幅警告 |
| 4 | 行 `output_qty` = `floor(可裁件数)` | 整件口径，不满足则报错 |
| 5 | 颜色必须是该款已定义的颜色，且尺码在该款的尺码集合内 | `20007` |

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **耗料是布的属性，出数是颜色的属性**。这才是物理事实，也是库存管理的自然边界（批次 = 缸号 + 匹号，ADR-0012）。 |
| 2 | **一床多颜色是真实的省布手段**。不同颜色拼接裁边，能省 5-10% 布。原结构直接禁止了这种做法。 |
| 3 | **与库存选批一致**。裁剪出库按缸号选批（ADR-0011），行 = 布批时，行与批次一一对应，对账简单。 |
| 4 | **避免耗料被重复录**。原结构拆单后同一缸布的耗料要录 N 次，容易不一致。 |
| 5 | **耗料与出数解耦后不再循环**。耗料按排版录入（正向），出数按比例算出（正向），用 CHECK 校验一致性。 |
| 6 | **保留 ADR-0014 的三种录入模式**，只是挂载层从"行"变成"颜色" —— 粒度更细，正好符合"一色特殊不影响另一色"的现实。 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 维持"行 = 款号 + 色组"，一行只能一色 | ✅ | 一床多颜色做不了；拆单导致同缸耗料重复录 |
| 行 = 款号 + 缸号，但颜色直接平铺在明细层（不分组） | ✅ | 分组丢失"每个颜色一套录入模式与比例"的语义；比例校验无法按色聚合 |
| 引入"床"实体，行挂床下 | ✅ | 多一层间接，床与行的边界模糊（一床可能多布批）；行=布批已够 |
| 耗料按颜色分摊 | ✅ | 循环依赖（算件数要先知道耗料，算耗料要先知道件数）；改为行级录入 + CHECK 校验 |
| 同一缸布可裁多个款号 | ✅ | **业务上不成立**（一个缸的颜色对某个款有效，对另一个款通常无效）。行仍绑款号 |
| 裁剪单直接一行一颜色，多颜色就是多行 | ✅ | 就是原结构，无法表达"这匹布被两色共用、需按比例分配件数"的语义 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 支持一床多颜色；耗料一次录入；与库存批次天然对齐；录入模式按颜色独立 |
| 负面/代价 | 三层结构比两层深；界面需要"行 → 颜色 → 尺码"的可折叠明细；导入模板变复杂 |
| 风险 | ① 同一缸多行导致库存行重复扣 → 选批用 `FOR UPDATE` + 条件 UPDATE ② 行耗料与出数不一致 → 提交与审核双重校验 ③ 颜色比例漏配 → `20006` ④ 一行多色导致打菲归属歧义 → 打菲必须引用 `cutting_order_size_line_id` |
| 迁移路径 | `cutting_order_lines` 增 `dye_lot_no`/`bolt_no`/`width_cm`/`weight_kg`；`cutting_order_colors` 改名 `cutting_order_line_colors` 并增 `doc_id→line_id` 外键；`cutting_order_lines` 保留为尺码明细并改名 `cutting_order_size_lines`。阶段一表为空，纯结构调整 |
| 回滚方式 | 结构变更可逆（表未上线） |
| 对规范的影响 | 04 §7.7 层级改为三层（§7.7.2 行=布批 / §7.7.3 行颜色 / §7.7.4 尺码明细 / §7.7.5 三种录入模式）；09 §1.5b 补布批与颜色层；08 §2.1 裁剪审核副作用重排 |
| 对测试的影响 | **必测**：① 一行含 2 颜色各按比例出数（360 + 250 = 610）② 行耗料 ≥ Σ颜色耗料校验 ③ 余量归行 ④ 行耗料不足报 `30002` ⑤ 同缸布可被多行占用（扣减正确）⑥ 一色 MANAGER 另一色 MASTER（模式混用）⑦ 打菲引用尺码明细行且件数正确 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 一床多颜色可录入 | 是 | 手工造单验证 |
| 耗料录入次数 | 同缸同匹只录一次 | 行唯一性校验 |
| 耗料一致性 | 100% | `行耗料 ≥ Σ颜色耗料 + 损耗` 校验脚本 |
| 库存对账 | 恒 0 行 | `v_stock_reconciliation` |
