## 背景

要解决什么问题？为什么现在必须做？（写事实与约束，不写方案）

- 现状一：04 §6.1 规定「生产库表 `users/roles/permissions/accounts/migrations` 禁止硬删；**其余表只允许软删**」，并给出理由「破坏外键完整性，且误删不可恢复」。
- 现状二：04 §6.2.1 规定生产应用账号 `erp_app` 的授权是 `SELECT, INSERT, UPDATE`，并明确写「**生产库不给应用账号任何硬删能力**」「应用账号天然不具备 DELETE/TRUNCATE/DROP」。
- 现状三：业务方 2026-10-01 决策（modules/01 §2 R27、§3.6.2、04 §7.4 规则前两条）——**未被任何单据引用的颜色 / 尺码 / 码表允许物理删除（真删，不留残渣）；已被引用的只能停用（`20003`）**，`is_builtin = true` 不是删除判据。
- 痛点：以上三条**互相矛盾**。按现状二实现，`DELETE /api/v1/colors/{color_code}` 在生产库会直接报 `permission denied for table colors`；按现状一实现，则业务方明确要的「删掉就是不要了」做不到，只能软删，而软删会让候选下拉、码表选择、旧单据回显全部带上"已删除"的历史包袱（这正是业务方要避免的）。
- 痛点二（同一族问题）：04 §7.4 规则第 4 条写「`seed_baseline` 是一次性初始化，删掉内置行后**不会自动回来**」，但规则第 1 条要求用 `ON CONFLICT DO NOTHING` —— 该语义的直接后果是「键不存在就插回」，**真删的内置行会被 seed 悄悄恢复**。modules/01 §5.2 幂等规则第 4 条与 §7 并发表已明确指出这个矛盾，§12 待登记清单 ① 标为「需规范回写或技术决策」，至今未决。
- 硬约束：
  - 生产是 2C/12G 单机 compose（ADR-0006），权限是**唯一**的硬边界 —— 代码层「禁止硬删」只能靠自觉，DB 层 REVOKE 才能真正兜住（04 §6.2.1 的立意）。
  - `document_logs` 必须 `REVOKE UPDATE, DELETE`（04 §6.2.1 + §7.9），日志不可篡改是审计底线。
  - AGENTS.md §2.1：禁止物理删除业务数据；本 ADR 处理的是**主数据字典**，不触碰业务数据表。

---

## 决策

**我们决定：把「可物理删除」的白名单收敛到四张字典表，按表白名单授予 `DELETE`，其余表继续禁止硬删；内置行真删时以 `document_logs` 留痕为「墓碑」，`seed_baseline` 遇墓碑跳过。**

具体约定：

### 1. 授权白名单（唯一硬删入口）

```sql
-- 迁移里显式声明"可硬删的表"，只有这四张
GRANT SELECT, INSERT, UPDATE, DELETE ON
    colors, sizes, size_groups, size_group_items TO erp_app;

-- 其余全部业务表仍不授 DELETE（04 §6.2.1 的 GRANT 保持不变）
-- 审计表仍然最严
REVOKE UPDATE, DELETE ON document_logs FROM erp_app;
```

| 表 | 是否可物理删除 | 理由 |
| --- | --- | --- |
| `colors` / `sizes` / `size_groups` / `size_group_items` | ✅ 可（且仅当引用计数 = 0） | 主数据字典，被业务方明确要求"删掉就是不要了"；被引用时由引用计数与 `20003` 保护 |
| `users` / `roles` / `permissions` | ❌ 永远不可 | 04 §6.1 硬删禁令表 |
| `document_logs` / `auth_login_logs` | ❌ 永远不可 | append-only 审计 |
| 其余全部业务表（单据、台账、流水、库存、工资、凭证） | ❌ 只软删 | 04 §6.1 + AGENTS.md §2.1 |

### 2. 删除必须是「条件删除」，禁止先查后删

```sql
DELETE FROM sizes
WHERE id = :id
  AND NOT EXISTS (SELECT 1 FROM style_sizes          WHERE size_id = :id)
  AND NOT EXISTS (SELECT 1 FROM size_group_items     WHERE size_id = :id)
  AND NOT EXISTS (SELECT 1 FROM style_color_size_ratios WHERE size_code = :size_code);
-- rowcount = 0  →  20003（details.ref_count + details.references[]）
```

引用方（建款号 / 建款号尺码 / 建比例行）在 service 内对字典行 `SELECT ... FOR SHARE`，与删除串行化 —— 保证**绝不出现"尺码被删但款号里还挂着"的悬空引用**（modules/01 §7 已定口径，本 ADR 只是补上权限前提）。

`size_groups` 真删时**级联删除其 `size_group_items`**，响应回传级联条数并写 `document_logs`。关联表随主表删除，归类为「主数据字典的级联」，不属于 04 §6.1 禁止的业务数据硬删。

### 3. 内置行真删 = 留墓碑；seed 遇墓碑跳过

```
用户 DELETE /colors/WHT（未被引用）
  └─> 同一事务内：
        1) 条件 DELETE 该行
        2) INSERT document_logs (doc_type='Color', doc_id=<行 id>,
                                 doc_no='WHT', action='DELETE',
                                 operator_id/operator_name=当前用户,
                                 changed_fields={"builtin": true})
```

`seed_baseline` 与 `restore_builtin` 的插入前**先查墓碑**：

```sql
-- 伪代码：ON CONFLICT DO NOTHING 之前多一步判断
INSERT INTO colors (color_code, name, is_builtin, ...)
SELECT * FROM jsonb_to_recordset(:seed_rows) AS t(color_code, name, ...)
WHERE NOT EXISTS (                      -- ★ 新增：被真删过的内置项不复活
    SELECT 1 FROM document_logs
    WHERE doc_type = 'Color' AND doc_no = t.color_code AND action = 'DELETE'
)
ON CONFLICT (color_code) DO NOTHING;
```

| 命令 | 用途 | 触发时机 |
| --- | --- | --- |
| `python -m app.cli.seed_baseline` | 首次部署 / 新增内置项版本 | 建库后首次；**不删除、不覆盖用户改动**（04 §7.4） |
| `python -m app.cli.restore_builtin` | 用户在界面上点「恢复内置库」后显式执行 | 补回被真删的内置行（同样跳过墓碑？还是补回？——见下） |

> ✅ **墓碑的解除（已定，原为待定细节）**：`restore_builtin` **清除墓碑并写入反向记录** —— 在 `document_logs` 追加 `action='RESTORE'`（`doc_type`/`doc_no` 同原 DELETE 行），seed 的墓碑判断以「存在 `DELETE` 且不存在更新的 `RESTORE`」为准。这样两条命令职责不重叠：`seed_baseline` 永不复活用户删掉的行，`restore_builtin` 是用户显式表达的「我要它回来」。
> 判定 SQL：
> ```sql
> -- 有墓碑且未被恢复 → 跳过
> EXISTS (SELECT 1 FROM document_logs
>         WHERE doc_type = 'Color' AND doc_no = t.color_code AND action = 'DELETE')
> AND NOT EXISTS (
>     SELECT 1 FROM document_logs d
>     WHERE d.doc_type = 'Color' AND d.doc_no = t.color_code AND d.action = 'RESTORE'
>       AND d.created_at > (SELECT max(created_at) FROM document_logs
>                            WHERE doc_type='Color' AND doc_no=t.color_code AND action='DELETE'))
> ```

## 理由

为什么选这个方案？逐条对应背景里的痛点：

| # | 理由 |
| --- | --- |
| 1 | **满足业务方明确决策**：R27「未被引用的字典项可真删」得以落地，不需要业务方再改口 |
| 2 | **保住 04 §6.2.1 的立意**：权限边界仍然由 DB 保证 —— 白名单之外的所有表，`erp_app` 连 `DELETE` 语句都执行不了，不依赖任何代码自觉 |
| 3 | **白名单是最小攻击面**：4 张表都是**无外键指向业务数据的纯主数据表**（唯一的出向 FK 是 `size_group_items → sizes/size_groups`，同在白名单内），删掉它们不可能破坏任何业务数据。风险与收益之比明显优于"给 `erp_app` 全库 DELETE" |
| 4 | **墓碑方案让"真删"与"seed 不复活"同时成立**：04 §7.4 的两条规则不再互斥；墓碑存在 `document_logs` 里，而该表 `REVOKE UPDATE, DELETE`，**墓碑不可被篡改或清理**（除非 DBA 手工操作并留痕），语义天然可靠 |
| 5 | **不复用软删**（见备选方案 ②）：软删需要所有候选接口、报表、单据回显处处加 `deleted_at IS NULL` 判断，漏一处就是脏数据；而且用户看到的仍是"已删除的 WHT 还在列表里"，与业务诉求相反 |
| 6 | **不需要引入存储过程或额外角色**（见备选方案 ③）：迁移与运维复杂度不增加，普通 GRANT 就够，2C/12G 单机 compose 场景下更简单可靠 |
| 7 | **保留"停用"作为有引用时的唯一出路**：业务方原本的诉求（防误删）通过引用计数 + `20003` + 前端二次确认 + 必填原因（停用）完整保留 |

## 备选方案与否决原因

**必须写**。否则未来 AI 会重复评估同一批方案。

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| ① 给 `erp_app` 全库 `DELETE`，靠代码保证只删字典 | ✅ | 与 04 §6.2.1「生产库不给应用账号任何硬删能力」直接对立；一次代码 bug 或 SQL 注入就能删掉计件流水、库存台账、凭证 —— 而 `piecework_logs` 是 INV-2 的审计链，删掉不可恢复 |
| ② 字典项一律软删（放弃 R27 的"真删"） | ✅ | 与业务方 2026-10-01 决策冲突；且软删会让候选下拉、旧单据回显、码表带出处处要判 `deleted_at`，漏判即脏数据；用户明确"删掉就是不要了" |
| ③ 用 `SECURITY DEFINER` 存储过程包办字典删除，`erp_app` 只有 `EXECUTE` | ✅ | 增加一个高权限函数 = 增加一个可被 SQL 注入利用的入口（函数体若拼接不当即可提权）；且函数内做引用计数判断时无法复用 service 层的 `apply_data_scope` 与 `document_logs` 写入逻辑，事务与审计链会被割裂。收益（收敛权限）不足以抵偿复杂度 |
| ④ 字典项移出 `public` schema，单独 schema + 单独账号 | ✅ | 04 §1 明确「统一 `public`，不跨 schema（模块多但库单，跨 schema 反而增加运维复杂度）」；且 `document_logs` 仍需跨 schema 写入，审计链反而断裂 |
| ⑤ 内置行不做墓碑，改为「内置行一律禁止真删」（回到第三批前口径） | ✅ | modules/01 §2 R27 与 04 §7.4 规则第 5 条已明确**作废**该口径（业务方确认"可以增删改"），复活它等于推翻已闭环的业务决策 |
| ⑥ 内置行真删改走 `deleted_at` 软删（墓碑即软删位） | ✅ | 与业务方"不留残渣"的诉求冲突；且内置行真删后仍占 `uq_sizes_code` 唯一键位 —— 重新建同名尺码会被唯一索引拦住，`restore_builtin` 与用户自建会互相打架。墓碑放在 `document_logs` 不占业务键位 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | R27 可落地；权限边界不破；`document_logs` 顺带成为字典删除的不可篡改审计源 |
| 负面/代价 | `erp_app` 多了 4 张表的 `DELETE` 权限（攻击面从 0 变 4 张纯主数据表）；`seed_baseline` 需要多一次 `document_logs` 查询（可忽略）；规范要改 3 处 |
| 风险 | ① 条件 DELETE 写错（如漏了某个引用表）→ 悬空引用。**对策**：引用表清单与 modules/01 §2 R27 第 ③ 条逐项对齐，并写"删除后全库外键巡检"SQL 进 `tests/integration/`（每次迁移后跑）。② 墓碑表随业务增长变大 → 只影响 `document_logs` 的既有增长趋势，不新增负担。③ 有人为了"方便"把白名单扩大到全部主数据表 → **对策**：白名单以常量列表写在迁移里并在 §6.2.1 登记，新增必须写 ADR |
| 迁移路径 | 存量数据零影响（尚无生产数据）。步骤：① 修订 04 §6.1/§6.2.1/§7.4 与 modules/01 §5.2/§7 → ② 迁移 `0003` 里执行四条 `GRANT DELETE` → ③ 实现 DELETE 端点（条件 DELETE + 墓碑） → ④ `seed_baseline` 加墓碑判断 → ⑤ 补测试。**无需停机** |
| 回滚方式 | `REVOKE DELETE ON colors, sizes, size_groups, size_group_items FROM erp_app;` + `alembic downgrade` 回退 `0003`（表本身可重建，无数据损失）。已真删的字典行**不可恢复**，但其墓碑在 `document_logs` 里可查（内容即 seed 常量里的原始值） |
| 对规范的影响 | 04 §6.1 / §6.2.1 / §7.4（3 处）；modules/01 §5.2 / §7 / §12。**不新增错误码**（用已登记的 `20003`）、**不新增权限点**（用已登记的 `base:delete`） |
| 对测试的影响 | 新增必测：TC-B03（两分支删除）、TC-B21（真删内置行 → seed 不复活）、TC-B22（真删内置行 → `restore_builtin` 恢复）、TC-B23（`size_groups` 真删级联明细）、CC-3（删 vs 引用真并发）、TC-B24（`erp_app` 对非白名单表 `DELETE` 报 `permission denied`）、TC-B25（`document_logs` 的 `UPDATE`/`DELETE` 被拒） |

## 验证方式

上线后用什么指标确认这个决策是对的？

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 非白名单表的物理删除尝试 | **0 次成功** | 集成测试 `TC-B24` + 季度权限审计（11 §8） |
| 悬空引用（字典被删但仍被引用） | **0 行** | `tests/integration/test_no_dangling_refs.py`：每次迁移后全库外键巡检 + 04 §7.2.4 同款对账查询 |
| 被真删的内置行复活 | **0 次** | `document_logs` 中有 `action='DELETE'` 的内置键，与 `colors`/`sizes`/`size_group_items` 中 `is_builtin=true` 的行取交集，恒为空 |
| 删除接口的 `20003` 命中率 | 与用户预期一致（误删尝试应 > 0，说明引用计数提示有效） | `document_logs` 统计 `action='DELETE'` 的 `reason` 分布 |
| seed 幂等性 | 连跑 3 次行数与内容零变化 | `TC-A01`（CI 每次跑） |
