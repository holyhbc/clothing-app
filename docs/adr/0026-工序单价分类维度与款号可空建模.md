---

## 背景

要解决什么问题？为什么现在必须做？

- 现状一：ADR-0009（`Accepted`，业务负责人决策）确定「单价维度 = **款号 × 工序 × 生效区间**」，明确否掉「工序 + 技能等级」二级定价。04 §7.8.3 与 modules/01 §3.4 落地的 DDL 是：
  ```sql
  operation_rates (
      style_no       varchar(32) NOT NULL,   -- 款号
      operation_no   varchar(16) NOT NULL,
      effective_from date NOT NULL,
      effective_to   date,
      unit_price     numeric(12,6) NOT NULL,
      ...
  );
  ```
  取价 SQL 也是单档：`WHERE style_no=? AND operation_no=? AND effective_from<=:d AND (effective_to IS NULL OR effective_to>:d) ORDER BY effective_from DESC LIMIT 1`。
- 现状二：ADR-0020（`Accepted`，2026-10-01，业务负责人决策）新增商品分类，并要求「按分类算裁剪工资」，给出**三档取价优先级**：`款号专用价 > 分类+工序专用价 > 工序通用价`；同时要求 `operation_rates` 增**可空** `product_category_id`，并要求流水落 `rate_source ∈ {STYLE, CATEGORY, OPERATION}`。04 §7.11、02-裁剪 C37、modules/01 §11.5 B-CAT-06 都已引用这一口径。
- 痛点（**三处硬矛盾**）：
  1. **第三档存不进去**：ADR-0020 要求支持「工序通用价」，它按定义没有款号；但 `operation_rates.style_no` 是 `NOT NULL`。**当前 DDL 无法表达 ADR-0020 的三档模型。**
  2. **同一个索引被定义成两个互不兼容的样子**：04 §7.8.3 建 `idx_operation_rates_lookup ON (style_no, operation_no, effective_from DESC)`；04 §7.11 又建同名索引 `ON (operation_id, style_no, product_category_id, effective_from)` —— 其中 **`operation_id` 这一列在表里根本不存在**（列名是 `operation_no`），且列序完全不同。同一项目里两个 DDL 片段不可能同时成立。
  3. **主体文档落后于 ADR**：modules/01 §3.4 的字段表、§6 的接口清单（`POST /operation-rates` 请求体无 `product_category_id`）、§8 的取价 SQL 与索引场景、§9 的错误码触发场景，**全部没有分类维度**。而 modules/01 §11.5 B-CAT-06 又引用了它 —— 模块文档自相矛盾。
- 为什么现在必须做：P0 的 T-BASE-002 要写 `operation_rates` 的迁移、`resolve` 取价接口与调价区间校验。**迁移一旦按 §7.8.3 建成就锁死了 `style_no NOT NULL`，P1 计件取价、P2 工资结算全部要跟着返工。** 这是整个系统金额口径的源头，不能带着矛盾往下走。

---

## 决策

**我们决定：`operation_rates` 的 `style_no` 与 `product_category_id` 均改为可空，用「三档 × 互斥约束 + `NULLS NOT DISTINCT` 唯一索引 + 单条 `ORDER BY` 取价 SQL」实现 ADR-0020 的三档模型，并把 04 §7.11 的错误索引定义作废、统一到 04 §7.8.3。**

### 1. 表结构（修订 04 §7.8.3）

```sql
CREATE TABLE operation_rates (
    id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    -- ★ 款号可空：NULL = 该价适用于「所有款号的该工序」（工序通用价）
    style_no            varchar(32) REFERENCES styles(style_no),
    operation_no        varchar(16) NOT NULL REFERENCES operations(operation_no),
    -- ★ 分类可空：NULL = 不限分类
    product_category_id uuid REFERENCES product_categories(id),
    effective_from      date NOT NULL,
    effective_to        date,
    unit_price          numeric(12,6) NOT NULL,
    reason              text,
    ...公共字段,
    -- ⚠️ 2026-10-03 修正：本行原文写的是
    --    CHECK (style_no IS NOT NULL OR product_category_id IS NOT NULL)
    --    （"至少指定款号或分类其中之一"），但它与**本文 §2 的档位 3 直接冲突** ——
    --    档位 3（工序通用价）的定义恰恰是 style_no 与 product_category_id 都为空，
    --    于是这条约束把第三档整个禁掉了（实测插入档位 3 报 ck_operation_rates_target 违例）。
    --    三档的真实形态是「两者恰好一个有值，或者都没有」，所以约束应该是
    --    「不能**同时**有值」。已登记 docs/12 §5 L-030。
    CONSTRAINT ck_operation_rates_target
        CHECK (NOT (style_no IS NOT NULL AND product_category_id IS NOT NULL)),
    CONSTRAINT ck_operation_rates_range
        CHECK (effective_to IS NULL OR effective_to > effective_from),
    CONSTRAINT ck_operation_rates_price CHECK (unit_price >= 0)
);

-- ★ 唯一索引：PG 默认认为 NULL 与 NULL 互不相等，会放过「重复的通用价」行，
--   必须用 NULLS NOT DISTINCT（PG 15+，本项目 PG 16，ADR-0002）
CREATE UNIQUE INDEX uq_operation_rates
    ON operation_rates (style_no, product_category_id, operation_no, effective_from)
    NULLS NOT DISTINCT;
```

> `NULLS NOT DISTINCT` 是本决策的**关键技术点**：没有它，「款号通用 + 分类 NULL + 同一工序 + 同一生效日」可以插入任意多行，取价变成不确定 —— 而计件金额错就是工资错（ADR-0020 已列风险）。

### 2. 三档定义与取价优先级（`rate_source` 的取值来源）

| 档位 | `rate_source` | 匹配条件 | 业务含义 |
| --- | --- | --- | --- |
| 1（最高） | `STYLE` | `style_no = :style_no` 且 `product_category_id IS NULL` | 这款这个工序的专用价 |
| 2 | `CATEGORY` | `style_no IS NULL` 且 `product_category_id = :category_id` | 这个分类下这个工序的通用价（分类取款号档案值，单据不可改） |
| 3（最低） | `OPERATION` | `style_no IS NULL` 且 `product_category_id IS NULL` | 全厂这个工序的通用价 |

取价 SQL（**唯一口径**，替换 04 §7.8.3 的单档 SQL；`:category_id` 来自 `JOIN styles.category_id`）：

```sql
SELECT unit_price, style_no, product_category_id, effective_from, effective_to
FROM operation_rates
WHERE operation_no = :operation_no
  AND effective_from <= :work_date
  AND (effective_to IS NULL OR effective_to > :work_date)
  AND (   (style_no = :style_no        AND product_category_id IS NULL)
       OR (style_no IS NULL           AND product_category_id = :category_id)
       OR (style_no IS NULL           AND product_category_id IS NULL) )
ORDER BY
  CASE WHEN style_no = :style_no THEN 0
       WHEN product_category_id = :category_id THEN 1
       ELSE 2 END,                       -- 档位优先
  effective_from DESC                     -- 同档位取最新生效的那一行
LIMIT 1;
-- 未命中 → 20004（该款号该工序未设置单价，或当日无生效单价）
```

`:category_id` 为 NULL（款号档案未设分类的极端情况）时，第 2 档自然不命中，只在 1、3 档中取。

### 3. 索引（作废 04 §7.11 的定义）

```sql
-- 作废：04 §7.11 的 ON (operation_id, style_no, product_category_id, effective_from)
--       （operation_id 列不存在，且与下面的索引同名）
-- 统一为：
CREATE INDEX idx_operation_rates_lookup
    ON operation_rates (operation_no, style_no, product_category_id, effective_from DESC);
-- 覆盖场景：取价（Q8）、区间重叠校验（Q9）、变更历史（Q10）——全部以 operation_no 起步
-- 部分索引：只索引当前有效的行？否 —— 查历史必须全量，故不设 WHERE
```

保留 modules/01 §8 已登记的另一个索引（**有查询场景支撑才建**）：
`idx_operation_rates_operation_current ON (operation_no, effective_from DESC) WHERE effective_to IS NULL`（计件员看"某工序当前价"概览）。

### 4. 档位的写入与调价规则

| 动作 | 规则 |
| --- | --- |
| 设价 | 必须显式指定档位：`style_no` 与 `product_category_id` 至少给一个（Schema 层校验 + DB CHECK 双保险）；`style_no` 给了就必须与款号档案的 `category_id` **不冲突**（即 `product_category_id` 要么不给，要么等于款号分类 —— 后者等价于档位 1，禁止，故**档位 1 必须 `product_category_id IS NULL`**） |
| 调价 | 沿用 ADR-0009 口径：**关闭旧区间（只改 `effective_to`）+ 插入新区间**，绝不 `UPDATE unit_price`；区间重叠校验按「同 `(style_no, product_category_id, operation_no)` 三元组」分组，组内不重叠；`reason` 必填（`10006`） |
| 区间锁 | 事务内对该三元组现有区间行 `SELECT ... FOR UPDATE` 排序加锁，防并发插出两条 `effective_to IS NULL`（modules/01 §7 已定口径，键从二元组扩为三元组） |
| 模板复制 | 复制**只搬档位 1（`STYLE`）与档位 3（`OPERATION`）**。档位 2（`CATEGORY`）**不复制** —— 它是"分类通用价"，属于全厂口径，不属于某一款的模板；复制会静默改写全厂工资口径 |
| 单价页展示 | 必须显示**当前生效价来源**（`rate_source`）+ 三档各自是否已设价（ADR-0020 "后果"列的强制要求） |
| 历史一致性 | 计件流水落库时快照 `unit_price` + `rate_source`（INV-3）；调价、模板复制、改分类**都不得回溯**已落库流水 |

### 5. 规范同步（必须同 PR 完成）

| 文档 | 修订内容 |
| --- | --- |

## 理由

| # | 理由 |
| --- | --- |
| 1 | **唯一能让 ADR-0020 与 ADR-0009 同时成立的方案**：ADR-0020 是 `Accepted` 的业务决策，不能悄悄降级（那是"放弃已写进 ADR 的方案"，12 §3.1 要求写新 ADR 标 `Superseded`）；而"款号可空"是让「工序通用价」这一档在数据模型里可表达的**最小**改动 —— 只放宽两个列的 `NOT NULL`，不新增任何表 |
| 2 | **`rate_source` 三值与三档一一对应**：ADR-0020 明确要求 `rate_source ∈ {STYLE, CATEGORY, OPERATION}` 且"事后可追溯是哪档价算的"。若按方案 (c) 只做两档，`OPERATION` 这个取值将永远为空，字段变成谎言 |
| 3 | **`NULLS NOT DISTINCT` 是必须的，不是锦上添花**：PG 默认 `UNIQUE` 把多个 NULL 视为互不相同，"同一天插入两条全厂通用价"不会被拦。计件金额与工资直接由此算出，取价不确定 = 工资不确定。用 `COALESCE` 表达式索引也能实现，但可读性差、且 `COALESCE(product_category_id, '0'::uuid)` 依赖哨兵值，PG 16 已原生支持 `NULLS NOT DISTINCT`，直接用 |
| 4 | **单条 `ORDER BY` 取价比"应用层按档位查三次"更好**：一条 SQL 保证"档位 + 生效日"两个维度一次性判定，天然避免多次往返之间被并发调价撕裂（读到档位 1 的旧值和档位 2 的新值这种组合）。`10 §5` 的并发纪律要求"必须有唯一约束兜底"，本 SQL 与 `uq_operation_rates` 配套 |
| 5 | **`ck_operation_rates_target` 拦掉无意义的行**：两个维度都空的行既不是款号价也不是分类价，与工序通用价重复；用 CHECK 兜住，避免"同一语义两行、优先级不可解释"的数据 |
| 6 | **作废 04 §7.11 的索引定义是正确的**：那个定义引用了不存在的列 `operation_id`，即使不冲突也建不出来。保留它只会让未来的 AI 反复踩坑 |
| 7 | **模板复制不搬档位 2**，与 ADR-0009 R22「只复制 `style_operations` + `operation_rates`」不冲突（分类价属于全厂口径，不是某款模板），且避免"复制一款把全厂工资口径改了"的静默事故 —— 与 ADR-0009 拒绝复制尺码比例的理由同类（静默复制比不复制更危险） |

## 备选方案与否决原因

**必须写**。否则未来 AI 会重复评估同一批方案。

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| ① **取消第三档**，只做「款号专用 / 分类+工序专用」两档 | ✅ | 技术上最省事（`style_no` 仍可空，但 `product_category_id` 与 `style_no` 互斥）。但 ADR-0020 §3 明确写了"工序通用价"与 `rate_source` 的 `OPERATION` 取值，等于推翻一条 `Accepted` 的业务决策。若业务方确认"确实不需要工序通用价"，应**先写 ADR-0027 修订 ADR-0020 §3**，而不是在代码里悄悄砍掉 |
| ② **拆成三张表**（`style_rates` / `category_rates` / `operation_rates`） | ✅ | 语义最干净（每档各一张表，无 NULL、无优先级歧义）。否决原因：① 三张表意味着三套区间校验、三套并发锁、三次查询或 `UNION ALL`，取价 SQL 与"至多一条 `effective_to IS NULL`"的断言复杂度显著上升；② 违反 04 §1「库单」与 04 §7「关键表结构约定」把同构实体收敛成一张表的既有风格；③ ADR-0020 明确写的是"`operation_rates` **增**可空 `product_category_id`"，拆表等于改决策 |
| ③ **分类价只做展示分组，不进 `operation_rates`** | ✅ | 改动最小（`operation_rates` 完全不动，04 §7.11 只保留 `styles.category_id`）。否决原因：这样"按分类算裁剪工资"无法实现 —— 而这正是 ADR-0020 立论的前提（背景第 1 条：裁剪工资要按商品分类分别计算）。等于把业务需求删掉 |
| ④ **给 `style_no` 设哨兵值 `'*'` 表示通用价**（保持 `NOT NULL`） | ✅ | 无需放宽约束、也不需 `NULLS NOT DISTINCT`。否决原因：① `'*'` 会污染 `styles` 的 FK（除非去掉 FK，与 04 §1「必须建外键」冲突）；② 取价 SQL 要写 `style_no IN (:style_no, '*')`，可读性差且容易漏 `ORDER BY` 的档位判定；③ 「通用价」不是某个款号的款号，语义污染，比 NULL 更难解释 |
| ⑤ **保持现状（`style_no NOT NULL`、不实现第三档）** | ✅ | 最小改动。否决原因：这是**明知规范有矛盾而不管** —— ADR-0020 的 `rate_source` 永远填不出 `OPERATION`，04 §7.11 的索引永远建不出来，02-裁剪 C37 里承诺的"取价档位可追溯"落不了地。矛盾会被推迟到 P2 工资结算时以"工资算错了"的形式爆发 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 三档模型完整落地；取价口径**全局唯一**（一份 SQL 供计件、工资、单价页预演共用）；`rate_source` 有真实语义；04 §7.8.3 与 §7.11 的索引冲突消除 |
| 负面/代价 | 取价 SQL 从 1 档变 3 档，`resolve` 接口与单价页都要显示档位来源（前端多一列，06 §2.2 表格规范要多一列设计）；`uq_operation_rates` 的键从 3 列变 4 列，**历史若有数据需重建索引**（P0 阶段无存量数据，零成本）；单价的业务概念从"2 个维度"变"3 个"，**计件员培训成本上升**（ADR-0020 已承认这个代价） |
| 风险 | ① **档位 1 与档位 2 同时命中同一工序**（款号有专用价，分类也有价）→ 取价永远优先档位 1，档位 2 对该款无效。**对策**：单价页对每个 `(工序, 款号)` 显示"当前生效价来源"并对被遮蔽的档位打「被款号价覆盖」标记（ADR-0020 强制要求显示来源，此处再加遮蔽标记）。② 用户误以为改了分类价会改这款的工资 → 单价页明确提示"该款已有款号专用价，分类价对此款不生效"。③ 误把档位 2 复制到别的款 → 已在 §4 禁止并写进模板复制测试 |
| 迁移路径 | **P0 阶段零存量数据**：`operation_rates` 尚未建表，只需让 `0004` 按 §1 建表即可，无回填、无停机。若未来已有数据：① 先按新键重建 `uq_operation_rates`（`CREATE UNIQUE INDEX CONCURRENTLY`）→ ② 检查是否存在重复档位行（若有，人工合并并写 `document_logs`）→ ③ 切换应用代码 |
| 回滚方式 | `alembic downgrade` 删表重建（无存量）。已产生的计件流水与工资单**不受影响**（它们存的是单价快照 `unit_price` + `rate_source`，INV-3） |
| 对规范的影响 | 04 §7.8.3（重写 DDL + 取价 SQL + 索引）、04 §7.11（作废其 DDL 片段）、modules/01 §3.4/§5.1/§6/§8/§9、modules/04-计件 §5（取价调用点）、modules/05-工资（取价调用点）。**不新增错误码、不新增权限点、不新增 PG enum**（`product_category_id` 用 FK 不用 enum） |
| 对测试的影响 | 新增必测：TC-B26（三档各命中一档，`rate_source` 正确）、TC-B27（款号有专用价时分类价不生效）、TC-B28（`NULLS NOT DISTINCT` 拦截重复的通用价行）、TC-B29（`style_no` 与 `product_category_id` 同时为空 → `10001`）、CC-4（同三元组 20 并发调价，至多一条 `effective_to IS NULL`）、CC-7（20 并发插入"同款号同工序同日"档位 1，至多 1 行）；改写 TC-B14/TC-B15/TC-B16/TC-B17 的取价断言；`EXPLAIN` 必须命中 `idx_operation_rates_lookup`（10 §5 的查询必须走索引） |

## 验证方式

上线后用什么指标确认这个决策是对的？

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 取价 SQL 命中索引 | `EXPLAIN` 出现 `Index Scan`/`Bitmap Index Scan on idx_operation_rates_lookup` | 单测断言 SQL + 上线后 `pg_stat_statements` 周报（11 §8） |
| 计件取价 P95 | < 150ms（00 §6 非功能需求） | `pg_stat_statements` + 接口埋点 |
| `rate_source` 分布 | 三档均有数据（若某档恒为 0，说明档位没被真正使用，需复盘单价维护习惯） | `SELECT rate_source, count(*) FROM piecework_logs GROUP BY 1` 月度报表 |
| 重复档位行 | **0 行**（`NULLS NOT DISTINCT` 生效） | 巡检 SQL：`GROUP BY style_no, product_category_id, operation_no, effective_from HAVING count(*)>1` 恒空 |
| 区间重叠 | **0 组** | 同款号/分类/工序三元组内区间相交检测，恒空 |
| 错价事故 | 0 起（计件金额与手工核算不符） | 工资结算前对账（05-工资 §5.7 三方对账）+ 业务方抽查 |
