## 背景

要解决什么问题？为什么现在必须做？（写事实与约束，不写方案）

- 现状：docs/04 §7.4 规定 `sizes` 表的唯一约束是
  `CONSTRAINT uq_sizes_code UNIQUE (size_code)`，即**尺码码全局唯一**；
  同时 `size_class size_class NOT NULL` 是**单值**列（`MENS` / `WOMENS` / `KIDS`）。
- 痛点/风险：modules/01 §3.6.4 定稿的内置码表要求 seed 两个码表 ——
  女款模板 `S M L XL`（`size_class = WOMENS`）与男款模板 `L XL XXL 3XL`
  （`size_class = MENS`）。**`L` 与 `XL` 同时出现在两个码表里**。
  在「`size_code` 全局唯一 + `size_class` 单值」下，这两件事无法同时成立：
  要么存不下两个 `L`（唯一约束冲突），要么把 `L` 归到某一类，
  而另一个码表就会出现「分类对不上的尺码」。
- 硬约束：
  - `size_class` 存在的意义就是区分男女装尺码（04 §7.4 `CREATE TYPE size_class`），
    它不是纯展示字段 —— 后续「选码表 → 带出尺码 → 配比例」链路会按它工作
  - 行业现实：`L` 在女装与男装里都存在，且 04 §7.4 列出的可选围度标注里
    女款 `L(165/88A)` 与男款 `L(165/88A)` **围度完全相同**，说明业务上
    「同一个码、两个适用人群」是常态而非例外
  - 04 是 DDL 权威，改它的约束必须留痕（AGENTS.md §8）

---

## 决策

**我们决定：把 `sizes` 的唯一约束从 `UNIQUE (size_code)` 改为
`UNIQUE (size_code, size_class)`，允许同一尺码码在不同尺码类下各存一行。**

```sql
-- docs/04 §7.4 原：
--   CONSTRAINT uq_sizes_code UNIQUE (size_code)
-- 改为：
CONSTRAINT uq_sizes_code_class UNIQUE (size_code, size_class)
```

配套两条约定：

1. **内置 seed 从 6 个尺码变为 8 个**（`L` / `XL` 各存 `WOMENS` 与 `MENS` 两份）：

   | size_class | size_code → name |
   | --- | --- |
   | `WOMENS` | `S`→`S(155/80A)`、`M`→`M(160/84A)`、`L`→`L(165/88A)`、`XL`→`XL(170/92A)` |
   | `MENS` | `L`→`L(165/88A)`、`XL`→`XL(170/92A)`、`XXL`→`XXL(175/96A)`、`3XL`→`3XL(180/100A)` |

   两个码表仍是 2 个、`size_group_items` 仍是 8 条（各指向本类的那一行）。

2. **「`style_color_size_ratios` 只能配款号尺码集合内的尺码」（`20007`）的判定
   只看码表成员关系，不附加 `size_class` 相等条件。**

## 理由

为什么选这个方案？逐条对应背景里的痛点：

| # | 理由 |
| --- | --- |
| 1 | **保住 `size_class` 的语义**。若强行让 `L` 只属于一类，女款码表里就会出现 `size_class=MENS` 的尺码，后续任何「按尺码类筛码表」的实现都会出错，且这种错误在数据上不可见 |
| 2 | **与内置清单自洽**。modules/01 §3.6.4 同时要求两个码表共存，改约束后无需在「少 seed 一个码表」与「尺码分类错误」之间二选一 |
| 3 | **用户自建尺码同样受益**。男装 `XXL` 与女装 `XXL` 围度不同但码相同，用户自建时不必被迫起 `M2XL` 这类畸形的码 |
| 4 | **删除语义不受影响**。引用判定看的是 `size_id`（指向具体那一行），不是 `size_code`；改成复合唯一键后「删掉男装 `L` 不影响女装 `L`」是自然结果 |
| 5 | **风险可控**。改动只涉及一个唯一约束与 seed 清单，迁移用 `DROP CONSTRAINT` + `ADD CONSTRAINT` 即可，不需要改任何已有业务代码（本卡是首批建该表） |

### 被否掉的方案

| 方案 | 否掉原因 |
| --- | --- |
| 保持 `UNIQUE(size_code)`，`L`/`XL` 归 MENS | 女款码表含 MENS 尺码，语义错；且要靠「校验不过滤 size_class」来掩盖，属于用约定掩盖数据错误 |
| 保持 `UNIQUE(size_code)`，`L`/`XL` 归 WOMENS | 同上，方向相反而已 |
| 只 seed 男款码表，女款模板留给用户自建 | 与 modules/01 §3.6.4「定稿，内置 2 个码表」直接冲突，且业务方已明确要女款模板 |

## 验证

- `tests/modules/test_base_dict_models.py`：断言 `uq_sizes_code_class` 存在且
  `uq_sizes_code` 已不存在
- `tests/modules/test_seed_cli.py`：断言 seed 后 `sizes` 恰好 8 行，
  `(L, WOMENS)` 与 `(L, MENS)` 各一行，码表成员指向本类那一行
- 并发用例：20 并发插入同 `(size_code, size_class)` → 恰好 1 行（CC-2）
