# ADR-0030：单次提交体量上限从 800 行放宽到 1200 行，单文件硬上限 400 行

## 背景

`AGENTS §7.1`（2026-10-03 补的计数口径）规定「单次提交 ≤ 800 行手写代码」，
2026-10-05 之前它被当成**硬线**执行。执行两周后的实际后果：

- **一个完整的事务被拆成三张半截的卡**：T-CUT-001c-2（契约 + 列表页 + 只读详情页，
  实测 1150 行）拆成 2a/2b/2c；T-BASE-007（物料 / 供应商 / 布批候选）拆成
  007a/007b。
- **中间态本身不能用**：2a 只有契约与 API 层而没有页面 —— review 无从判断
  「这一半对不对」，因为对不对取决于另一半。
- **总工作量明显更大**：每张拆出来的卡各自带一遍验收标准、各自跑一遍 5 道闸门。
- **最该一眼看出的部分反而跨卡**：三层的裁剪单明细编辑器被拆成「组件 + 页面」
  两张卡之后，「三层结构对不对」要跨两张卡才看得出来。
- **400 行单文件线形同虚设**：`views/base/styles/Detail.vue` 914 行、
  `api/base.ts` 1500+ 行早就存在 —— 既然 800 的提交线守不住，「一次读完」的真实
  抓手本来就该是**单文件**而不是提交总量，而这条规则里根本没写。

痛点的本质：**约束选错了对象**。行数是提交级的度量，而「AI / 人能不能一次读完」
是文件级的度量。

---

## 决策

**我们决定：单次提交体量上限从 800 行放宽到软上限 1200 行手写代码，并把硬约束移到
单文件 400 行。**

具体约定：

```
AGENTS §2.1  ❌ 禁止单次提交超过 1200 行代码或同时改动超过 3 个业务模块
AGENTS §7.1  口径：手写行数；生成物与锁文件不计入
              上限：软上限 1200 行；超了必须写明行数构成与拆分理由
              硬上限：单个文件 400 行（含测试文件），超了说明该抽组件
```

配套要求（保留并加强）：

1. **生成物与生成它的源码同提交**（不变）——否则 `git bisect` 会落到「生成器在、
   生成物不在」的提交上。
2. **超 1200 行或单文件超 400 行时，必须在提交信息与 `docs/12` 写明构成与理由**。
3. **单文件 400 行是硬线**：一个 900 行的 `List.vue`，读它的人（或 AI）要分三次
   才拼得出全貌，而中间那两次很容易漏掉一个约束 —— 比如「尾数为 0 显示破折号」
   这条规则如果落在第 600 行，读到第 450 行就下结论的人不会知道它存在。

---

## 理由

| # | 理由 |
| --- | --- |
| 1 | **完整的事务不该被拆**：一个功能拆成三张卡之后，三张卡的合计体量比一张大（各自的验收标准、闸门、任务卡都要写），而**正确性反而更难保证**（中间态不可用、review 无法判断） |
| 2 | **真实约束是文件级**：「一次读完」对应的是单文件大小。提交总量大但文件小（10 个 200 行的文件）一次 review 完全可以；提交总量小但有个 900 行的文件则不行 |
| 3 | **现状早已越线，规则失去约束力**：`Detail.vue` 914 行、`base.ts` 1500+ 行都已在库里。继续守 800 的结果是「拆卡但不拆文件」—— 拆了提交、没拆真正该拆的地方 |
| 4 | **AI 侧的代价被高估**：多拆卡要多跑几次闸门（每次 4~5 分钟容器构建 + 4 分钟单测），比多读 300 行的成本更高，且多张卡之间的上下文传递更容易丢约束 |

---

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 保持 800 行不变 | ✅ | 见背景：拆半截卡的代价大于收益；且 400 行单文件线本来就守不住 |
| 放宽到 2000+ 行 | ✅ | 「一次读完」的诉求还在；2000 行时单个提交里通常已经有 4~5 个文件，闸门失败后的定位成本明显上升 |
| **1200 行 + 单文件 400 行硬线** | ✅ | **采纳**。提交级放宽、文件级收紧 —— 两个约束各管一件事 |
| 只留单文件约束，不设提交上限 | ✅ | 10 个 200 行文件的提交也是「一次读不完」；闸门跑一次要 9 分钟，提交太大时失败定位成本高 |
| 提交上限 + 单文件上限都用 400 | ✅ | 400 行的提交上限等于强制把事务拆碎，正是要避免的 |

---

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 一个功能一张卡；跨文件约束（如「三层结构」与「汇总口径」）能被一次 review 看全；闸门跑得少 |
| 负面/代价 | 单个 diff 变大，`git log` 的提交粒度变粗；**必须在提交信息里写清文件清单与行数构成**，否则 review 的人无从下手 |
| 风险 | 「适量大点」容易滑向「无限大」——用**单文件 400 行硬线**兜底；超限时该抽组件而不是拆提交 |
| 迁移路径 | 无数据迁移；纯流程规范 |
| 回滚方式 | 把 `AGENTS §2.1` / `§7.1` 的数字改回 800 并删掉单文件那条 |
| 对规范的影响 | `AGENTS.md`（§2.1 / §7.1）、`docs/02-AI开发流水线规范.md` §风险应对表、`.opencode/command/implement.md`、`docs/13-AI提示词与任务模板库.md`（反例表）；新增 `docs/12` L-081 记录理由与代价 |
| 对测试的影响 | 无（测试范围不变）。**新增一条自检项**：`git diff --numstat` 里是否有单文件 > 400 行 |

---

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 单次提交手写行数 | ≤ 1200，超出的在提交信息里有构成说明 | `git log` + `docs/12` 变更记录 |
| 单文件手写行数 | ≤ 400 | `wc -l`，写测试时顺手看一眼 |
| 因「超行数」而拆出的卡 | 逐季度减少 | `docs/tasks/` 里 `-a/-b/-c` 后缀卡的数量 |
| 闸门失败后需要「跨提交找原因」的次数 | 0 | 出现即说明拆得太碎或文件太大 |
