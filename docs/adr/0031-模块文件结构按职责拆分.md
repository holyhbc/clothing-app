# ADR-0031：模块文件结构按职责拆分（逻辑 5 层固定，物理文件数按 400 行上限拆包并重导出）

| 项 | 内容 |
| --- | --- |
| 状态 | `Accepted` |
| 日期 | 2026-10-06 |
| 决策人 | 业务 / 架构确认（2026-10-06 会话） |
| 影响范围 | 后端目录结构与代码组织规范（`docs/01 §4.2`、`docs/03 §1.3`）；**不改** API 契约、数据库结构、错误码、权限点、枚举、单据号 |
| 关联 | `ADR-0030`、`AGENTS.md §7.1`、`docs/03-代码规范.md §1.3`、`docs/12` L-081 / L-089、`docs/modules/base-重构拆分.设计.md` |

---

## 背景

`docs/03 §1.3` 原文规定「**每个业务模块固定 5 个文件**」（`models.py` / `schemas.py` / `repository.py` / `service.py` / `router.py`，扁平单文件）。这条规则在 ADR-0030 之前写下，当时没有任何文件级体量约束；**ADR-0030（2026-10-05，Accepted）把硬约束移到了「单文件 ≤ 400 行」之后，两者直接冲突**。

现状与事实：

- **base 模块已经按本 ADR 的结构落地**（T-BASE-010）：`models/` 7 文件、`schemas/` 6 文件、`service/` 15 文件、`router/` 8 文件、`app/common/permissions/` 13 文件，全部手写文件 ≤ 400 行。这是**既成事实**，且 `docs/12` 变更记录 0092~0098 已将其归档。
- 这一既成事实**与 `docs/03 §1.3` 的文字直接冲突**，正是 `docs/12` L-089 里「待拍板」的那一条。
- 其它模块仍有大量越线文件（`cutting/service.py` 1047、`system/service.py` 869、`cutting/models.py` 696、`system/router.py` 511、`cutting/schemas.py` 457、`auth/service.py` 424 等），存量清单登记在 L-081。按现规则，这些层一旦要拆，每一步都会撞上「固定 5 个文件」的文字。
- 硬约束（不能违反）：
  1. **不得修改 ADR-0030 的结论**。本决策必须是它的直接推论。
  2. `docs/01 §4.1` 的**逻辑分层**（Router 不写业务 / Service 唯一事务边界 / Repository 只查 / 状态机只在 service / 跨模块走 service）是架构红线，不能取消。
  3. **对外导入面稳定**：base 拆分已验证「包 + `__init__.py` 重导出」可做到旧导入路径零改动（变更记录 0097：测试/夹具/工厂 +0/−0）。
- 痛点的本质：**「固定文件数」与「单文件 400 行」是两个互相打架的约束**。前者在模块变大时只能靠「把内容硬塞进 5 个文件」满足，代价就是产出 1000+ 行、谁都无法一次读完的文件 —— 而这正是 ADR-0030 要消灭的东西。

---

## 决策

**我们决定：模块内的逻辑分层固定为 5 个职责（models / schemas / repository / service / router）不变；物理文件数不再固定为 5 —— 当某一层的单文件超过 400 行（ADR-0030）时，该层改为包（目录 + `__init__.py`），按主题 / 域拆成多个文件，硬约束仍是单文件 ≤ 400 行；包必须用 `__init__.py` 重导出该层原有公开名，保证外部导入零改动。**

具体约定：

```
职责层（逻辑，固定 5 层，不变）：
  models      仅字段与约束，无逻辑
  schemas     Pydantic 输入输出，含校验规则
  repository  查询方法，只读为主，不含业务判断
  service     业务逻辑 + 事务边界 + 状态机迁移   ← 核心
  router      HTTP 接口，仅依赖声明 / 校验 / 调 service / 包装响应
  依赖方向：models → schemas → repository → service → router，禁止反向 import

物理形态（可伸缩）：
  单层 ≤ 400 行  → 保持单文件（models.py 等）；不为「凑结构」提前拆包
  单层 > 400 行  → 改包：<layer>/__init__.py + 按主题/域拆出的若干文件
  包内每个文件 ≤ 400 行（ADR-0030 硬线）
  文件名按领域主题（models/rate.py、service/dict_service.py），不是 part1/part2

包的重导出约定（兼容策略，base 拆分已验证）：
  1. __init__.py 重导出该层原有全部公开名，外部
     `from app.modules.<模块>.<层> import X` 零改动；
  2. __init__.py 只做聚合 / 重导出，不放业务逻辑；
  3. 单 router 包的 __init__.py 必须导出名为 router 的单个 APIRouter（既有约定）。
```

`repository` 层同样适用本规则；当前它多数未越线，保持单文件即可。

## 理由

| # | 理由 |
| --- | --- |
| 1 | **与 ADR-0030 的硬线一致**：400 行才是「一次读完」的文件级抓手。固定文件数会逼出 1000+ 行文件，直接违反 ADR-0030 —— 两个规范不能同时成立，必须有一个让位，而让位的应是「文件数」而不是「行数」 |
| 2 | **拆分判据客观、可执行**：`wc -l` 超 400 才拆，不靠临场判断。固定 5 个文件时，每张卡都要重判一次「这个文件算不算太大」，而结果没有依据 |
| 3 | **逻辑分层原样保留**：本决策只放开「物理文件数」，不放开「职责边界」。事务边界唯一（`AGENTS`）、Router 不查库（`docs/01 §4.1`）等红线不受影响 |
| 4 | **兼容策略已被真实验证**：base 拆分中 `models/`、`schemas/`、`service/`、`router/` 四个包全部以 `__init__.py` 重导出保持旧导入路径，792 测试 / 夹具 / 工厂零改动（`docs/12` 0097），OpenAPI 契约零 diff（0093/0095）。不是理论方案 |
| 5 | **消除 L-089 的临场判断**：该条的核心焦虑是「拆 `cutting/models.py` 会不会违规」。规则一旦明确，后续模块的拆分与排期都有统一依据，不需要每张卡再问一次 |

## 备选方案与否决原因

| 方案 | 是否考虑 | 否决原因 |
| --- | --- | --- |
| 继续固定 5 个文件（`models.py` 等扁平） | ✅ | **否决**：base 的 `service.py` 2751、`router.py` 1362、`models.py` 1302 无法在 5 个文件内压到 ≤400；强行保持只能产出 1000+ 行、谁都无法一次读完的文件，与 ADR-0030 的硬线直接冲突。这是被 T-BASE-010 的既成事实否证的方案 |
| 只允许 `models` 拆、`service`/`router` 不拆 | ✅ | **否决**：越线的恰恰主要是 `service`/`router`（`cutting/service.py` 1047、`system/service.py` 869、`system/router.py` 511）。按层给出不一致的规则，下一个人无法判断「我这一层到底能不能拆」，等于把 L-089 的临场判断从一处扩散到每一处 |
| 取消逻辑分层，直接按主题建文件 | ✅ | **否决**：分层是 `docs/01 §4.1` 的架构红线（Router 不写业务、Service 唯一事务边界、Repository 只查、状态机只在 service）。取消分层会让事务边界与权限二次校验失去落点，远超「文件组织」范畴 |
| 允许拆包但**不要求** `__init__.py` 重导出 | ✅ | **否决**：会强制全仓改 import 路径，把一次纯结构重构变成跨模块改动（触发 `AGENTS §6` 单会话单模块约束），且极易漏改而只在运行期暴露。重导出是本方案能被安全采用的**前提**，不是可选项 |
| **逻辑 5 层固定 + 物理按 ≤400 行拆包 + 包重导出** | ✅ | **采纳**：提交级约束（ADR-0030）管「一次提交的规模」，本 ADR 管「模块内文件怎么组织」，两者各管一件事、互不冲突 |

## 影响

| 项 | 说明 |
| --- | --- |
| 正面 | 与 ADR-0030 形成完整体系（提交级 + 文件级）；拆分判据客观；逻辑分层与外部导入面保持不变；后续模块的拆分有统一依据，L-089 不再阻塞 |
| 负面/代价 | 包结构多出 `__init__.py` 与重导出维护；「一个模块几个文件」不再能一眼数清，需查 `docs/01 §4.2` 目录示意；`__init__.py` 若误放业务逻辑会成为循环导入温床 |
| 风险 | ① 按错误主题拆包导致循环导入 → 用「依赖方向单向 + `__init__.py` 只聚合不放逻辑」兜底；② 有人把「可以拆包」理解成「必须拆包」→ 明确「≤400 行保持单文件」，不为凑结构提前拆 |
| 迁移路径 | 无数据迁移。存量越线文件按 `docs/12` L-081 登记，**随各自模块卡迁移**（`AGENTS §2.1` 禁顺手重构）；base 已按本 ADR 落地（T-BASE-010，变更记录 0092~0098） |
| 回滚方式 | 撤销本 ADR，并把 `docs/03 §1.3` 改回「每个业务模块固定 5 个文件」；已拆出的包需合回单文件（无数据影响，纯代码组织） |
| 对规范的影响 | 修订 `docs/03 §1.3`（标题与正文）、`docs/01 §4.2` 目录示意；新增本 ADR 并登记 `docs/01 §6` ADR 索引；更新 `docs/12` §2 变更记录、§5 的 L-081 / L-089。**不新增**错误码 / 权限点 / 状态迁移 / 枚举值 / 单据号前缀 |
| 对测试的影响 | 无新业务用例。拆分类改动必须验证：① 包 `__init__.py` 重导出后旧导入路径命中（`pytest --co` 无 `ImportError`、全量测试通过）；② OpenAPI 契约零 diff（base 已验证的做法）。沿用 `docs/10` 与 `docs/12 §9` |

## 验证方式

| 指标 | 目标值 | 观测方式 |
| --- | --- | --- |
| 新增 / 拆分出的单文件行数 | ≤ 400（含测试文件） | `wc -l`，随拆分卡与提交自检 |
| 拆分后旧导入路径 | 零改动、测试无 `ImportError` | `pytest --co` + 全量测试；对照拆分前的 import 面 |
| 拆分后 OpenAPI | 零 diff | 重跑 `generate:api` 后 `git diff --exit-code` |
| `__init__.py` 内容 | 仅聚合 / 重导出，无业务逻辑 | review；代码走查 |
| 单模块文件数 | 不再作为约束 | 以「单层是否 ≤400」替代 |
