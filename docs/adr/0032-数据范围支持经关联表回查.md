# ADR-0032：数据范围支持经关联表回查（`ScopeSpec.via`）

| 项 | 内容 |
| --- | --- |
| 状态 | `Accepted` |
| 日期 | 2026-10-07 |
| 决策人 | 架构（T-BUND-007b 实施中确认） |
| 影响范围 | **后端数据范围核心层** `app/core/scope.py` —— 影响**所有模块**的数据范围过滤；不改 API 契约、数据库结构、错误码、权限点 |
| 关联 | `ADR-0031`、`docs/07-认证与权限规范.md §3`（数据范围）、`docs/modules/03-打菲.md §3.3`、`docs/12` L-105 |

---

## 背景

`docs/07 §3` 规定数据范围按**表自身的归属列**过滤（车间 → `workshop_id`、集团 → `group_no`）。
`app/core/scope.py` 的 `apply_data_scope()` 据此实现，只认**本表模型上真实存在的列**
（`_column(model, name)` 查不到就直接放行或按最严拒绝）。

打菲的**码表 `bundles` 没有 `workshop_id`** —— 车间归属在父表 `bundling_orders` 上。
于是撞上一个真实的三选一：

| 方案 | 问题 |
| --- | --- |
| A. 给 `bundles` 加冗余 `workshop_id` 列 | 每次生成码都要回填；父单**不能改车间**（打菲单 `workshop_id` 建后锁定），所以冗余不会失配 —— 但这是**为了绕开一层过滤而加的列**，且要写迁移。 |
| B. 在 `bundles` 的 repository 里手写 `workshop_id IN (...)` | **绕过 `scope.py`**。这正是 `scope.py` 要收口的东西 —— 一旦每个模块各写一遍，就再也说不清「数据范围到底在哪些地方生效」，审计时必然漏。 |
| C. 让 `scope.py` 自己支持「经关联表回查」 | 改的是**核心层**，影响所有模块 —— 所以必须写 ADR，不能顺手就改。 |

`docs/modules/03-打菲.md §3.3` 已经写明「`workshop_id` / `group_no` **可从 `bundling_orders` 关联取**」，
即设计文档要求 C 方案（关联取），但当时 `scope.py` 还不支持 —— 这是文档与实现的缺口，
T-BUND-007b 撞上后必须决策。

方案 A 其实也有真实优点（冗余列让 `bundles` 能直接进报表与分页索引），但：
**现在没有任何一张表已经带了归属冗余列**，为「一张表」先立一套新惯例，
后面每张无归属列的表都要重新讨论一遍；而 `bundles` 三年内的量级（年增数十万行）
在 `doc_id` 已有索引的前提下，`join bundling_orders on id = doc_id` 走主键不会成为瓶颈。

---

## 决策

**我们决定：给 `ScopeSpec` 增加 `via: ScopeVia | None`，由 `apply_data_scope()` 自己 `join` 父表并用父表的归属列做范围条件（父表软删一并过滤）。不在任何 repository 里手写范围 `where`。**

```python
@dataclass(frozen=True)
class ScopeVia:
    model: type[Any]   # 父表模型（如 BundlingOrder）
    on: ColumnElement  # join 条件（如 BundlingOrder.id == Bundle.doc_id）

@dataclass(frozen=True)
class ScopeSpec:
    ...
    via: ScopeVia | None = None
```

约定：

1. **`via` 的过滤列一律取自父表**。子表自己没有归属列才需要 `via`；若子表自己有，
   仍用子表的（就近优先），避免为了「统一」而无谓 join。
2. **父表软删一并过滤**：父表 `deleted_at IS NOT NULL` 时子表记录视为不可见 ——
   否则会出现「码还在、父单已软删」的幽灵数据。
3. **`in_scope()` 对 `via` 资源按最严拒绝**：它只拿到一个对象、没有 statement 可 join。
   单对象场景走「先取对象判存在性 → 对父单 `assert_in_scope()`」两步
   （详情 `31001` → 越权 `12002`）。
4. **`via` 关系需登记在守卫测试里**（`tests/modules/test_scope_via.py`），
   与 `test_permission_registry` 同性质：不配守卫的 `via` 等于没生效。
5. **不为此加冗余列**。将来若报表性能实测不够，再单独立项（届时会是独立 ADR）。

---

## 后果

**正面**

- 「数据范围只在 `scope.py` 生效」这条不变量**保住了**，不会出现各模块各写一遍的漏洞。
- `bundles` 的列表 / 统计 / 导出自动获得车间隔离，**新增码端点不需要重复想起这件事** ——
  这正是把能力放进核心层的回报。
- 与 `03 §3.3` 的既有设计一致（文档不再与实现冲突）。

**负面 / 代价（必须承认）**

- **改了核心层，影响所有模块**。因此本 ADR 的守卫测试不是可选项；新增 `via` 必须配用例。
- 多一次 `join`。走主键时开销可忽略，但若将来有 `via` 指向**非主键列**，
  需要重新评估（届时应在大表上 `EXPLAIN` 一次）。
- `in_scope()` 无法处理 `via`，单对象场景要两步 —— 比「子表自带归属列」多一次查询。
  列表场景不受影响（走 `apply_data_scope`）。
- `bundles` 上**没有** `workshop_id`，因此单靠该表无法在不 join 的前提下做车间过滤。
  报表若要绕开 join，需要先决定是否引入冗余列（本 ADR 明确**不**引入）。

**待验证**：`SCOPE_SPECS` 里 `bundles` 的 `via` 指向 `BundlingOrder`；
若将来打菲单允许改车间，需回头确认改车间时的码归属处理（本仓当前**不允许改**，见 `03 §3`）。
