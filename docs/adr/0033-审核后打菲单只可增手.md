# ADR-0033：审核后的打菲单只可增手，减手必须走 `reverse`

## 背景

L-109：T-BUND-008 补并发用例时发现，错误码 `31006`（已计件的码不可改手数 → `31006`）
**在全仓没有任何抛出点**。追下去发现它不是「漏实现」，是**规范自相矛盾**：

- **`03 §2` B23** 规定「审核后若要改某尺码的 `hands`（**增手/减手**），存在已计件码 → `31006`」，
  并允许同步未计件码的 `bundle_qty`；
- **但 `03 §4.1` 的 `update` 只允许 `DRAFT`/`REJECTED`** —— 已审核单**根本改不了**。

于是 B23 第①条的 `31006` 分支**物理上不可达**。这不是实现漏了，是两条规则打架。

而事实上**合法路径早就有了**：`08 §2.1.1` 规定「反审核时任一码已计件 → 拒绝，
必须先红冲；已打菲未计件 → **未打印的码软删重建、已打印码置 `VOIDED`（`31007`）**」。
这条路径 T-BUND-005b 的 `reverse` **已经实现且有测试**。

所以真实问题不是「怎么实现 B23」，而是：

> 审核后要改手数，走**已有的 `reverse`** 还是**另开一条 `APPROVED` 态的改单路径**？

## 决策

**审核后的打菲单只可增手；减手必须走 `reverse`。**

- **增手**（`hands` 增加）：`APPROVED` 态允许，走**专用端点** `POST /{id}/hand-increments`。
- **减手**：`APPROVED` 态一律拒绝（`30001`，提示走 `reversals`）。
- **B23 原 `31006` 条款作废**，`31006` 退回 `DEFERRED_CODES` 预留 Q-B19。

---

## 为什么增手值得单开一条路（这是决策的关键，不是「顺手也做了」）

**因为我们上一轮刚把 `31004` 从「码数必须等于裁剪手数」放宽为「不得超打」，理由是
「主管分批打是常态 —— 先审 3 手开工，后面再补」。**

那么「后面再补」这一步就必须有路走。否则分批打的完整链路是：

> 审核 3 手 → 打完 → 想补 2 手 → **反审核**（已打印码 `VOIDED` → 重打标签）→ 改 → **重新审核**

—— 为了「多打 2 手」把已经贴在衣服上的标签作废重印一遍，还多走一圈审核。
**这与我们刚定下的口径自相矛盾**：既然承认少打是常态，就得承认补打是常态。

## 为什么增手安全到可以单开一条路

增手**只补生成新码（手号从 `N+1` 起），不碰任何已存在的码**。逐项过一遍风险：

| 风险 | 增手时 | 减手时 |
| --- | --- | --- |
| 作废已打印的码 | **不发生** | **必然发生**，而码不可恢复（B12） |
| 已计件码（`counted_at` 非空） | **不碰**，`bundle_qty`/`counted_qty` 都不动 | 要废的就是可能被计件的那几手 → 钱已经付出去 |
| `ck_bundles_cnt (counted_qty <= bundle_qty)` | 不受影响 | 有风险 |
| `cutting_outputs` 结转 | 只**加** `delta × qty_per_hand`，单向 | 要减回，且与 `reserved_qty` 交错 |
| 重打标签的物理成本 | **零**（新号新标签） | 每手一张，作废重印 |

**增手那一列全是「不发生」，减手那一列全是「必然发生且不可逆」。**
这就是两者必须走不同路径的全部理由。

## 为什么减手必须复用 `reverse` 而不是另写一套

减手的本质是「废掉超出新 N 的那几手码」—— 而这**正是** `08 §2.1.1` 已经规定的
「未打印软删重建 / 已打印 `VOIDED`（`31007`）」。`reverse` 已经把这件事做对并测过。

**另写一套等于把同一件事实现两次**，两份实现迟早在某次需求下分叉。
而且 `reverse` 还有一个减手单独做没有的好处：**反审核后单子回到 `SUBMITTED`，
改完还能再走一遍完整的审核六步**（含四条断言与结转对账），不需要为「减手」单独写一套对账。

## 为什么增手要专用端点，而不是放开 `PUT /lines`

`PUT /lines` 是**全量替换**语义。在 `APPROVED` 态放开它，等于允许整行换掉 ——
而行上的码可能已被员工扫码计件。**增手只需要「某个尺码 + 加几手」这一个动作**，
所以端点的入参必须**在结构上**只容得下这个动作：

```
{ size_code | line_id, delta_hands（必须 > 0）, version }
```

**不接受** `hands` 全量替换、不接受 `color_code` / `cutting_size_line_id` / 其它字段。
这样「借增手之名改别的」不是靠校验拦住的，是**类型上就表达不出来**。

## 后果

**正面**

- `31006` 不再是一个**永不触发**的登记码 —— 退回 `DEFERRED_CODES` 后，错误码表与实现**双向一致**
  （`test_errors_registry.py` 的守卫是双向的，「登记了却没实现」本就是它要抓的形态之一）。
- 分批打（少打 → 补打）有了完整闭环，与 2026-10-06 放宽 `31004` 的决定**自洽**。
- `reverse` 保持**唯一**的减手通道，已有的 `32003` 拦截与 `31007` 码处置**一处即足**。
- 增手是**纯增量**操作：不作废、不重印、不红冲，物理成本为零。

**负面 / 代价（必须承认）**

- **增手不能改 `bundle_qty`**（每手件数）。因为 `bundle_qty` 的来源是裁剪侧的 `qty_per_hand`，
  改它等于**裁剪改单联动 = Q-B19**，而 Q-B19 明确「未单开卡」。所以 B23 原第二句
  （同步未计件码的 `bundle_qty`）**本决策不覆盖**。
- **增手后 `cutting_outputs.bundled_qty` 单调增加**，若此时超打会被 `31004` 拦
  （`hands ≤ 裁剪可打手数` 的不变式在增手时**必须重跑一遍** —— 不是自动成立）。
- 多一个端点 = 多一份 OpenAPI 契约、多一套前端调用、一处路由顺序坑
  （`/hand-increments` 必须在 `/{order_id}` 之后声明，但不能与 `/{order_id}/xxx` 混淆）。
- 业务方**必须被告知「补打走增手、减手走反审核」** —— 否则现场会继续走
  「反审核 + 重打标签」的老路，等于这条路径白加。

**待验证 / 后续**

- Q-B19（裁剪改单 → 打菲码联动）落地时，`31006` 随 `qty_per_hand` 变更一并启用。
- 若将来出现「同一 (单,色,码) 要在已计件后改每手件数」的真实需求，
  必须先红冲计件流水（`32003` 的语义），而不是放宽增手。
