## 1. 背景与目标

### 1.1 为什么做

规范体系已闭环（13 篇规范 + 10 篇模块设计 + 24 篇 ADR，约 14000 行），但**仓库里一行后端代码都没有**：`backend/`、`frontend/`、CI、`docker-compose.yml` 均不存在，`docs/requirements`、`docs/tasks`、`docs/releases` 全空，git 无提交记录。10 个业务模块（裁剪/打菲/计件/工资/库存/销售/往来/财务/采购）**全部**依赖 5 个横切件：

| 横切件 | 谁依赖它 | 不先做会怎样 |
| --- | --- | --- |
| 工程骨架 + 质量基线（ruff/mypy/pytest/vite/pnpm/CI） | 全部 | 每个任务卡都要重复搭环境，闸门无法执行 |
| 应用基座（统一响应、错误码、`request_id`、乐观锁、软删、公共字段） | 全部 | 后续每个模块都要重写一遍包装与异常，05/04 规范形同虚设 |
| 认证 + 权限 + 数据范围 | 全部 | INV-8 无法落地；工资/成本数据无隔离 = 合规事故 |
| 基础资料主数据（组织、字典、工序、款号、工序单价） | 裁剪/打菲/计件/工资/库存/采购/销售 | 单据无处引用 `style_no` / `operation_no` / `unit_price` |
| 前端基座（shared 类型、admin 骨架、token、拦截器） | 全部前端任务卡 | 类型手写 → 前后端不一致（06 §7 明令禁止） |

因此 P0 的内容**不是业务功能，而是"让业务功能可以被正确地写出来"**。

### 1.2 成功标准（可度量）

| # | 标准 | 验证方式 |
| --- | --- | --- |
| S1 | `docker compose up -d` 后 `GET /readyz` 返回 200（依赖就绪） | curl |
| S2 | `POST /api/v1/auth/login` 用 `super_admin` 账号登录，返回 `access_token` + `refresh_token`（HttpOnly Cookie），`GET /api/v1/auth/me` 可读 | curl + 手工 |
| S3 | 建款号 `HB-2026-0001` → 配 2 个款号工序 → 设 2 条单价 → `GET /api/v1/operation-rates/resolve?work_date=...` 返回命中的那一档价 | 手工 + 接口测试 |
| S4 | 无 token → `401/11001`；无权限 → `403/12001`；跨车间按 ID 直查 → `403/12002` | 权限矩阵测试 |
| S5 | `python -m app.cli.seed_baseline` 连跑 3 次，权限点/内置角色/6 分类/2 码表/6 尺码/16 色卡行数与内容完全一致 | TC-I09 |
| S6 | 5 道闸门全绿（docs/02 §3）；后端行覆盖 ≥ 80%，新增行 100% | 闸门脚本 |
| S7 | 模糊搜索 `GET /styles/options?q=0021` 的 `EXPLAIN` 出现 `Bitmap Index Scan on idx_styles_trgm` | EXPLAIN（04 §5.1 验收口径） |

### 1.3 非目标（明确不做，防止顺手扩大）

| 不做 | 理由 / 何时做 |
| --- | --- |
| 任何业务单据（裁剪/打菲/计件/结算/出入库/采购/销售/收付款/凭证） | P1~P5 |
| Excel 导入（三步式模板/校验/commit）与导出的**全量实现** | P0 只做**导出**（列表页必备，05 §9.1）；导入端点在 P1 起按模块补（05 §9.3 清单） |
| 员工端 H5 登录（短信验证码 `SmsAuthProvider`） | P2。P0 只落 `AuthProvider` 协议 + `employee_external_identities` 表（ADR-0003 预留位），不实现发送短信 |
| SSE `/api/v1/events/stream` | P2 起。P0 预留 `/events/stream` 路由位返回 `501`，不实现 |
| Redis 异步 worker（Redis Streams / 报表 / 条码） | P3 起 |
| `2FA`（财务与总经理强制） | 07 §1.1 标注"后续里程碑" |
| 物料 / BOM / 仓库出入库 / 客户供应商完整字段与接口 | 物料与 BOM 属基础资料但裁剪才用；P0 只建 `warehouses` / `uom_units` / `customers` 表与只读接口，`materials` / `bom_items` 放 P1（裁剪前置） |
| 移动端 `packages/mobile` | P2。P0 只建目录占位与构建配置，不写页面 |
| 打印 / 条码 / 二维码 | P1 打菲 |

> ⚠️ 「不做」不等于「不预留」：`AuthProvider`、`stock:cost:view` 字段过滤钩子、`rate_source` 取价来源、幂等键 `Idempotency-Key` 依赖、导出 service 复用点，P0 都要留出接口位。

### 2.2 关系

```
workshops 1─< workshop_groups            workshops 1─< users >──1 roles >──< permissions
users 1─< user_roles                                  role_workshops >── workshops
users 1─< auth_refresh_tokens      users 1─< employee_external_identities

customers 1─< styles 1─< style_colors          colors 1─< style_colors
                 1─< style_sizes               sizes 1─< style_sizes
                 1─< style_color_size_ratios   sizes 1─< size_group_items >──1 size_groups
                 1─< style_operations >──1 operations        product_categories 1─< styles
                 1─< operation_rates >──(逻辑) operations    operation_rates >── product_categories(可空)

uom_units 1─< materials(P1)     warehouses(P1 才有库存行)
document_logs：全模块 append-only，**不建 FK**（日志必须能记录"对象已不存在"）
```

**冗余列与外键的取舍**（照抄 modules/01 §3.7，不重新发明）：

| 情况 | 做法 | 理由 |
| --- | --- | --- |
| 单据 → 款号 / 工序 | `varchar` 冗余 + **service 层校验存在且启用**，不建 FK | 单据量大，FK 拖慢列表与报表；款号/工序不可删保证安全 |
| 单据/子表 → `users` / `workshops` / `materials` | **必须建 FK**（04 §1 强制） | 高频 JOIN 且不可变 |
| `style_operations.operation_no` / `operation_rates.operation_no` | **建 FK** → `operations(operation_no)`（04 §7.8.2 已定义） | 工序号本身是唯一键 |
| `operation_rates.style_no` | **建 FK** → `styles(style_no)`（与 `style_operations` 一致） | 保证"款号存在才可能设价" |

### 2.3 不变量

| # | 不变量 | 由谁保证 |
| --- | --- | --- |
| INV-7（沿用） | 所有业务表软删，列表默认过滤 `deleted_at IS NULL` | `BaseModel` 统一 mixin + `apply_data_scope` 末尾统一附加（07 §3.2） |
| INV-8（沿用） | 后端同时校验「操作权限」与「数据范围」，前端隐藏 ≠ 安全 | `require_permission()` + `apply_data_scope()` + 权限矩阵测试 |
| **INV-P0-1** | **字典项删除后不得出现悬空引用**（款号里挂着已删尺码/颜色） | 删除走**条件 DELETE**（`WHERE id=? AND NOT EXISTS(引用)`），`rowcount=0` → `20003`；引用方建款/建行时 `SELECT ... FOR SHARE` 校验 → 串行化（modules/01 §7 已定口径） |
| **INV-P0-2** | 同一 `(style_no, operation_no, 档位)` 的生效区间**不重叠**，且**至多一条** `effective_to IS NULL` | 事务内 `SELECT ... FOR UPDATE` 排序加锁 + 服务端区间校验（`10001` + `details`）+ `uq_operation_rates` 唯一索引兜底（ADR-0026） |
| **INV-P0-3** | `operation_rates.unit_price` **只 INSERT，永不 UPDATE**；调价 = 旧行改 `effective_to` + 插入新行 | service 层无 `UPDATE unit_price` 代码路径 + 测试断言（TC-B14） |
| **INV-P0-4** | 权限点三处一致：`permissions` 表 seed ⊆ 07 §2.2 表格 = `packages/shared/enums/permissions.ts` 常量 | **自动化测试解析 `docs/07-认证与权限规范.md` §2.2 表格**，与迁移 seed 集合、TS 常量集合双向断言（07 §2.2 明确"三处不一致视为闸门 1 失败"） |
| **INV-P0-5** | 停用主数据**永不**影响历史单据查询（单据存 code，报表 join 取名） | service 查询历史时不过滤 `is_active`；仅"新建单据时校验启用"（modules/01 §7） |
| **INV-P0-6** | `document_logs` 不可 UPDATE/DELETE | DB 层 `REVOKE UPDATE, DELETE`（04 §6.2.1）+ 应用账号无 DELETE 权限（ADR-0025） |

### 2.4 索引与查询场景

**没有索引支撑的查询场景不得写进代码。** P0 全部索引如下（`WHERE deleted_at IS NULL` 部分索引为本项目高频约定）：

| # | 场景（业务动作） | SQL 条件 | 命中索引 |
| --- | --- | --- | --- |
| Q1 | 登录查用户 | `employee_no=? OR phone=?` + `is_active` | `uq_users_employee_no` / `uq_users_phone` |
| Q2 | 每次请求装配权限 | `user_roles ⋈ role_permissions ⋈ permissions WHERE user_id=?` | `pk_user_roles(user_id)` + `pk_role_permissions(role_id)` |
| Q3 | 数据范围过滤 | `workshop_id IN (...)` | 各表 `idx_*_workshop_id`（`users` 上建） |
| Q4 | **款号模糊候选**（选择器） | `(style_no \|\| ' ' \|\| name) ILIKE '%q%'` | **`idx_styles_trgm` GIN，必须 Bitmap Index Scan**（04 §5.1） |
| Q5 | 客户/物料/工序/颜色/尺码模糊候选 | 同上 | `idx_customers_trgm` / `idx_operations_trgm` / `idx_colors_trgm` / `idx_sizes_trgm`（04 §5.1 已列） |
| Q6 | 款号列表按客户筛选 | `customer_id=? AND deleted_at IS NULL ORDER BY style_no` | `idx_styles_customer_id` |
| Q7 | 候选默认排序"常用优先" | `ORDER BY last_used_at DESC NULLS LAST LIMIT 20` | `idx_styles_last_used_at` |
| Q8 | **计件取价（P1 依赖，本卡必须建好）** | `WHERE style_no=? AND operation_no=? AND effective_from<=:d AND (effective_to IS NULL OR effective_to>:d) ORDER BY effective_from DESC LIMIT 1` | `idx_operation_rates_lookup`（04 §7.8.3，**ADR-0026 会调整列序**） |
| Q9 | 单价区间重叠校验 | 同上但区间相交条件 | `idx_operation_rates_lookup` 最左两列 |
| Q10 | 单价变更历史（含全部区间） | `style_no=? AND operation_no=? ORDER BY effective_from DESC` | 同 Q8（最左两列相同） |
| Q11 | 员工端可绑定工序列表（P2 依赖） | `style_no=? AND is_piecework AND deleted_at IS NULL ORDER BY sequence` | `idx_style_operations_style(style_no, sequence)` |
| Q12 | 建款一键带出尺码 | `size_group_id=? ORDER BY sort_order` | `pk_size_group_items(size_group_id,…)` 前缀 |
| Q13 | 字典下拉取全部启用项 | `is_active AND deleted_at IS NULL ORDER BY code` | `uq_colors_code` / `uq_sizes_code` 唯一索引前缀（B-tree 可当有序索引用） |
| Q14 | 字典引用计数（删前提示） | `COUNT(*) WHERE color_code=?` | `idx_style_colors_color_code` / `idx_style_sizes_size_code` / `uq_style_color_size_ratios` 前缀 |
| Q15 | 登录失败审计 | `employee_no=? ORDER BY created_at DESC` | `idx_auth_login_logs_employee_no` |
| Q16 | 刷新令牌校验/吊销 | `token_hash=?`；`user_id=? AND revoked_at IS NULL` | `uq_auth_refresh_tokens_hash` / `idx_auth_refresh_tokens_user`（部分索引） |
| Q17 | 款号尺码比例带出（P1 依赖） | `style_no=? AND color_code=?` | `idx_style_color_size_ratios_lookup(style_no, color_code)` |
| Q18 | 工序列表按车间/状态筛选 | `workshop_id=? AND is_active AND deleted_at IS NULL` | `idx_operations_workshop_id_is_active` |

> **P0 一律不建无场景索引**（04 §5 末条）。`pg_trgm` 扩展在**第一条迁移**里建（04 §5.1 要求），闸门 4 在 PG 16 上验证。

## 3. 状态机

### 3.1 单据状态机：P0 不适用

P0 **没有任何业务单据**，`document_status` 枚举与 08 的迁移表在 P1（裁剪单）才建立。此处只登记 P0 存在的两个"类状态机"，它们**不走 `DocumentStatus`**，照抄 modules/01 §4 的「三态 + 变更日志」：

| 动作 | 起始 | 目标 | 权限点 | 前置校验 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| `create` | — | 启用 | `base:create` / `base:operation:manage` / `base:category:manage` | 编码格式合法；唯一索引未冲突（`20002`/`10001`） | 写 `document_logs`（`action='CREATE'`） |
| `update` | 启用/停用 | 启用/停用 | `base:update` / `base:operation:manage` | `version` 乐观锁（`10003`）；编码字段不可改 | 写 `document_logs` + `changed_fields` diff |
| `disable` | 启用 | 停用 | `base:disable` | **必填 `reason`**（缺 → `10002`） | `is_active=false` + 日志 |
| `delete` | 启用 | 软删 / **真删（仅字典四表）** | `base:delete` | 引用计数 = 0（字典：条件 DELETE）；其余表软删 | `deleted_at=now()` 或物理删除 + 日志（modules/01 §4） |
| `restore_builtin`（P0 自定义） | 缺失 | 启用 | CLI only | 键不存在且无删除留痕 | `ON CONFLICT DO NOTHING` 补行（ADR-0025） |
| 角色/权限变更 | — | — | `system:role:manage` | 目标权限点存在 | 写 `document_logs`（`doc_type='Role'`）+ **清空权限缓存**（07 §5） |
| 登录/登出 | — | — | — | 连续 5 次失败锁 15 分钟 | 写 `auth_login_logs`；登出吊销 refresh token |

### 3.2 非法动作与反向对称

- **不适用**（无单据审核）。P0 唯一的"反向"要求：改密码 / 吊销 refresh token 是可逆的（重新登录即可），无副作用需要回滚。
- 停用（`disable`）的反向是 `enable`，P0 **不提供** `enable` 端点 —— 停用即终态，需要恢复请走 `PATCH`（`base:update`）。⚠️ 这是本设计的取舍，需在 §10 Q-P0-06 确认。
- 字典真删**不可恢复**（业务方 2026-10-01 明确"删掉就是不要了"），因此前端必须二次确认并提示"该操作不可撤销"。

### 4.6 幂等 / 分页 / 排序 / SSE

| 项 | 口径 |
| --- | --- |
| 幂等（`Idempotency-Key`） | P0 仅 **模板复制** 与 **登录**需要：Redis（TTL 24h，存 `sha256(key+user_id)` → 首次响应体）+ 同键不同 body → `10002`。其余 P0 接口都是低频管理操作，不做幂等 |
| 分页 | `page`（1 起）+ `size`（默认 20，**上限 100**）；`offset > 10000` → `10001`（05 §9.5.4） |
| 排序 | `sort_by` + `sort_order`（`asc`/`desc`），**服务端白名单映射**，禁止拼 SQL（05 §2 / 04 §5.1） |
| 模糊搜索 | `q` 对「编码 + 名称 + 副标识」`ILIKE`，多关键字空格分隔 = AND；**必须命中 GIN 索引** |
| SSE | P0 **不实现**；`/api/v1/events/stream` 路由占位返回 `501` + `details` 说明"P2 实现"，不静默 404 |

## 5. 并发与一致性

| 风险 | 场景 | 方案 |
| --- | --- | --- |
| **重复建款号** | 两人同时建 `HB-2026-0001` | `uq_styles_no`（部分唯一索引 `WHERE deleted_at IS NULL`）兜底，捕获 `IntegrityError` → `20002`。**禁止"先查后插"**（modules/01 §7、10 §5.4） |
| **字典项删除 vs 他人正在引用** | A 删尺码，B 同时建款号把该尺码写进 `style_sizes` | 删除走**条件 DELETE**（`WHERE id=? AND NOT EXISTS(SELECT 1 FROM style_sizes ...)`），`rowcount=0` → `20003`；引用方建款时对字典行 `SELECT ... FOR SHARE`。**绝不出现悬空引用**（INV-P0-1） |
| **停用工序 vs 新建款号工序配置** | A 停用 `03 拼前`，B 同时给新款配 `03` | B 的 service 内 `SELECT ... FOR SHARE` 校验 `is_active`；A 的停用与 B 的建配串行化 → `20001` |
| **并发调价（同一款同工序同日）** | 两次 `POST /operation-rates` 同 `effective_from` | 事务内对目标 `(style_no, operation_no)` 区间行 `SELECT ... FOR UPDATE` 排序加锁 → 服务端区间重叠校验（`10001` + `details`）→ `uq_operation_rates` 唯一索引兜底（`20002`）。**不得出现两条 `effective_to IS NULL`** |
| **调价 vs 计件并发（P2 依赖）** | 调价事务与 N 条计件同时跑 | 无写冲突（调价只碰 `operation_rates`）；已落库流水 `unit_price` 永不变（INV-3）。P0 只需保证 Q8 取价 SQL 走索引，P2 写真并发测试 |
| **模板复制重复点击 / 断网重发** | 同源→同目标连点两次 | `Idempotency-Key`（Redis 24h）+ 目标款号 `style_operations` 行 `FOR UPDATE` + `uq_style_operations` 兜底；**整批单事务**，禁止"复制一半" |
| **权限变更 vs 在途请求** | 管理员改了角色，某请求正在装配权限 | 权限**每次请求查库**（07 §1.1「权限查库，避免权限变更不生效」）。不引入权限缓存 → 无失效窗口。改权限后其后续请求立即生效（已签发 JWT 因不含权限明细也自动正确） |
| **比例全量替换互相覆盖** | 两个管理员同时改同款同色比例 | 事务内对该 `(style_no, color_code)` 现有行 `FOR UPDATE` 排序加锁 + 请求带 `version`（按该维度取 `MAX(version)`）→ `10003`；**不允许 MERGE 式部分更新**（modules/01 §7） |
| **乐观锁** | 所有人同时改一条主数据 | 统一入口 `update ... WHERE id=? AND version=?`，`rowcount=0` → `10003`。**Router/Repository 不得手写乐观锁** |
| **seed 与用户并发新增字典项** | seed 正在插 `XL`，用户也在建 `XL` | `ON CONFLICT DO NOTHING` + 捕获冲突跳过（不报错、不覆盖）；seed 整体单事务，冲突跳过不导致回滚 |

**P0 必须配套的并发测试用例**（10 §5.4：真并发、`asyncio.gather` + 每任务独立 session、必须有唯一约束兜底）：

| # | 用例 | 期望 |
| --- | --- | --- |
| CC-1 | 20 并发建同款号 | `styles` 恰好 1 行；成功 1 个返回 201，其余 `20002` |
| CC-2 | 20 并发建同色码字典 | 恰好 1 行；其余 `10001`/`20002`（口径见 modules/01 §11.6） |
| CC-3 | A 删字典项 vs B 建款号引用该字典项（真并发） | **绝不允许悬空引用**：要么删除成功且 B 被 `20003`/`20001` 拦，要么 B 成功且删除返回 `20003` |
| CC-4 | 20 并发调同一 `(style_no, operation_no, effective_from)` | 至多 1 条成功；区间不重叠；**至多一条 `effective_to IS NULL`** |
| CC-5 | 20 并发复制模板到同一目标款号 | 目标 `style_operations` 无重复行（`uq` 兜底）；失败方为幂等返回或 `SKIP`/`ABORT` 语义 |
| CC-6 | 20 并发 PATCH 同一条主数据（同一 `version`） | 恰好 1 个成功，其余 `10003` |

## 7. 风险与回滚

| 风险 | 影响 | 缓解 | 回滚方式 |
| --- | --- | --- | --- |
| **规范内部冲突被带进代码**（§10 五项） | 迁移建错表 → 后面全部返工 | 未确认前**不写迁移**；冲突逐条登记 + ADR | 删除未合并的迁移文件；已合并则写新迁移修正（禁止改历史迁移） |
| 权限点三处不一致（07 §2.2 / 迁移 seed / TS 常量） | 越权或误拒 | INV-P0-4 自动化测试（解析 docs 表格双向断言） | 闸门 1 拦截，不允许放宽 |
| 应用账号误授 `DELETE` 导致业务数据被硬删 | 数据不可恢复 | 只对**四张字典表**授 `DELETE`（ADR-0025），其余表仍不授；`document_logs` 连 `UPDATE` 都 REVOKE | `REVOKE DELETE ON colors, sizes, size_groups, size_group_items FROM erp_app` |
| seed 把用户真删的内置行插回来 | 用户困惑、误用已淘汰色/码 | `ON CONFLICT DO NOTHING` + **删除留痕跳过**（查 `document_logs`）+ `restore_builtin` 显式命令（ADR-0025） | 重跑 `restore_builtin` / 再次真删 |
| 每次请求查库装配权限带来延迟 | 列表页 P95 超 800ms | P0 权限点规模 ≈ 150 条、用户角色 ≈ 2 条，一条 JOIN 走主键索引；**先测再优化** | 若超阈值 → 加 60s Redis 缓存并在权限变更时主动失效（需写 ADR） |
| `mypy strict` + `ruff ANN/S` 规则一次性太严，团队（AI）反复返工 | 拖慢交付 | P0 第一张卡就把基线配全并跑通，之后不再动配置 | 确需放宽 → **先改 03 §1.6 + 写 ADR**，禁止私自放宽（docs/02 §3） |
| 本机无 Docker / 无 PG 16，闸门 4/5 跑不了 | 无法验收 | `docker-compose.ci.yml` 一键起 PG16+Redis；`make gates` 封装 5 道闸门 | 无 |
| 2C/12G VPS 上同时跑 dev+test 库 OOM | 线上受影响 | 11 §1 铁律：测试库只在 CI 容器；本机开发用 `garment_erp_dev` | 停测试容器 |

- **迁移回滚**：P0 全部迁移**可完全回滚**（`downgrade()` 逐个 `DROP TABLE` / `DROP TYPE` / `DROP EXTENSION`）。⚠️ 两处不可逆需在迁移注释中标注：`pg_trgm` 扩展若被后续模块索引依赖则 `DROP EXTENSION` 会失败（P1 起不再 down 到此处）；`DROP EXTENSION` 属破坏性 DDL，需二次确认（11 §10 红线 7）。
- **发布回滚**：P0 无历史版本可回退（首次发布）。镜像 tag 用 `v0.1.0`，禁止 `latest`（11 §4）。数据回滚 = 从备份恢复（P0 无业务数据，恢复成本≈0）。
