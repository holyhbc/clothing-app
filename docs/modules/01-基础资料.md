## 1. 模块职责与边界

| 项 | 内容 |
| --- | --- |
| 职责 | 提供组织、款号、物料、工序、款号工序配置、单价历史、往来单位等主数据；提供 BOM（单件用量 + 耗损率）；提供**工序与单价模板复制**；提供**尺码比例主数据**（款号 × 颜色 × 尺码 → 手数，ADR-0013）与**颜色 / 尺码 / 码表字典（含内置标准库）**；保证编码规则唯一且稳定 |
| 拥有 | `users` / `roles` / `workshops` / `workshop_groups` / `warehouses` / `styles` / `style_colors` / `style_sizes` / **`colors`** / **`sizes`** / **`size_groups`** / **`size_group_items`** / **`style_color_size_ratios`** / `materials` / `bom_items` / `operations` / `style_operations` / `operation_rates` / `customers` / `suppliers` / `uom_units` |
| 不负责 | 单据审核与状态流转（裁剪/打菲各自模块）；计件流水写入与取价调用（属 piecework 模块，只读本模块取价）；库存数量（属 stock 域）；账号登录与令牌（属 auth 模块） |
| 与 auth 的分工 | 业务属性（姓名、工号、车间、组别、`data_scope`、在离职状态）由本模块维护；密码、`must_change_password`、角色授权、登录日志由 auth 模块写。两模块共表不同列，**必须同事务约定写入同表不同列**，禁止两处同时 UPDATE 同一行 |
| 与 stock 的分工 | 本模块只有 `materials.unit_price`（参考单价）；批次实际成本、结存、锁定量在 `material_stocks`，不可从本模块读取当成本 |
| 与计件/工资的分工 | 本模块拥有 `operations` / `style_operations` / `operation_rates` 三表，含调价与模板复制；[04-计件](./04-计件.md) 只在流水落库那一刻**按 `work_date` 读一次**取价并快照（INV-3），不反写；[05-工资](./05-工资.md) 只读 `piecework_logs` 的单价快照 |

| 与销售/往来的分工 | `customers` / `suppliers` 只存主数据；应收余额、核销在 finance 模块 |
| **与裁剪的分工（REV-2026-10）** | `style_color_size_ratios` 的**维护权在本模块**（属基础资料，**不是裁剪单的一部分**）：⚠️ **REV-2026-10 第三批（ADR-0014）**：比例已**降级为「建议值」** —— [02-裁剪](./02-裁剪.md) 只在**带出建议**时读它，**件数一律由裁剪单行的 `hands` × `qty_per_hand` 算出**；**部分尺码缺配只提示不拦**，只有该 `(style_no, color_code)` **完全没有**比例才报 `20006`，多余尺码报 `20007`。原「裁剪单行 `ratio_override` 临时覆盖」机制**已作废**（改为行级 `hands` 可改 + 单据级 `ratio_snapshot` 快照）。**改裁剪单行永不回写本表**（零污染）。原因：比例是「客户的排版要求」，与款号/颜色这类主数据同生命周期，且要能被裁剪单导入导出复用 |

## 2. 业务规则

| # | 规则 | 说明 |
| --- | --- | --- |
| R1 | 款号格式 | `{客户前缀}-{年份}-{4 位序号}`，如 `HB-2026-0001`；存库统一转大写，大小写不敏感唯一 |
| R2 | 款号不可删 | 已产生计件或库存的款号只能停用（`is_active=false`），停用后不允许新建裁剪/打菲单，历史单据照常查询与反审核 |
| R3 | 物料编码格式 | 面料 `F-{类目码}-{6 位}`（`F-CT-000128`）；辅料 `T-{类目码}-{6 位}`（`T-ZL-000456`）；成衣 `FG-{款号}-{色}-{码}` |
| R4 | 物料分类 | `material_type ∈ {FABRIC, TRIMMING, LABEL, FINISHED_GOOD}`；`FABRIC` 参与裁剪耗料，`TRIMMING`/`LABEL` 领用出库，`FINISHED_GOOD` 由裁剪结转生成、不手工建 |
| R5 | 单位一致性 | BOM 的 `usage_qty` 与 `materials.unit_id` 关联，`usage_qty` 用 `numeric(14,3)`；面料用米（`M`）或码（`YD`），辅料用个/只/条 |
| R6 | BOM 唯一性 | `UNIQUE (style_no, material_id)`；同款同物料只允许一行。**同一次请求内重复行** → `10001`（Schema 层拦）；**与已存在行冲突**（原行已停用需改料）→ `20003` |
| R7 | 耗损率 | `waste_rate` 存 `numeric(6,4)`，5.2500 表示 5.25%；取值范围 0~100，加 CHECK |
| R8 | 工序号 | `operation_no` 为 `varchar(16)`（示例 `'01'` `'02'`），**编号与名称均由用户自定义**，全厂唯一，不随款变化；`01` 裁、`02` 打边、`03` 拼前 只是本厂现状，**不是内置枚举**（见 R16） |
| R9 | 一扎件数 | 由**款号工序配置** `style_operations.bundle_qty` 决定；`operations.default_bundle_qty` 只是工序字典上的默认值，可被款号工序覆盖；**默认 1，不硬编码**（09 §3、04 §7.5.1） |
| R10 | 单价快照（INV-3） | 取价只发生在计件流水落库那一刻：按 `work_date` 命中生效区间取一次 `unit_price` 落库；改基础资料只影响**未来**取价，历史 `piecework_logs.unit_price` 是快照，永不 UPDATE |
| R11 | 单价历史只追加 | 调价 = 旧行只改 `effective_to = 新价生效日` + 插入新行 `effective_from = 新价生效日`；**绝不 `UPDATE unit_price`**，也不使用"当前版本"布尔列；旧行永久保留供审计与反查 |
| R12 | BOM 变更（下游影响） | 改 `bom_items.usage_qty` / `waste_rate` 只影响**未来新提交**的裁剪单耗料计算；已审核裁剪单已扣料，不追溯 |
| R13 | 引用保护 | 被裁剪单、打菲单、BOM、库存、计件、`style_operations` / `operation_rates` 引用的资料禁止软删，返回 `20003`（07 §3.3「删除时若被引用 → `20003`」），只能停用 |
| R14 | 软删 | 全部业务表带 `deleted_at`，列表默认过滤（INV-7）；`users` / `roles` / `permissions` 为硬删禁令表（04 §6.1） |
| R15 | 并发唯一 | 编码唯一性全部用唯一索引兜底，禁止"先查后插"（`20002`） |
| R16 | 工序不内置枚举 | `operations` 是**用户自定义主数据**，自由增删改；加工序、改工序名零发版，**禁止**在代码常量或 PG enum 里预置工序（[ADR-0009](../adr/0009-计件单价与款号工序模板.md) §2） |
| R17 | 工序被引用只能停用 | 被 `style_operations` / `piecework_logs` / `operation_rates` 引用的工序**禁止删除**，只能 `is_active=false` 停用；删除被引用工序 → `20003`；停用后不参与新建单据与新建款号工序配置，历史数据照常可查 |
| R18 | 生效区间不重叠 | 同一 `(style_no, operation_no)` 的生效区间**不允许重叠**：服务端校验新区间与所有既有区间无交集，**同时**由 `uq_operation_rates` 唯一索引兜底；重叠 → `10001` + `details` 回传冲突区间 |
| R19 | 允许未来生效价 | `effective_from` 可为未来日期（提前公告调价），但 `effective_from > work_date` 的价**不参与当日取价**；`effective_to IS NULL` 表示当前有效 |
| R20 | 调价必填原因 | 调价（关闭旧区间 + 插入新区间）`reason` **必填**，缺失 → `10006`；`unit_price = 0` 允许（免费工序），但同样需要 `reason` 说明 |
| R21 | 单价按工序定，不分技能等级 | 单价维度 = `款号 × 工序 × 生效区间`，**不引入技能等级维度**（业务方明确否掉「工序 + 技能等级」二级定价：等级判定主观、争议大，ADR-0009） |
| R22 | 模板复制范围 | 复制范围严格限定 `style_operations` + `operation_rates`；**不复制** BOM、颜色、尺码（因款而异，ADR-0009 已否决"整单复制"方案） |
| **R23** | **尺码比例归基础资料，不归裁剪单**（REV-2026-10，ADR-0013） | `style_color_size_ratios`（款号 × 颜色 × 尺码 → **手数**，[04 §7.7](../04-数据库规范.md)）是**主数据**，维护权在本模块；裁剪单只读 + 可单据级临时覆盖（[02-裁剪](./02-裁剪.md) C23）。比例维度是**款号 × 颜色**（同款不同色可不同），`ratio` 用 `numeric(14,4)`（允许 1.5 手），`Σratio` = 手数合计（**不要求整数**） |
| **R24** | **比例是建议值，缺配不硬拦（REV-2026-10 第三批修订，ADR-0014）** | 一个 `(style_no, color_code)` 下**部分**尺码缺 `ratio` → **不再报错**，只是「带不出建议」，由 [02-裁剪](./02-裁剪.md) 返回 `missing_size_codes` **提示**，用户可切 `MANUAL` 手录；**该颜色一条比例都没有** → `20006`（仍硬拦）；比例里出现款号颜色组内**没有**的尺码 → `20007`（**仍硬拦**，主数据脏数据，本模块 `PUT` 时提前拦）。`ratio > 0`（DB `CHECK`）。⚠️ **本模块 `PUT /style-color-size-ratios` 仍建议按款号尺码集合配齐**（配齐了带出建议才准），但**配不齐不再阻止裁剪** |
| **R25** | **内置标准库 + 可自由新增（REV-2026-10 第三批修订）** | `colors` / `sizes` / `size_groups` 三张字典表采用「内置标准库 + 用户自由新增」：**① 内置清单只写 2 个尺码模板 + 16 色基础色卡**（业务方 2026-10-01 明确"只内置 2 个"，清单见 §3.6.4）；② 用户**可自由新增**任意颜色 / 尺码 / 码表，**不受内置清单限制**（R25 的核心不变）；③ **删除规则：未被引用的字典项允许物理删除（真删，不留残渣）；已被引用的禁止删除，只能 `is_active = false` 停用 → `20003`**（04 §7.4 规则前两条）；④ **禁止把颜色 / 尺码做成代码常量或 PG enum**（同 R16 精神） |
| **R26** | **seed 幂等 + 不覆盖用户改动（REV-2026-10 第三批修订）** | `python -m app.cli.seed_baseline` 写入内置尺码 / 色卡 / 码表：按**唯一键 `ON CONFLICT DO NOTHING`** upsert，**重复执行结果完全一致**（不新增行、**不覆盖用户改过的 `is_active` / 名称**）；seed **只增不删**；被用户**真删**的内置行**不会自动回来**（符合"我删了就是不要了"，04 §7.4 规则第 4 条）。⚠️ **第三批起内置项不再"必须走停用"**：未被引用的内置项可直接 `DELETE` 真删（与用户项同权），被引用后才受 `20003` 保护 |
| **R27** | **★ 字典项删除规则（REV-2026-10 第三批新增，业务方确认）** | ① **未被任何单据 / 配置引用 → 允许物理删除（真删）**，`is_builtin` **不作为**"不可删"的判据；② **已被引用 → 禁止删除，返回 `20003`**，只能停用（停用后不参与新建单据，历史数据照常可查）；③ **引用判定范围**：`style_sizes` / `style_colors` / `style_color_size_ratios` / `size_group_items` / `materials.color_code` / `purchase_order_lines.color_code` / `purchase_arrival_lines`（ADR-0015 新增）/ 裁剪 / 打菲 / 计件等各单据行表；④ 删除前先查引用计数并在响应回 `ref_count`，前端提示"被 N 处引用，改用停用"；⑤ ⚠️ **变更说明**：原口径「`is_builtin = true` 的内置项一律拒绝删除、只能停用」**已作废** —— 它与业务方"可以增删改"的确认冲突（04 §7.4 已改为「`is_builtin = true` 的行**可停用、可删除**」） |

### 2.1 下游影响矩阵

| 改动对象 | 影响的模块 | 不影响 |
| --- | --- | --- |
| `operation_rates`（调价：关闭旧区间 + 插入新区间） | 只影响 `work_date` 落在新区间的**未来**取价（新建计件流水金额） | 历史 `piecework_logs.unit_price`/`amount`、已结算工资（INV-3）、已落库区间 |
| `materials.unit_price` | 未来采购参考价、报价 | `material_stocks` 批次成本、已发生台账 |
| `bom_items.usage_qty` / `waste_rate` | 未来裁剪单耗料与应出数计算 | 已审核裁剪单的已扣料、已生成耗料台账 |
| `operations.default_bundle_qty` | 未来新建 `style_operations` 的默认带出值 | 已有 `style_operations.bundle_qty`、已审核打菲单已生成的 `bundle_no` 与件数 |
| `style_operations.bundle_qty` / `is_piecework` | 该款该工序未来计件的 `qty` 与是否计件、员工绑定可选工序列表 | 已落库流水的 `qty`/`amount`（快照）、历史绑定记录 |
| `style_operations.sequence` | 员工端工序选择顺序、裁剪打菲工序路线的展示顺序 | 历史流水（只存 `operation_no`） |
| `operations.name` | 报表与列表的工序显示名 | 一切金额与流水（流水只存 `operation_no`，报表 join 取名） |
| `operations.is_active = false` | 新建款号工序配置与新建单据被拒；员工绑定页不再出现该工序 | 历史 `style_operations` / `piecework_logs` / `operation_rates` 可查 |
| `styles.is_active = false` | 新建裁剪/打菲单被拒（`20001`） | 历史单据查询、反审核、报表 |
| `users.workshop_id` / `group_no` | 该员工未来数据范围与新流水归属 | 历史流水（历史流水保留原 `workshop_id`） |
| **`style_color_size_ratios.ratio`**（REV-2026-10 第三批改写） | 比例只是**建议值**：改比例只影响**之后带出建议**的裁剪单；**已提交 / 已审核裁剪单的件数完全不变**（由行上 `hands` 决定，`ratio_snapshot` 保留当时快照） | 已审核裁剪单的 `output_qty` / `balance_qty` / 已扣料 / 已生成 `cutting_outputs` / 已生成的打菲码 |
| **`materials.width_cm`**（REV-2026-10） | 未来**新建**采购行带出的默认门幅 | 已入库批次 `material_stocks.width_cm`（批次值优先，可与本值不同）、已生成台账 |
| **`colors` / `sizes` / `size_groups` 停用** | 新建款号色组 / 尺码配置被拒；新建裁剪单选该色 / 码被拒 | 历史单据、`style_colors` / `style_sizes` 既有配置、`style_color_size_ratios` 既有比例、报表 |

## 3. 数据模型

所有表含公共字段（04 §2）：`id` / `created_at` / `created_by` / `updated_at` / `updated_by` / `deleted_at` / `version` / `remark`。下表只列业务字段。

### 3.1 员工与组织

**`users`（员工）**

| 字段 | 类型 | 必填 | 唯一 | 说明 |
| --- | --- | --- | --- | --- |
| `employee_no` | `varchar(32)` | ✅ | ✅ | 工号，系统生成，跨车间唯一 |
| `name` | `varchar(64)` | ✅ | — | 姓名 |
| `phone` | `varchar(20)` | ✅ | ✅ | 员工端 H5 登录账号（07 §1.2） |
| `password_hash` | `text` | ❌ | — | argon2id；员工端短信登录可空，由 auth 模块写 |
| `workshop_id` | `uuid` FK→`workshops` | ❌ | — | 所属车间，非车间员工（财务/仓管）为空 |
| `group_no` | `varchar(32)` | ❌ | — | 所属组别，对应 `workshop_groups.group_no` |
| `data_scope` | `data_scope` enum | ✅ | — | `SELF`/`GROUP`/`WORKSHOP`/`FACTORY`，默认 `SELF`（07 §2.1） |
| `is_active` | `boolean` | ✅ | — | 在离职；离职员工不可登录，历史流水保留 |

**`roles`（角色）**：`code`（✅唯一，`workshop_supervisor` 等）、`name`、`data_scope`、`is_system`（内置角色不可删）。

**`permissions`（权限点）**：`code`（✅唯一，如 `base:read`）、`name`、`module`、`action`、`sort`。权限点清单以 07 §2.2 为准，本模块只登记不改。

**`role_permissions`**（PK `role_id`+`permission_id`）、**`user_roles`**（PK `user_id`+`role_id`）：仅关联表，无公共字段。

**`workshops`（车间）**

| 字段 | 类型 | 必填 | 唯一 | 说明 |

| 字段 | 类型 | 必填 | 唯一 | 说明 |

| `effective_from` | `date` | ✅ | ↑ | 生效起（**含**当日）；**允许未来日期**（提前公告，R19） |

| `reason` | `text` | ❌ | — | 变更原因；**调价必填**（R20，缺失 → `10006`）；首次设价可空 |

约束与索引（照抄 04 §7.5.3）：`uq_operation_rates UNIQUE (style_no, operation_no, effective_from)`、`idx_operation_rates_lookup ON operation_rates (style_no, operation_no, effective_from DESC)`。

**取价 SQL（唯一口径，按计件日期 `work_date` 命中生效区间）**：

```sql
SELECT unit_price FROM operation_rates
WHERE style_no = :style_no AND operation_no = :operation_no
  AND effective_from <= :work_date::date
  AND (effective_to IS NULL OR effective_to > :work_date::date)
ORDER BY effective_from DESC
LIMIT 1;
```

命中不到 → `20004`（该款号该工序未设置单价，或当日无生效单价）。

**调价流程（禁止 UPDATE 价格，04 §7.5.3）**：

1. 校验新区间与所有既有区间无交集（R18），`reason` 非空（R20）
2. 旧行只改 `effective_to = 新价生效日`（`unit_price` 永不动）
3. 插入新行 `effective_from = 新价生效日` + 新 `unit_price`
4. 同事务写 `document_logs`（`doc_type='OperationRate'`，`action='UPDATE'`，`changed_fields` 记新旧价与生效日）
5. 历史计件流水的 `unit_price` 快照（INV-3）**完全不受影响**

**已作废口径（REV-2026-10）**：不设 `is_current` 布尔列，也不设 `approved_by`（单价无审核流程，维护人由 `updated_by` 与 `document_logs.operator_name` 追溯，07 §5）；"当前有效"= `effective_to IS NULL`。

#### 3.6.1 `style_color_size_ratios`（款号尺码比例，**引用 04 §7.7.1，权威口径在 04**）

```sql

CREATE TABLE style_color_size_ratios (

    ...公共字段,

CREATE INDEX idx_style_color_size_ratios_lookup
  ON style_color_size_ratios (style_no, color_code);
```

| 项 | 口径 |
| --- | --- |
| 归属 | **基础资料主数据**（R23），维护权在本模块；[02-裁剪](./02-裁剪.md) 只读 + 单据级覆盖 |
| 维度 | **款号 × 颜色 × 尺码**；`Σratio` = **手数合计**（如 1+2+2+1 = 6 手，**不要求整数**，也允许 5.5 手） |
| 唯一 / 约束 | `uq_style_color_size_ratios (style_no, color_code, size_code)`；`CHECK (ratio > 0)` |
| 齐全性（R24，ADR-0014 修订） | **部分**缺配 → 只提示（`missing_size_codes`），不拦；**完全**未配该颜色 → `20006`；比例出现款号没有的尺码 → `20007`（硬拦） |
| **每手件数不在本表** | `qty_per_hand` 是**裁剪单行输入**（业务方明确「每次裁剪输入，不同数据」），**不做基础资料配置**（ADR-0013 §2） |

| 尺码 | `ratio`（手） |
| --- | --- |

| XL | 2.0000 |
| XXL | 2.0000 |
| 3XL | 1.0000 |
| **合计（手数）** | **6.0000** |

### 3.7 关键关系

```
customers 1─< styles 1─< style_colors / style_sizes / bom_items / style_operations
materials 1─< bom_items          operations 1─< style_operations 1─< operation_rates
styles 1─< style_operations     styles 1─< operation_rates     operations 1─< operation_rates
workshops 1─< workshop_groups    workshops 1─< users
uom_units 1─< materials

# REV-2026-10 字典与比例（§3.6）
colors    1─< style_colors                    colors    1─< purchase_order_lines
sizes     1─< style_sizes                     sizes     1─< size_group_items
sizes     1─< style_color_size_ratios         size_groups 1─< size_group_items 1─< sizes
styles    1─< style_color_size_ratios         style_colors 1─< style_color_size_ratios
```

- `style_operations` 是**款号与工序的多对多载体**：它同时是「该款工序路线」「该款每工序一扎几件」「模板复制」的载体（04 §7.5.2）。
- `operation_rates` 逻辑引用 `operations`（`operation_no` 字符串冗余，与流水一致不加 FK），**外键由 `style_operations` 保证款号工序存在**；迁移时必须补齐 `style_operations` 的两个 FK（04 §1 强制外键）。

- 单据不建 FK 到款号（`style_no` 字符串冗余），但**必须**建 FK 到 `users` / `workshops` / `materials`（04 §1 强制外键）。
- `style_no` 在单据上是 `varchar(32)` 冗余列 + 服务层校验存在且启用，原因：单据量大、外键会显著拖慢列表与报表；款号不可删（R2）保证冗余安全。校验必须在 service 层，**不靠数据库 FK**。

## 5. 核心流程

1. **初始化内置标准库**：执行 §5.2 的 `python -m app.cli.seed_baseline`，写入内置 `colors` / `sizes` / `size_groups` + `size_group_items`（`is_builtin=true`），并同时 seed 角色 / 权限 / 科目等基线数据（[11 §部署步骤 5](../11-部署运维与发布规范.md)）。**必须幂等**，可重复执行。
2. 管理员建 `warehouses`（面料库/辅料库/成衣库）与 `workshops`（裁剪/缝制），再按车间建 `workshop_groups`。
3. 建 `uom_units`（米、码、个、公斤），供 `materials.unit_id` 引用。
4. 建 `customers` → 建 `styles`（按 R1 生成款号）→ 维护 `style_colors` 色组；**尺码按码表一键带出**（选 `size_group` → 批量建 `style_sizes`，见 §5.3），也可逐码新增。
5. **建 `style_color_size_ratios`（R23/R24）**：按 `(style_no, color_code)` 全量录入各尺码**手数**比例。⚠️ **REV-2026-10 第三批（ADR-0014）**：比例是**建议值**，**建议**在该款第一次裁剪前配齐（配齐了「按比例带出」才准），但**漏配不再阻止裁剪** —— 只有该颜色**完全**没配比例才 `20006`；**部分**漏配只是带不出那一行，用户可手录。红色 L:XL:XXL:3XL = `1:2:2:1` → 手数合计 6 手（**裁剪单可任意偏离，偏离不回写本表**）。
6. 建 `materials`（按 R3/R4 生成编码），面料填 `is_colorful=true`；面料可填 **`width_cm`（标准门幅）** 作为建采购行时的默认值（ADR-0012：权威值在批次上，采购行可覆盖）。
7. 建 `operations`（工序字典：编号、名称、归属车间、`is_piecework`、`default_bundle_qty`），加工序零发版（R16）。
8. 建 `style_operations`（款号 × 工序 × `sequence` × `bundle_qty`），或用 §5.1 模板复制从相近款号一键带入。
9. 建 `operation_rates`（款号 × 工序 × `unit_price` + `effective_from`），或用 §5.1 模板复制带入源款号的现行价。
10. 建 `bom_items`（款号 × 物料 × `usage_qty` + `waste_rate`）。⚠️ BOM 只提供**单件用量与耗损率**，用于算**耗料**；**不用于反算应出件数**（[02-裁剪](./02-裁剪.md) C7/C8）。
11. 建 `users`（工号、手机号、车间、组别、`data_scope`），分配 `roles` 得到 `permissions`。
12. 业务开工：裁剪单引用款号 / 色组 / 尺码 / **尺码比例 + 每手件数**与 BOM；打菲单引用款号/工序/`bundle_qty`；计件按 `work_date` 命中 `operation_rates` 生效区间取价并快照 `unit_price`。
13. 变更时：调价按「关闭旧区间 + 插入新区间」（R11），BOM 改「改行」，**尺码比例按 `(款号,颜色)` 全量替换并写日志**，停用资料一律 `is_active=false` 并留原因。

### 5.1 工序与单价模板复制（ADR-0009 §3）

**为什么做**：同一客户连续几款衣服工序与工价基本相同。手工重录 `15 工序 × 6 款 = 90 行`，出错率极高；复制比录入快 10 倍（ADR-0009 理由 6）。

**复制语义**：把**源款号**的 `style_operations`（工序结构：工序号、`sequence`、`bundle_qty`、`is_piecework`）+ `operation_rates`（单价历史）整套复制到**目标款号**。

| 项 | 规则 |
| --- | --- |
| 接口 | `POST /api/v1/styles/{style_no}/operations/copy-from/{source_style_no}`，`{style_no}` = **目标**款号 |
| 权限点 | `base:rate_template:manage`（07 §2.2 已登记） |
| 事务 | 整个复制在**单事务**内完成：先校验源款号与目标款号，再写 `style_operations`，最后写 `operation_rates`；任一环节失败**整单回滚**，禁止"复制了一半" |
| 复制范围 | 仅工序与单价；**不复制** BOM、颜色、尺码（R22），**⚠️ 也不复制尺码比例 `style_color_size_ratios`（REV-2026-10 明确，见下方理由）** |
| 幂等 | 同一源款号 → 同一目标款号重复复制，行为由 `conflict_policy` 决定（见下）；前端重复点击靠 `Idempotency-Key`（05 §5）返回首次结果 |
| 留痕 | `document_logs`（`doc_type='StyleOperationCopy'`, `action='CREATE'`），`changed_fields` 记源款号、复制模式、写入/覆盖/跳过条数与目标款号 |
| 返回 | 写入条数、`skipped` 明细（工序号 + 原因）、复制后的目标款号工序与单价快照 |

**三个复制选项**（用户选择，不由系统默认，缺省必须显式传）：

| 选项 | `copy_mode` | 行为 |
| --- | --- | --- |
| ① 沿用源价 | `COPY_PRICE_AS_IS` | 工序结构 + 单价全部复制；源款号每个工序的**当前有效价**（`effective_to IS NULL` 的那一行）作为目标款号新区间的 `unit_price`，`effective_from` 取**复制当天**；若源工序无现行价则跳过该工序价格并在 `skipped` 里回传 |
| ② 沿用源价并按比例调整 | `COPY_PRICE_WITH_RATIO` | 同 ①，另传 `price_ratio`（`numeric(6,4)`，如 `1.0800` = 上浮 8%），`unit_price = round(源价 × ratio, 6)`；比例必须 `> 0`，比例与逐工序新价在响应里**逐项回显**供人工核对（ADR-0009 验证方式：复制错误率必须为 0） |
| ③ 只复制工序结构 | `COPY_STRUCTURE_ONLY` | 只复制 `style_operations`，**不写** `operation_rates`；目标款号单价必须单独设置，未设价时计件按 `20004` 拒绝 |

> 选项 ③ 的必然结果：目标款号在设价前**不能计件**（[04-计件](./04-计件.md) 取价命中不到即 `20004`），前端应在复制成功提示里明确写"该款工序单价待设置"。

**⚠️ 尺码比例 `style_color_size_ratios` 一律不复制（REV-2026-10 决策，理由如下）**：

| 项 | 说明 |
| --- | --- |
| 结论 | 模板复制**只复制 `style_operations` + `operation_rates`**；**不复制** BOM、颜色、尺码、**尺码比例**（R22 + 本行） |
| 理由 ① | **比例与「款号 × 颜色」的销售构成强绑定**。`1:2:2:1` 是这个款这个色给客户报的比例（业务方原话：按尺码比例裁剪）；另一个款即使同客户同系列，销售构成也会变（版型宽松度、目标客群、价格带都不同），**照抄比例等于替业务方编了一个错的数**，而且**错得很隐蔽**——直到车间裁完才发现 |
| 理由 ② | **比例错了直接导致多耗料**。比例决定**带出的建议手数**，手数 × 每手件数决定件数，件数决定耗料（`Σ(件数 × usage)`）；比例偏一个尺码就会整缸布的耗用与结转全错（[02-裁剪](./02-裁剪.md) C13/C21/C22） |
| 理由 ③ | **比例是「要重新定」而不是「要复制」的主数据**。ADR-0009 复制工序与单价的前提是「工序结构与工价在同客户同系列高度重复」；比例**没有这个前提** |
| 理由 ④ | **静默复制比不复制更危险**。不复制 → 目标款号缺比例 → 裁剪侧**明确提示去补**（该颜色完全未配才 `20006`；部分缺配提示 `missing_size_codes`，R24）；复制 → 用户以为已经好了，**提示失效**，问题推迟到出布头对不上账时才爆 |
| 前端表现 | 复制成功提示追加一行：**「尺码比例未复制，请按目标款的销售构成为各颜色录入尺码比例」**，并给 `style_color_size_ratios` 的录入入口跳转 |
| 与单据内偏离的区分 | 复制是**建款阶段**的主数据动作（不复制比例）；**生产阶段**的「本次临时改量」是**裁剪单行级 `hands` 可改**（[02-裁剪](./02-裁剪.md) C22/C29 —— 改行不改主数据、无需原因、单据级 `ratio_snapshot` 留痕）。⚠️ REV-2026-10 第三批：原 `ratio_override` + 必填原因的「单据覆盖」机制**已作废**。**两者都不允许把别的款的比例当成自己款的比例** |

**冲突处理（目标款号已有同工序）**：由请求参数 `conflict_policy` 指定，**不设系统默认**，防止默默覆盖别人的数据。

| `conflict_policy` | 行为 |
| --- | --- |
| `SKIP` | 保留目标款号已有工序/单价，跳过源款号对应项，记入 `skipped` |
| `OVERWRITE` | 用源款号的值覆盖目标款号**当前有效**的那一行（`style_operations` 直接改行；`operation_rates` 走「关闭旧区间 + 插入新区间」，**绝不 UPDATE `unit_price`**，R11），原值写 `document_logs` |
| `ABORT` | 发现任一冲突即**整体失败**并回滚，返回冲突清单（工序号 + 目标已有值） |
| `MERGE`（可选） | 工序结构合并（按 `operation_no` 匹配），单价**一律不覆盖**，目标款号缺的工序才补价 |

**典型场景**：

| 场景 | 操作 |
| --- | --- |
| 同客户同系列快速建款 | 新建款号 → 以上一款为源 → 模式 ①（或 ② 加价）→ `conflict_policy=SKIP` → 30 秒内建出成套工序与工价（ADR-0009 验证目标：录入耗时 ≤ 30 秒） |
| 同款换色不改工序 | 模式 ③，只带工序结构（价格已在旧款设好，按款号定价需要重设） |
| 旺季整体调价 | 不走复制，走 `POST /api/v1/operation-rates` 逐工序调价（可 `effective_from` 设未来日期，R19） |
| 复制后核对 | 复制响应回显工序数与单价数，与源款号逐项核对（ADR-0009 验证方式） |

### 5.2 内置标准库初始化（REV-2026-10 新增，R25/R26）

**为什么做**：颜色与尺码是**每张单据都要选的高频下拉**，逐个手建既慢又容易前后不统一（有人写 `XL`、有人写 `大码`）。用 **内置标准库 + 可自由新增**（R25）解决：**开箱有一套常用值，同时不锁死用户**。

**执行方式**（与 [11 §部署步骤 5](../11-部署运维与发布规范.md) 同一条命令，**不新增部署步骤**）：

```bash
# 首次部署与后续升级都跑同一条命令，幂等
docker compose exec api python -m app.cli.seed_baseline
```

**写入内容**（§3.6.4 定稿，照 04 §7.4）：**只写 2 个尺码模板 + 16 色基础色卡**，以及既有基线数据（角色 / 权限 / 科目 / 内置角色，07 §2.3）。

| # | 写入对象 | 内容 | 条数 |
| --- | --- | --- | --- |
| 1 | `size_groups` | ① `女款模板 S-M / L-XL`（`size_class='WOMENS'`）② `男款模板 L XL XXL 3XL`（`size_class='MENS'`） | **2** |
| 2 | `sizes` | 随模板带出的 **8 个**尺码行：`WOMENS` = `S` `M` `L` `XL` / `MENS` = `L` `XL` `XXL` `3XL`（`L`、`XL` 各存两份，唯一键含 `size_class`，ADR-0027），`name` 用实际围度标注 | **8** |
| 3 | `size_group_items` | 两个模板的有序尺码项（`size_id` + `sort_order`），**各指向本尺码类的那一行** | **8** |
| 4 | `colors` | 16 色基础色卡：`WHT` 本白 / `BLK` 黑 / `NVY` 藏青 / `KHK` 卡其 / `GRN` 军绿 / `BEG` 米色 / `RED` 正红 / `BLU` 蓝 / `GRY` 深灰 / `PNK` 粉 / `PUR` 紫 / `SLT` 浅灰 / `BRN` 棕 / `OLV` 橄榄 / `BEG2` 浅卡其 / `WHT2` 本白(裁剪区分) | **16** |
| 5 | `style_color_size_ratios` | ❌ **不写** | 0 |

全部字典行标 `is_builtin = true`（**仅界面标识**，不影响删除权限，R27）。

**幂等规则（R26，必须逐条落实）**：

| # | 规则 | 实现口径 |
| --- | --- | --- |
| 1 | 按**唯一键 `ON CONFLICT DO NOTHING`** | `colors.color_code` / `sizes.size_code` / `size_groups.name` 冲突即**跳过**，**不插入重复行、不覆盖已有行**（04 §7.4：`ON CONFLICT DO NOTHING` 且**不得覆盖用户已修改的行**） |
| 2 | **不覆盖用户改过的 `is_active`** | 已存在且 `is_active=false` 的内置项**保持停用**（用户可能主动停用它），seed **不得**悄悄启用 |
| 3 | **不覆盖用户改过的名称** | `colors.name` / `sizes.name` 只在**首次插入**时写入；已存在则**不动**（避免用户改了名被每次部署冲回去） |
| 4 | **只增不删** | seed **不删除任何行**；被用户**真删**的内置行**不应被 seed 悄悄插回**（`ON CONFLICT DO NOTHING` 只在键不存在时插入，因此需按「删除留痕」跳过，见 §12 待登记项 ①） |
| 5 | 可重复执行 | 连跑 3 次，`colors`(16) / `sizes`(6) / `size_groups`(2) / `size_group_items`(8) 行数与内容**完全一致**（TC-33） |
| 6 | 失败即整体回滚 | 整个 seed 在**单事务**内执行；任一条失败整体回滚，不留半套库 |
| 7 | 写日志 | `document_logs`（`doc_type='BaselineSeed'`，`action='CREATE'`，`changed_fields` 记插入/更新条数） |

**内置项的增删改**：

| 动作 | 是否允许 | 权限点 |
| --- | --- | --- |
| 新增颜色 / 尺码 / 码表 | ✅ **随时允许**，不受内置清单限制（R25）；不需发版、不需改 seed | `base:create` |
| 修改 `name` / `sort_order`（**04 §7.4 字段名**） | ✅ 允许（含内置项改名，不影响历史单据——单据存 `color_code` / `size_code`） | `base:update` |
| 停用 `is_active=false` | ✅ **允许**（必填 `reason`） | `base:disable` |
| **删除（未被引用）** | ✅ **允许真删**（REV-2026-10 第三批修订，R27）——**内置项与用户项同权**，`is_builtin` **不拦** | `base:delete` |
| **删除（已被引用）** | ❌ **拒绝** → `20003`，改用停用（R27） | `base:delete` |

> ✅ **内置清单已定稿 2026-10-01**（§3.6.4）：**2 个尺码模板（女款 `S M L XL` / 男款 `L XL XXL 3XL`）+ 16 色基础色卡**，照 [04 §7.4](../04-数据库规范.md)。第三批前草案的「14 色 / 27 尺码 / 4 码表」**作废**（§12 Q-B11 已闭环）。
> **seed 清单以数据形式维护**（代码内常量列表 + `seed_baseline` 读取），日后加模板 / 加色**只改常量、不改表结构、不发版**。
> **工厂若需要 3XL 以上或童装码表**：新建尺码 → 建码表（`size_class='KIDS'` 或 `MENS`）→ 按序加 `size_group_items`，**零发版**（R25，TC-43 覆盖）。

### 5.3 码表一键带出款号尺码（REV-2026-10 新增）

1. 建款号时选一套 `size_group`（码表）→ 系统读 `size_group_items`（按 `sort_order` 升序）→ **批量建 `style_sizes`**，自动带出 `size_code` / `size_name` / `sort_no`（`style_sizes` 自己的列名，**不是字典表的 `name` / `sort_order`**）。
2. 允许**在码表基础上增删本款尺码**（款号自己的尺码集可以与码表不同，如加一个 `4XL`）；**允许不用码表逐码新增**。
3. 带出完成后**立即提示下一步**：为该款**每个颜色**录入尺码比例（§5 第 5 步）—— 配了才能用「按比例带出」省事；**不配也能裁**（裁剪侧走模式 B/C 手录，只有该颜色**完全**未配才 `20006`，R24）。

## 7. 并发与幂等

| 风险场景 | 方案 |
| --- | --- |
| 并发建同款号 | `uq_styles_style_no` 唯一索引兜底，捕获冲突转 `20002`；禁止"查后插" |
| 并发改单价（同日同款同工序） | 调价 = 旧行改 `effective_to` + 插入新行，**同事务**；`uq_operation_rates UNIQUE (style_no, operation_no, effective_from)` 保证同一生效日只有一行；并发第二次 → 唯一索引冲突转 `20002`，业务提示"该生效日单价已被他人调整"；若旧行已被他人关区间 → `10003`，要求刷新后重试 |
| **调价与计件并发** | 调价只改 `operation_rates`，**不触碰 `piecework_logs`**；计件落库时先取价再插流水，二者无写冲突。**无论调价事务提交与否，已落库流水的 `unit_price`/`amount` 一律不变**（INV-3）；正在事务中的计件按它读到的区间快照落库，读到旧价就是旧价（合法且可解释）。测试必须真并发：调价事务与 20 条计件同时跑，断言流水条数与金额集合只可能是「全部旧价」或「新旧混合」，**绝不允许半条** |
| **生效区间重叠校验的并发** | 服务端"先查区间再插入"**不足以防重**，必须靠 `uq_operation_rates` 兜底；同 `effective_from` 的并发插入必有一方抛唯一冲突（转 `20002`）。不同 `effective_from` 但区间相交的情况靠插入前区间校验拦（`10001` + `details` 冲突区间）；为缩小竞态窗口，调价事务内对目标 `(style_no, operation_no)` 的现有区间行 `SELECT ... FOR UPDATE` 排序加锁 |
| **模板复制并发**（同一目标款号被并发复制两次） | 目标款号已有同工序时由 `conflict_policy` 决定（`SKIP`/`OVERWRITE`/`ABORT`/`MERGE`）；兜底靠 `uq_style_operations UNIQUE (style_no, operation_no)`：**并发第二次不会写脏数据**，只能走覆盖/跳过/报错之一。整批复制必须单事务 + 目标款号维度的乐观锁（复制前 `SELECT ... FOR UPDATE` 锁目标款号的 `style_operations` 行），否则两次复制会交错产生"半套工序" |
| 模板复制重复点击 / 断网重发 | 接口支持 `Idempotency-Key`（05 §5）：同键同 body 返回首次结果；Redis TTL 24h + `uq_style_operations` 唯一索引双保险 |
| 复制与调价并发（同一目标款号同一工序） | 复制写的价格与人工调价都落到 `operation_rates`，`effective_from` 相同必撞唯一索引 → 后到者得 `20002`/`10003`，**不允许静默覆盖**；响应提示"该款该工序在复制当天已有单价" |
| 并发改 BOM | 全量替换用 `version` 乐观锁；`UNIQUE (style_no, material_id)` 防重复行 |
| 并发停用工序 + 新建款号工序配置 | 建配置时 service 内 `SELECT ... FOR SHARE` 校验 `is_active`；停用与建配置串行化 |
| 并发停用 + 新建单据引用 | 建单据时 service 内 `SELECT ... FOR SHARE` 校验 `is_active`；停用与建单串行化 |
| 导入重复执行 | 导入接口支持 `Idempotency-Key`（05 §5），同键同 body 返回首次结果 |
| 导出与列表范围不一致 | 导出复用列表 service，**禁止另写导出路径**（07 §3.2 铁律 3） |
| 批量导入部分失败 | 整批单事务；失败即整批回滚，返回行号，不做"成功一半" |
| **REV-2026-10 比例主数据 vs 裁剪单并发（第三批放宽）** | 比例 `PUT` 只改 `style_color_size_ratios`；裁剪单只在**带出建议**时读它并把建议值落到行上 `hands` + 单据级 `ratio_snapshot`。二者**无写冲突**，且**比例在 `submit` 与 `approve` 之间被改动完全不影响本单件数**（件数由行决定，ADR-0014 核心收益）；`approve` 二次校验只拦「完全无比例 `20006`」与「多余尺码 `20007`」。兜底：`uq_style_color_size_ratios` 唯一索引 + `version` 乐观锁 |
| **REV-2026-10 比例全量替换并发** | `PUT /style-color-size-ratios` 是「按 `(style_no, color_code)` 全量替换」，**两个管理员同时改同一款同一色会互相覆盖**。必须：① 事务内对该 `(style_no, color_code)` 现有行 `SELECT ... FOR UPDATE` 排序加锁（同 §7 生效区间校验做法）；② 请求带 `version`（按 `style_no + color_code` 维度取 `MAX(version)` 或建聚合行），不符 → `10003`；③ **不允许 `MERGE` 式部分更新**，避免"删掉别人刚加的尺码" |
| **★ 删字典项 vs 他人正在引用（REV-2026-10 第三批，R27）** | A 在 `DELETE /sizes/{size_code}`，B 同时建款号把该尺码写进 `style_sizes` 删除事务内**先查引用计数 → 计数为 0 才 DELETE**，且与引用方串行化：引用方建款/建采购行时对字典行 `SELECT ... FOR SHARE`；删除方改为 `DELETE ... WHERE id=? AND NOT EXISTS(SELECT 1 FROM style_sizes ...)` 的**条件删除**，`rowcount = 0` → **`20003`**。**绝不出现"尺码被删但款号里还挂着"的悬空引用**|
| **★ seed 幂等 vs 用户真删（REV-2026-10 第三批）** | 用户真删了内置项后再跑 `seed_baseline` seed 用 `ON CONFLICT DO NOTHING`：**只补"键不存在"的行**，因此真删的行**会被重新插回** ⚠️ —— 这与 04 §7.4「删掉后不会自动回来」冲突，实现需按「删除留痕」跳过（`document_logs` 中有删除记录的 `is_builtin` 行不再重建，见 §5.2 幂等规则第 4 条与 §12 待登记项 ①）|
| **REV-2026-10 seed 与用户同时新增字典项** | `seed_baseline` 按**唯一键 `ON CONFLICT DO NOTHING`** 且**不覆盖用户改过的 `is_active` / 名称**（R26）：与用户并发新增同名编码时，唯一索引先到者成功，后到者捕获冲突并**跳过**（不报错、不覆盖）；seed 整体单事务，冲突跳过不导致回滚 |
| **REV-2026-10 停用字典项 vs 新建单据引用** | 停用 `colors`/`sizes` 与新建裁剪单 / 采购单行引用**串行化**：新建单据时 service 内 `SELECT ... FOR SHARE` 校验 `is_active`；已停用 → `20001` 口径拒绝。停用**永不**影响历史单据查询（单据存 `color_code` / `size_code`，报表 join 字典取名，停用项仍可查） |

| 场景（业务动作） | SQL 条件 | 命中索引 |
