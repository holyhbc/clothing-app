## 1. 背景与目标

**为什么做**：工厂网络差，扫码计件必须扛住断网。T-PIECE-007 已交付在线主链路，但断网时扫码**直接失败、这一手的产出丢失**（工人少拿钱，码停在 `counted_at IS NULL`）。[07 §7](../07-认证与权限规范.md) 早已要求工位机页用 IndexedDB 持久队列 + 指数退避 + 冲突不静默丢弃；T-PIECE-007 因引入新运行时依赖刻意留空，本卡补上。

**成功标准**（可度量）：

- 断网（`navigator.onLine === false`）时扫码 100% 落 IndexedDB 队列，刷新 / 关闭再开浏览器仍在。
- 恢复网络后按 `1s/2s/4s/8s/30s` 退避、最多 8 次自动重试；同一记录的 `Idempotency-Key` 在重试间**不变**，服务端**不重复计数**（[05 §5](../05-接口设计规范.md)、BR-PW-24）。
- 离线回放遇 `32001`（同码已被他人计件）时该条**保留在队列**并标记冲突；顶部常驻条显示冲突条数、可展开逐条查看，**不静默丢弃、不自动移出**。
- 8 次仍失败（或遇永久业务错误）的记录进入 `failed` 且保留，可人工重试或删除。
- 组件测试覆盖 入队 / 退避重试 / 回放冲突 / 失败 / 清理。

**非目标**：

- **PWA service worker / 离线页面壳**：只做数据队列，不做离线页面缓存（离线时页面本身仍需能加载）。
- 员工端 H5 的 `localStorage` 队列（[07 §7](../07-认证与权限规范.md) 另一口径，属链路 B）。
- SSE 实时推送、多标签页分布式锁、冲突自动裁决（一律人工）。

## 2. 领域模型

本设计**不新增数据库表、不改迁移**（04 §7 不适用）。数据模型是**浏览器端 IndexedDB 库**，只存在于工位机本地。

### 2.1 实体与字段

| 实体 | 存储 | 主键 | 关键字段 | 说明 |
| --- | --- | --- | --- | --- |
| 离线计件队列记录 | IndexedDB 库 `garment-erp-piecework-offline`（v1）→ object store `pending_counts` | `id`（`crypto.randomUUID()`，入队生成） | 见下表 | 一条 = 一次待提交的扫码 |

记录字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 记录标识（`keyPath`）；入队生成 |
| `idempotencyKey` | string | 是 | **入队时生成、重试间不变**（[05 §5](../05-接口设计规范.md)）；即 `POST /piecework/count` 的 `Idempotency-Key` 头 |
| `payload` | object | 是 | 直接作为请求体（见下三行展开） |
| `payload.bundle_no` | string | 是 | 打菲号（扫码结果） |
| `payload.employee_id` | string | 是 | **入队时选定**的操作员；重试沿用，不受之后换人影响 |
| `payload.scanned_at` | string | 是 | ISO 8601 带时区；**入队时刻固定**，重试不变（BR-PW-11 以它归属 `work_date`） |
| `payload.station_id` | string \| null | 否 | 工位号（T-PIECE-007 的 `workstation_no`） |
| `payload.device_id` | string | 是 | 设备号，首次生成后持久化（§6.3）；[07 §7](../07-认证与权限规范.md) 离线归属 |
| `payload.qty` | string | 否 | 部分生产件数（`String(number)`）；不传 = 该手整手（BR-PW-26） |
| `status` | enum | 是 | `pending` / `syncing` / `conflict` / `failed` |
| `attempts` | number | 是 | 已尝试次数，`0..8`（INV-Q5） |
| `nextAttemptAt` | number | 是 | epoch ms；`status='pending'` 时生效 |
| `createdAt` | number | 是 | epoch ms，入队时刻 |
| `lastError` | object \| null | 否 | `{ code, message, details? }`，最近一次失败 |
| `conflict` | object \| null | 否 | `32001` 的 `details`：`counted_by_name` / `counted_at` / `counted_qty` / `bundle_qty` / `hands` |

索引：`by_status (status)`、`by_next_attempt_at (nextAttemptAt)`。

### 2.2 关系

```
IndexedDB pending_counts.payload ──(HTTP)──▶ POST /api/v1/piecework/count
  payload.bundle_no  ──▶ bundles.bundle_no         （服务端锁码、一码一员工，BR-PW-29）
  payload.scanned_at ──▶ piecework_logs.scanned_at → work_date（BR-PW-11）
  payload.device_id  ──▶ piecework_logs.device_id  （07 §7 离线归属）
  idempotencyKey     ──▶ 05 §5 幂等键（Redis 24h + 唯一索引双保险）
```

队列记录**不是业务数据**：真正的业务事实是服务端落库的 `piecework_logs` + `bundles.counted_*`。因此队列记录的删除不受 INV-7 软删约束（见 §3 `manual-delete`）。

### 2.3 不变量

| # | 不变量 | 由谁保证 |
| --- | --- | --- |
| INV-Q1 | `idempotencyKey` 在记录生命周期内**不变** | 代码（入队生成后只读）+ 组件测试 |
| INV-Q2 | `scanned_at` 在入队时刻固定，重试沿用 | 代码 + 组件测试 |
| INV-Q3 | 同一 tab 内**同一时刻只有一个 flush 循环** | 代码（模块级 `inflight` 守卫）+ 并发测试 |
| INV-Q4 | 成功记录必删；`conflict` / `failed` 记录必留 | 代码 + 组件测试 |
| INV-Q5 | `0 ≤ attempts ≤ 8`，且单调不减 | 代码 + 组件测试 |
| INV-Q6 | `status='conflict'` ⟺ 最近一次错误码为 `32001` 且 `conflict != null` | 代码 + 组件测试 |

### 2.4 索引与查询场景

| # | 场景（业务动作） | 查询 | 命中索引 |
| --- | --- | --- | --- |
| Q1 | flush 取「到期待提交」 | `by_status.getAll('pending')` 后过滤 `nextAttemptAt <= now` | `by_status` |
| Q2 | 顶部常驻条计数（待提交 / 冲突 / 失败） | `by_status.count(status)` × 3 | `by_status` |
| Q3 | 展开冲突 / 失败列表（按入队时间升序） | `by_status.getAll('conflict' \| 'failed')` 后按 `createdAt` 排序 | `by_status` |
| Q4 | 单条删除 / 人工重试 | `store.get(id)` / `store.put(record)` | 主键 `id` |

> 队列规模量级为 `10²`（单工位断网数分钟），以上索引足够；`by_next_attempt_at` 供后续若需按到期时间批量取用，当前不是瓶颈。

## 3. 状态机

> 这是**客户端队列**的状态机，不是 08 的单据状态机：无权限点、无审核/反审核、不写 `document_logs`。

| 动作 | 起始 | 目标 | 权限点 | 前置校验 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| `enqueue` | — | `pending` | 不适用 | 本地 `bundle_no` 正则通过；操作员 / 工序 / 工位已选定 | 写记录；生成 `id` / `idempotencyKey`，固定 `scanned_at`，`attempts=0`、`nextAttemptAt=now` |
| `claim` | `pending` | `syncing` | 不适用 | `nextAttemptAt <= now` | `attempts += 1` |
| `succeed` | `syncing` | （删除） | 不适用 | 服务端 `code=0`（含 `idempotent=true`） | 删除记录；用响应 `today_*` 覆盖大字卡 |
| `retry` | `syncing` | `pending`（`attempts < 8`）/ `failed`（`attempts = 8`） | 不适用 | 可重试错误（§6.4） | 记 `lastError`；`nextAttemptAt = now + delay(attempts)` |
| `conflict` | `syncing` | `conflict` | 不适用 | 服务端 `32001` | 写 `conflict`（`details`）；**不再自动重试、不删除** |
| `fail` | `syncing` | `failed` | 不适用 | 永久错误（§6.4） | 记 `lastError`；不自动重试、不删除 |
| `reset` | `syncing` | `pending` | 不适用 | 页面加载发现遗留 `syncing`（上次被关掉 / 崩溃） | 回 `pending`；重发用**同一键**，服务端幂等 |
| `manual-retry` | `failed` | `pending` | 不适用 | 操作员在面板点「重试」 | `nextAttemptAt=now`，`attempts` **保留**（不清零，避免无限重试） |
| `manual-delete` | `conflict` / `failed` | （删除） | 不适用 | 操作员在面板点「删除」 | 物理删除该条（队列非业务数据，不适用 INV-7） |

**非法迁移**：`conflict` / `failed` 不得自动回 `pending`（只能人工重试）；`pending` 不得跳到 `conflict` / `failed`（必须先 `claim`）。

**退避序列**：`RETRY_DELAYS_MS = [1000, 2000, 4000, 8000, 30000, 30000, 30000, 30000]`；第 `n` 次失败后 `nextAttemptAt = now + RETRY_DELAYS_MS[n-1]`；`attempts` 到 8 再失败即 `failed`（[07 §7](../07-认证与权限规范.md)「1/2/4/8/30，最多 8 次」）。

## 4. 接口清单

**无新增接口、无新增错误码、无新增权限点。** 队列只消费 T-PIECE-002 已交付的端点：

| 方法 | 路径 | 权限点 | 数据范围 | 请求要点 | 响应要点 | 错误码 |
| --- | --- | --- | --- | --- | --- | --- |
| POST | `/api/v1/piecework/count`（复用，无新增） | `piecework:count` | `WORKSHOP` | `bundle_no`、`employee_id`、`scanned_at`、`station_id`、`device_id`、可选 `qty`；头 `Idempotency-Key` = 记录的 `idempotencyKey` | `today_hands/today_qty/today_amount`、`bundle_qty`、`hands`、`idempotent` | 复用既有：`32001` `32006` `32005` `32002` `20004` `31001` `31002` `10003` `10004` `11001` `99999` |

- **幂等要求**：唯一写接口；`Idempotency-Key` 由客户端在**入队时**生成并冻结在记录里（[05 §5](../05-接口设计规范.md)）。⚠️ [07 §7](../07-认证与权限规范.md) 原文「重试携带同 `bundle_no`」是简述 —— 真正的幂等机制是 `Idempotency-Key`（`bundle_no` 只是键的组成部分之一），本设计**不新增**幂等语义。
- 分页 / 排序 / 过滤：不适用（无列表接口；队列列表是本地 IndexedDB 查询）。
- SSE：不适用（本卡不订阅）。

## 5. 并发与一致性

| 风险 | 场景 | 方案 |
| --- | --- | --- |
| 同一记录被重复提交 | 定时器与 `online` 事件同时触发 flush | 模块级 `inflight` 守卫（INV-Q3）；同一 tab 只有一个 flush |
| 跨标签页重复提交 | 同一浏览器开两个工位机页，flush 同一条记录 | **不做跨标签锁**：两页用同一 `idempotencyKey`（存于记录），服务端幂等返回首次结果（05 §5），两页都删除该条 |
| 服务端已处理但响应丢失 | 请求到达、响应超时 | 记录留在队列；重试**同键** → 服务端 `idempotent=true` → 删除 |
| 提交中页面被杀 | 记录停在 `syncing` | 页面加载 `reset`：`syncing → pending`；重发同键 |
| 先成功后删除失败 | 服务端成功、IndexedDB 删除抛错 | 下次 flush 重发同键 → 幂等成功 → 再删；无重复计件 |
| 离线连扫同码 | 同一员工同一 `bundle_no` 入队两次 | 不客户端去重；两条各自重试，服务端 BR-PW-24② 对同员工同码返回首次结果（不重复计数），第二条也按成功删除 |

**必须配套的并发测试用例**（见 §9）：

- 20 个到期记录在同一 tick 触发 flush → **只执行一个循环**，每条恰好提交一次。
- 模拟两页用同一条记录（同一 `idempotencyKey`）分别 flush → mock 服务端只落 1 条，两页都删除记录。
- 构造 `syncing` 遗留记录 → 加载后 `reset` 为 `pending`，且重试键与入队时相同。

### 6.1 页面与组件

| 项 | 内容 |
| --- | --- |
| 页面清单 | `piecework/scan`（T-PIECE-007 已有，本卡增强） |
| 组件 | 复用 `Scan.vue` / `ScanDisplay.vue` / `ScanSetupBar.vue` / `useScanMachine.ts`；**新增** `offline/queue.ts`（`idb` 封装：开库、增删查、状态更新）、`offline/useOfflineQueue.ts`（flush 循环 + 响应式计数）、`offline/QueuePanel.vue`（冲突 / 失败展开面板） |

### 6.2 与 `useScanMachine` 的集成点（★ 在线策略）

**选择：在线直连优先，可重试失败回退入队（复用同一幂等键）；离线直接入队。**

`submit()` 流程：

1. 本地正则校验、操作员 / 工序 / 工位就绪校验（T-PIECE-007 不变）。
2. **生成一次** `payload`（`scanned_at = now` 固定）与 `idempotencyKey`。
3. `!navigator.onLine` → **入队**（`enqueue`），行内提示「已离线缓存（第 N 条），联网后自动提交」，**不发请求**。
4. 在线 → 调 `countPiecework(payload, key)`：
   - 成功 → 现有行为（用响应 `today_*` 覆盖大字卡、提示音、绿框）。
   - `32001` / `32006` → 现有行内黄 / 红提示，**不入队**（在线即已确定是业务冲突 / 超产，无需排队）。
   - 可重试错误（网络 / 5xx / `10003` / `10004`）→ **入队（复用同一 `key` 与 `payload`）**，行内提示「网络异常，已缓存」。
   - 其余永久业务错误（§6.4）→ 现有行内红提示，**不入队**。
5. flush 由 `useOfflineQueue` 负责。

**为什么不在线也统一走队列（被否决）**：统一走队列（先入队再 flush）能让离线路径每次都被走到、更耐久，但它改变了 T-PIECE-007 已测的在线语义，且与 [04-计件 §5.1](./04-计件.md) 步骤 8、[06 §2.5](../06-前端与UI规范.md) 第 6 条「网络异常时写本地队列」的既有口径不符 —— 本卡只有 1 张前端卡，不重写在线链路。**代价**（已接受，见 §7）：浏览器在「请求已发出、回退入队之前」被杀会丢这一条，但该码仍是 `counted_at IS NULL`，**重扫即可补回**，不产生账实不符。

### 6.3 `device_id` 口径

- 首次生成 `crypto.randomUUID()`（不可用时退化为随机串），持久化到 **localStorage** 键 `piecework.device_id`；之后读取复用。
- 与 T-PIECE-007 的 `piecework.workstation`（工位号）**是两个概念**：`station_id` = 业务工位位置；`device_id` = 本机设备标识（[07 §7](../07-认证与权限规范.md) 离线归属、问题排查）。两者都随请求发出。
- localStorage 在此**只存设备标识、不存队列** —— 队列在 IndexedDB（与 ADR-0034 的选型一致，不违背「工位机不用 localStorage 做队列」）。

### 6.4 错误分类与呈现

| 类别 | 判定 | 队列动作 | 界面 |
| --- | --- | --- | --- |
| 网络 / 超时 | `fetch` 失败 | `retry` | 行内「网络异常，已缓存」 |
| 服务端故障 | HTTP 5xx / `99999` | `retry` | 同上 |
| 限流 / 处理中 | `10004` / `10003` | `retry` | 同上 |
| 同码已被他人计件 | `32001` | `conflict`（保留） | 顶部冲突徽标 +1；展开显示「已由 张三 09:44 计 60 件」 |
| 超产 | `32006` | `failed` | 顶部失败徽标 +1；展开显示原因 |
| 其他业务拒绝 | `32002` `32005` `20001` `20004` `31001` `31002` `10001` `10002` `12001` `12002` `11001` | `failed`（不重试） | 同上；`11001` 需重新登录后可人工重试 |

### 6.5 顶部常驻条与展开面板

- 基础文案遵 [07 §7](../07-认证与权限规范.md)：`在线` / `离线（缓存 N 条待提交）`。
- 冲突 / 失败计数 > 0 时追加徽标（`冲突 N` / `失败 N`），点击展开 `QueuePanel`：
  - 列表项：`bundle_no`、`scanned_at`、状态、错误文案（冲突项带原计件人 / 时间 / 件数）。
  - 冲突项操作：**删除**；不做任何操作即视为**保留**（下次刷新仍在）。
  - 失败项操作：**重试** / **删除**。

## 7. 风险与回滚

| 风险 | 影响 | 缓解 | 回滚方式 |
| --- | --- | --- | --- |
| 请求已发出但回退入队前浏览器被杀 | 丢一条扫码 | 该码仍 `counted_at IS NULL`，**重扫即可**；§6.2 已接受此代价 | — |
| IndexedDB 不可用（隐私模式 / 配额） | 无法离线缓存 | 开库失败时**明确提示「离线不可用」**，不假装缓存成功；在线仍可扫 | — |
| `device_id` 被清（清缓存） | [07 §7](../07-认证与权限规范.md) 归属信息变化 | 重新生成新 `device_id`，不影响计件正确性（`scanned_at` 才是归属日期的依据） | — |
| 客户端时钟不准 | `scanned_at` 偏差 → `work_date` 错 | 沿用既有口径（BR-PW-11 以 `scanned_at` 归属）；服务端唯一索引兜底不重复 | — |
| 工位机长期离线、队列长期不消 | 工人以为做了、实际未计 | 顶部常驻「离线（N 条待提交）」+ 大字卡**不累加**；恢复后自动补交 | — |
| `idb` 依赖引入 | 供应链 / 体积（约 1KB） | 版本锁 `^8.0.4`（存在性已核实）；不引入其它依赖 | 回退镜像 tag |
| 单文件超 400 行 | 违反 ADR-0030 | 按 §6.1 拆 `queue.ts` / `useOfflineQueue.ts` / `QueuePanel.vue` | — |

- **迁移回滚**：无数据库迁移，不适用（理由：数据只在浏览器）。
- **发布回滚**：镜像回退上一 tag；IndexedDB 残留队列数据无害（旧版本不打开该库，不报错）。

## 9. 测试计划

| 层级 | 用例 | 断言 |
| --- | --- | --- |
| 单元 | 退避序列 | 第 1..8 次失败后 `nextAttemptAt - now ∈ {1,2,4,8,30,30,30}s`；第 8 次失败 → `failed` |
